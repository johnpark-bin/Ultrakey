# F-17 · 키보드별 설정

> **한 줄 요약** — 물리 키보드(VID+PID)마다 독립된 두 기능을 정의한다: (1) **디바이스별 키 변환 세트** — 선택한 키를 다른 키로 바꾸는 규칙의 목록(Karabiner `Simple Modifications` 대응, `left_command ↔ left_option` 스왑은 이 목록의 한 사례일 뿐이다), (2) **디바이스별 Function Keys** — 이 디바이스의 F1~F12 각 키가 `fn` 없이 무엇을 하는지 정의(Karabiner 의 `fn + F1` 의미론은 경로 B 로 표현할 수 없어, "무엇에 매핑할까"가 아니라 "무엇을 하는가"로 다시 정의한다). 경로 B(IOHID `UserKeyMapping`, 정적 usage→usage)로 구현하며, ⭐ **이 기능 자체가 F-07 의 자원 공존 문제(D-1)의 당사자다** — D-1 을 포함한 모든 경로 B 쓰기가 디바이스 한정으로 재설계되지 않으면 이 기능은 **자기 자신을 파괴한다**(스파이크에서 실제로 두 번 일어났다).
> **의존성** — `F-07`(`key-remapping-engine.md`) §3-a2·§3-d·§5 #10·#19, 결정 D-1 — 이 문서는 D-1 이 **디바이스 한정 설치로 재설계됨**을 선행 조건으로 요구한다(§3.6). `F-09`(`preferences-ui.md`) — 새 탭 `Keyboards`, 새 컨트롤 유형(가변 길이 목록 편집기), 종속 표현 3종·탭별 리사이즈 규약의 확장. `F-15`(`settings-store-and-integrity.md`) — 희소 키-값 맵, "부재 = 기본값", 충돌 대화상자 패턴.
> **관련 명세** — `F-05`(`hyperkey.md`) §4 — 소스 키 35종 열거를 기능 1 의 from/to 어휘로 재사용. `F-08`(`power-user-presets.md`), `../dev/architecture.md` §6.1 — D-1 caps lock 모멘터리 정규화(현재 전역 설치, 재설계 대상). [`../research/per-device-hid-spike.md`](../research/per-device-hid-spike.md) — ⭐ **이 명세 전체의 사실 토대. 여기 인용하는 판정을 바꾸지 않는다.** [`README.md`](README.md#-원본과-갈라지는-지점-divergence) — 원본과 갈라지는 지점 색인.

## 1. 개요

⛔ **이것은 원본 SuperKey 에 없는 기능이다.** `README.md` "원본과 갈라지는 지점(divergence)" 표가 이미 확정한 대로, Ultrakey 가 새 탭을 만드는 갈라짐은 `F-16`(한국어 입력, 이슈 #20)에 이어 이것이 두 번째다. 갈라지는 근거는 하나로 충분하다:

> ⭐ **macOS 에는 디바이스별 차등 설정이 없다.** `Use F1, F2, etc. keys as standard function keys` 는 시스템 설정에 **토글 하나**뿐이고 **전역**이다. 외장 키보드는 F-키로, 내장 키보드는 미디어 키로 — 같은 Mac 에서 동시에 두는 것이 macOS 로는 불가능하다. 이것이 이 기능이 존재해야 하는 유일하고 충분한 이유다.

갈라짐이 **아키텍처의 갈라짐이 되어서는 안 된다** — 이 기능은 `F-09`(UI 규약)·`F-15`(저장 규약)·`F-07`(경로 B 인프라)을 그대로 따르고, 새로 만드는 것은 새 탭 하나(§3.1)와 새 컨트롤 유형 하나(가변 길이 목록 편집기, §3.4.1)뿐이다.

### 기능 1 — 디바이스별 키 변환 세트

Karabiner `Simple Modifications` 에 대응하지만 그 UI·규칙을 베끼지 않고 우리 동작으로 다시 쓴다(Karabiner 는 참조로만 인용한다). **선택한 키를 다른 키로 바꾸는 규칙의 목록**을 디바이스마다 갖는다. 경로 B — 정적 usage→usage 테이블 — 로 구현하며, 이 경로의 제약(조건 없음, 정적 대응만 표현 가능, `key-remapping-engine.md` §3-d)에 정확히 들어맞는다.

⭐ **`Left Command ↔ Left Option` 스왑은 별도 기능이 아니다.** 이는 이 목록에 다음 4행을 넣은 한 사례일 뿐이다:

```
left_command  → left_option
left_option   → left_command
right_command → right_option
right_option  → right_command
```

이 기능이 별도의 "modifier swap" 토글을 갖지 않는 이유도 여기 있다 — 목록 편집기 하나가 이 사례를 포함해 임의의 1:1 재배정 요구를 전부 흡수한다.

### 기능 2 — 디바이스별 Function Keys

⭐ **스파이크가 이 기능의 정의를 바꿨다.** 출력(경로 B 목적지로 Consumer Page usage 를 쓰는 것)은 스파이크 S-8 이 **키 입력으로 확인**했다. 그러나 `UserKeyMapping` 은 modifier 조건 필드가 없는 정적 테이블이라(`key-remapping-engine.md` §3-d), `fn + F1` 같은 **조건부** 재정의는 표현할 수 없다. 그래서 우리 기능 2 는 Karabiner 처럼 "`fn + F1` 을 무엇에 매핑할까"를 묻지 않는다 — **"이 디바이스의 F1~F12 각 키가 (fn 없이) 무엇을 하는가"** 를 정의한다. Karabiner 와 같은 사용자 가치를 다른 의미론으로 낸다. 이것은 표현력의 우연한 축소가 아니라 **정직한 재정의**다 — §3.5 에서 상세히 다룬다.

두 기능 모두 3상태 폴백(공통 따름 / 디바이스별 값 / 끔)을 공유하며, 이는 `F-15` 의 "부재 = 기본값" 규약의 재귀적 확장이다(§3.3).

## 2. 사용자 시나리오

**시나리오 A — 외장 키보드에서만 command/option 을 바꾼다.** 사용자가 내장 키보드는 그대로 두고, 자주 쓰는 서드파티 외장 키보드(예: F108Pro)에서만 `left_command ↔ left_option` 4행을 등록한다. `Keyboards` 탭에서 디바이스 선택 팝업을 F108Pro 로 바꾸고 4행을 추가한다. 내장 키보드에서는 이 규칙이 전혀 적용되지 않는다.

**시나리오 B — 여러 키보드에 서로 다른 규칙.** 사무실 키보드에는 `caps lock → left control`, 집 키보드에는 `caps lock → escape` 를 각각 등록한다. 두 규칙은 서로 다른 디바이스 키(`<vid>:<pid>`) 아래 저장되어 있어 충돌하지 않는다 — 스파이크 S-1(실측)이 확정한 대로, `--matching {VID,PID}` 로 쓴 배열은 그 디바이스에만 적용된다.

**시나리오 C — 외장은 F-키로, 내장은 미디어 키로(macOS 로는 불가능한 조합).** 사용자가 내장 키보드는 F1~F12 가 밝기/볼륨 등 미디어 기능으로 동작하길 원하고(노트북을 랩탑처럼 쓸 때), 외장 키보드는 F1~F12 가 개발 도구 단축키(F5=새로고침 등)로 그대로 동작하길 원한다. macOS 의 `Use F1, F2, etc. keys as standard function keys` 는 전역 토글이라 이 조합 자체가 불가능하다 — `Keyboards` 탭에서 내장 키보드를 선택해 F1~F12 각각에 원하는 시스템 기능을 지정하고, 외장 키보드는 손대지 않으면(부재 = 공통 따름, 공통도 부재) 표준 F-키로 남는다.

**시나리오 D — 공통 설정을 따르다 한 디바이스만 끈다.** 사용자가 `For all devices` 아래에 `left_command ↔ left_option` 스왑을 등록해 두었다(모든 키보드에 적용). 그런데 특정 게임용 키보드에서는 이 스왑이 게임 단축키와 충돌해 불편하다. 그 디바이스를 선택해 기능 1 전체를 "끔"으로 설정한다 — 공통 목록은 그대로 있지만 이 디바이스에서는 적용되지 않는다(§3.3 의 `null` sentinel).

**시나리오 E — 디바이스를 뽑았다가 다시 꽂는다.** 사용자가 규칙을 걸어 둔 외장 키보드를 뽑는다. `Keyboards` 탭의 디바이스 팝업에는 그 키보드가 `(연결 안 됨)` 배지와 함께 계속 남아 있고, 설정은 그대로 보존된다. 나중에 같은 키보드(같은 VID+PID)를 다시 꽂으면 핫플러그 감지가 그 디바이스의 합성 배열을 다시 적용한다(§3.6 항목 8).

**시나리오 F — 같은 `from` 을 두 행이 요구한다.** 사용자가 실수로 `caps lock → left control` 행을 두 번 추가한다(두 번째는 `caps lock → escape`). 저장 시점에 F-15 패턴의 충돌 대화상자가 뜨고, 사용자가 확인하면 먼저 만든 행이 꺼지고 새 행이 활성화된다(§3.4).

## 3. 동작 명세

### 3.1 ⭐ `Keyboards` 탭 — 신설 탭 자체의 명세

이 절은 `F-09`(`preferences-ui.md`)가 아직 다루지 않는 다섯 번째 탭의 명세다. F-09 가 확정한 규약(§3.1 탭 구조, §3.7 즉시 반영, §3.8 종속 표현 3종)을 그대로 따르되, 이 탭에서 어떻게 구체화되는지 여기서 정의한다.

#### 3.1.1 탭 이름 — 확정: `Keyboards`(ko: `키보드`)

**근거**: 이 탭의 조직 원리는 "키보드 목록"이다 — 모든 설정이 "어느 키보드인가" 아래에 놓인다. F-09 의 기존 4개 탭이 전부 단일 명사(`Seek`·`Hyperkey`·`Presets`·`General`)이므로 그 형식을 따른다.

**기각한 대안**:
- **`Devices`** — 스파이크 S-1 이 보여주듯 마우스 동글도 키보드 usage(`UsagePage 1 / Usage 6`)를 노출할 수 있어 목록에 뜰 수 있다(스파이크 §2, 대상 디바이스 B — 마우스 동글에 실제로 키 매핑이 걸렸다). "Devices" 라는 넓은 이름은 이 혼동을 부추긴다 — 이름으로 범위를 좁게 그어야 한다.
- **`Per-Device`/`키보드별 설정`** — 형용사구라 다른 탭 이름(단일 명사)과 형식이 어긋난다.
- **`HID`** — 구현 용어가 UI 로 새어 나온다.

#### 3.1.2 탭 내부 배치 — 디바이스 선택은 팝업 버튼

탭 상단에 **디바이스 선택 팝업** 하나를 둔다. 항목 구성(위에서부터):

| 순서 | 항목 | 표시 |
| :--- | :--- | :--- |
| 1 | 공통 계층 | `For all devices` |
| 2 | 현재 붙어 있는 키보드 전부 | 제품명(예: `F108Pro Dongle`, 실측: 스파이크 §10 `hidutil list` 출력의 `Product` 컬럼) |
| 3 | 설정만 남아 있는 미연결 키보드 | 제품명 + `(연결 안 됨)` 접미 |

선택이 바뀌면 그 아래 두 그룹(**키 변환 세트** = 기능 1, **Function Keys** = 기능 2)이 선택된 대상의 값으로 즉시 갈린다(다른 컨트롤과 동일하게 별도 "적용" 버튼 없음, F-09 §3.7).

**근거**: F-09 의 어느 탭에도 사이드바(좌측 목록 + 우측 상세)가 없다. 이 탭만 좌우 분할 구조를 가지면 F-09 §3.1 의 "탭 전환 시 창이 내용에 맞게 리사이즈된다"는 규약과 겹쳐 이 탭만 폭이 크게 튄다. 팝업은 F-09 가 이미 쓰는 컨트롤 유형이라(§3.2 컨트롤 타입 카탈로그) 문자열 카탈로그·키보드 접근성 규약을 그대로 물려받고, 미연결 디바이스도 팝업 항목 하나에 `(연결 안 됨)` 을 붙이는 것만으로 자연스럽게 표현된다.

**기각한 대안 — 좌측 디바이스 목록 + 우측 설정(Karabiner 식 master-detail)**: 한눈에 여러 디바이스를 조망할 수 있다는 장점은 분명하지만, F-09 의 탭 구조 규약(사이드바 없음, 탭별 고정 크기)을 이 탭만 깨고 폭이 크게 늘어난다. ⚠️ 디바이스가 많아지면(예: 여러 대의 외장 키보드를 상시 연결하는 사용자) 팝업이 불편해질 수 있으므로, 이는 **재검토 가능한 결정**으로 §9 에 남긴다.

#### 3.1.3 종속 표현 3종의 적용

F-09 §3.8 의 3종 규약을 이 탭에 다음과 같이 구체화한다.

| 유형 | 이 탭에서의 사례 |
| :--- | :--- |
| **① 비활성화(dimmed)** | 기능 1 목록 편집기의 `+ Add item` 버튼은, 이미 **빈 행**(from 또는 to 가 아직 선택되지 않은 행)이 목록 끝에 있는 동안 dimmed 된다. 근거: 빈 행은 저장하지 않는다는 규약(§3.4.1)을 지키려면, 사용자가 완성되지 않은 행을 여러 개 쌓지 못하게 막아야 한다 — 먼저 그 행을 완성하거나 삭제해야 새 행을 추가할 수 있다 |
| **② 숨김(hidden)** | (a) 선택된 대상이 실제로 붙어 있으면(또는 `For all devices` 를 선택했으면) `(연결 안 됨)` 경고 배지는 DOM/AX 트리에서 완전히 사라진다. 선택된 대상이 미연결 디바이스일 때만 나타난다. (b) `For all devices` 를 선택한 상태에서는 기능 2 각 F-키의 선택 팝업에서 `--- (공통 설정을 따름)` 선택지 자체가 사라진다 — 공통 계층 위에는 따를 상위 계층이 없으므로 그 선택지는 개념적으로 성립하지 않는다. 이때 팝업은 **시스템 기능 12종 + `표준 F-키로 사용`** 만 갖는다 |
| **③ 문장 중간 삽입(inline)** | **해당 없음.** 이 탭의 모든 컨트롤(디바이스 팝업, 기능 1 의 행, 기능 2 의 F-key 팝업)은 라벨 뒤에 컨트롤이 붙는 표준 배치이지, `Caps lock +` [팝업] `= ◀▼▲▶` 류의 문장 중간 삽입 형태가 필요한 자리가 없다. 억지로 이 패턴을 만들지 않는다 — 없는 사례를 있는 것처럼 적는 것보다, 해당 없음을 명시하는 편이 정직하다 |

#### 3.1.4 탭별 리사이즈 — 기준 크기와 목록 영역 스크롤

F-09 §3.1 의 탭별 고정 창 크기 표(Seek 555×378 · Hyperkey 710×517 · Presets 825×527 · General 613×273, 전부 실측)에 이 탭을 추가해야 하지만, **이 탭은 신설이라 실측 근거가 없다** `(미확정)`. 설계 목표만 제안한다: 디바이스 팝업 + 두 그룹(목록 편집기 + F1~F12 표)을 담는 밀도가 `Hyperkey` 탭과 비슷할 것으로 보여, 그 크기(710×517pt)를 잠정 목표로 제안한다. 정확한 pt 값은 실제 UI 구현 후 F-09 문서가 실측·확정해야 한다.

⭐ **목록 편집기 때문에 같은 탭 안에서 높이가 변하는 문제**는 브리프가 이미 내린 결정을 그대로 따른다: **탭 최소 높이를 정하고, 목록이 그보다 길어지면 목록 편집기 영역만 세로 스크롤한다.** 창 자체는 행 추가·삭제로 늘었다 줄었다 하지 않는다. 예시 기준값(제안, `(미확정)`): 행 6개까지는 탭 높이에 흡수하고, 7행째부터 목록 영역 내부 스크롤이 나타난다.

**기각한 대안 — 창을 행 수에 맞춰 계속 리사이즈**: 창이 요동쳐 산만하고, 행이 많으면(예: 20개 매핑을 등록한 파워 유저) 화면 밖으로 넘칠 수 있다.

#### 3.1.5 F-09 §3.1 컨트롤 개수 표에 이 탭을 추가하는 방식

F-09 §3.1 의 탭별 컨트롤 개수 표는 지금까지 전부 고정 정수였다(Seek 9개, Hyperkey 8개 …). 이 탭은 컨트롤 개수가 설계 시점에 정해지지 않으므로 같은 형식을 쓸 수 없다 — **"고정 N개 + 가변 M행"** 형태로 표기한다:

| 항목 | 개수 |
| :--- | :--- |
| 고정 컨트롤 | 4개 — 디바이스 선택 팝업 1 + 그룹 제목 2("키 변환 세트", "Function Keys") + macOS Function Keys 상태 표시줄(읽기전용 뱃지 + 시스템 설정 버튼) 1 |
| 기능 1 (가변) | 선택된 디바이스/공통 계층의 행 수만큼(0행 이상) — 각 행은 팝업 2개 + 삭제 버튼 1 |
| 기능 2 (고정) | 12개 — F1~F12 각각 선택 팝업 1개(§3.5) |

F-09 §4 에 편입할 때는 "고정 16개 + 가변 M행(기능 1)"으로 표기할 것을 제안한다.

### 3.2 디바이스 식별과 열거

**식별자 = VID+PID 쌍.** 설정 키 형태는 `<vid>:<pid>`(16진수, 예: `5ac:24f`).

⭐ **Apple VID 문제의 실제 모습(스파이크 S-3, 실측).** 이슈 #21 은 "VID `0x5ac`(Apple)가 내장 키보드와 헷갈릴 수 있다"고 경고했으나, 실측된 위험은 다른 곳에 있었다 — **VID 단독 매칭은 `IOHIDSystem`(VID `0x5ac`/PID `0x0`/UsagePage `65280`/Usage `23`)을 함께 잡는다.** `IOHIDSystem` 은 개별 디바이스가 아니라 **시스템 전역 매핑의 대상 노드**이므로, VID 만으로 매칭해 쓰면 사실상 전역 쓰기가 된다. **규칙**: 매칭 사전에는 반드시 `VendorID` 와 `ProductID` 를 함께 넣는다. VID 단독 매칭·매칭 없는 `--set` 은 이 문서 전체에서 금지한다(§3.6 에서 재확인).

**열거**: `hidutil list --matching '{"PrimaryUsagePage":1,"PrimaryUsage":6}'` 로 VID·PID·제품명·Transport·Built-In·RegistryID 를 얻을 수 있다(실측, 스파이크 §10). 구현은 같은 매칭 사전을 IOKit(`IOServiceMatching(kIOHIDDeviceKey)` + `UsagePage`/`Usage` 필터)으로 쓴다.

**기존 자산 재사용 판정(스파이크 §10, 실측)**: `ultrakey-platform/src/hotplug.rs` 의 `IOServiceAddMatchingNotification` 기구는 매칭 필터가 `UsagePage 1 / Usage 6` 로 이 기능이 필요로 하는 것과 정확히 같고, Input Monitoring 권한도 불필요해(`docs/dev/architecture.md` §3 "결정 2") **재사용할 수 있다.** ⛔ 그러나 현재 `pub enum HotplugEvent { Attached, Detached }` 는 **디바이스 속성을 싣지 않는다** — 확인 결과 `hotplug.rs` 는 이터레이터를 순회할 뿐 `IORegistryEntryCreateCFProperty` 로 `VendorID`/`ProductID`/`Product` 를 읽지 않는다. 이 기능은 다음 확장을 요구한다:

1. `HotplugEvent::Attached`/`Detached` 가 `DeviceInfo { vendor_id, product_id, product_name, transport, built_in }` 를 함께 싣도록 확장한다. `IORegistryEntryCreateCFProperty` 로 `VendorID`/`ProductID`/`Product` 읽는 경로를 `drain_iterator` 안에 추가하면 된다(스파이크 §10 이 확장 지점으로 지목한 자리와 동일).
2. **현재 붙어 있는 키보드를 열거**하는 API(`list_attached_keyboards() -> Vec<DeviceInfo>`)를 신설한다 — 알림 등록 없이 `IOServiceGetMatchingServices` 로 한 번 순회하는 것으로 충분하다. `Keyboards` 탭의 디바이스 팝업 초기 목록과 §3.6 의 기동 시 재조정(startup reconciliation) 둘 다 이 API 를 쓴다.
3. `Built-In` 값을 얻는 정확한 IOKit 프로퍼티 키는 `(미확정)` — `hidutil list` 의 CLI 출력이 어떤 원천 프로퍼티(들)를 조합해 이 컬럼을 만드는지 스파이크가 확인하지 않았다. `ioreg -l` 로 후보 키를 대조해야 한다(§9).

**`(미확정)`으로 남는 것(스파이크 S-4, 그대로 승계)**:

- 이 검증 기기(`Mac16,11`)에는 **내장 키보드가 없어**, Apple VID 를 보고하는 서드파티 키보드와 진짜 Apple 내장 키보드가 **PID 로 구분되는지 실측하지 못했다.**
- **동일 모델 2대**(같은 VID+PID)는 하나로 보인다. VID/PID 는 원리상 *모델* 식별자이지 *개체* 식별자가 아니다. 이는 실측되지 않은 가정이 아니라 **한계로 명시**한다 — 두 대는 설정을 공유한다(§9 에서 재확인).
- `RegistryID`/`LocationID` 가 재부팅·포트 변경에 걸쳐 안정적인지 확인하지 않았다 — 설정 키로 VID+PID 대신 이들을 쓸 수 있는지는 `(미확정)`.

### 3.3 ⭐ 저장 규약 — 2계층 폴백과 F-15 "부재 = 기본값"의 맞물림

세 상태다: **공통 따름 / 디바이스별 값 / 끔.**

**결론: "공통 따름"은 저장 파일의 *부재*로 표현할 수 있고, 그것이 옳은 설계다.**

저장 키 모양(`F-15` 의 희소 키-값 맵 위에 얹는다):

```
perDevice.all.<기능>.<항목>          — "For all devices" 공통 계층
perDevice.<vid>:<pid>.<기능>.<항목>  — 디바이스별 계층
```

`<기능>` 은 `keyRemap`(기능 1) 또는 `functionKeys`(기능 2), `<항목>` 은 기능 1 에서는 그 디바이스의 규칙 배열 전체(`rows`, §3.4.1 참조), 기능 2 에서는 `f1`~`f12` 각각이다.

**읽기 규칙**: 디바이스별 키가 **없으면** 공통 키를 본다. 공통 키도 **없으면** 매핑을 설치하지 않는다(= macOS 기본 동작). 의사코드:

```
값 = deviceLayer[vid:pid][항목] 이 존재하면 그 값
     그렇지 않고 commonLayer["all"][항목] 이 존재하면 그 값
     둘 다 없으면 "매핑 없음"(macOS 기본 동작)
```

⭐ **F-15 의 "부재 = 기본값"과 충돌하지 않는 이유.** 최상위 계층(공통)의 부재가 곧 기본값이므로, "부재 = 상위 계층 따름"을 재귀적으로 적용하면 맨 위에서 "부재 = 기본값"으로 자연히 귀결된다. 두 규약은 **같은 규약의 1계층/2계층 판본**이다 — F-15 는 계층이 하나(파일에 값이 있는가 없는가)였고, 이 기능은 계층이 둘(디바이스 → 공통 → 없음)일 뿐이다.

⚠️ **단 한 곳에서 명시적 값이 필요하다 — "끔".** "공통은 켜 두었지만 이 디바이스에서만 끈다"는 **부재로 표현할 수 없다**(부재는 "공통 따름"이므로). 그래서 끔은 **명시적 sentinel 값(JSON `null`)**으로 저장한다. F-15 의 희소 맵은 값으로 임의 JSON 을 담으므로 `null` 저장과 키 부재는 구별된다 — 이는 규약 위반이 아니라 **규약 안에서 해결**된다.

⭐ **값 타입 통일 결정(이 문서의 설계 판단, 스파이크 근거 아님).** 기능 1(`rows`)과 기능 2(`f1`~`f12`)는 값의 타입이 다르다(배열 vs 불리언 성격의 상태). 그러나 "끔"의 표현은 **두 기능 모두 JSON `null` 로 통일**한다:

- 기능 1: `perDevice.<vid>:<pid>.keyRemap.rows` = 배열(디바이스별 목록) / `null`(끔) / 부재(공통 따름)
- 기능 2: `perDevice.<vid>:<pid>.functionKeys.f1` = **기능 이름 문자열**(예: `"mute"` — 디바이스별 값) / `null`(끔 = 표준 F-키) / 부재(공통 따름) — **`false` 는 쓰지 않는다**(§3.5).

**근거**: 별도로 "불리언 3원 규칙(부재/`true`/`false`)"을 기능 2 에만 쓰면, 기능 1(배열이라 `false` 자체가 의미를 갖지 않는다)과 기능 2 에서 "끔"의 표현 방식이 달라져 저장 계층 구현과 문서 양쪽에 특수 케이스가 늘어난다. `null` 하나로 통일하면 "이 값이 명시적 끔인가"라는 질문이 **기능과 무관하게 `값 === null` 하나로 판정**된다.

**UI 표기**: 디바이스별 항목의 기본 선택지가 `--- (공통 설정을 따름)`(기능 2 의 선택 팝업 첫 항목, §3.1.3 (b) 참조). 사용자가 다른 값을 고르면 그때 키가 생긴다 — F-15 의 "한 번이라도 건드린 항목만 저장" 과 정확히 일치한다.

### 3.4 기능 1 — 디바이스별 키 변환 세트

**행 스키마**: `{ "from": <소스 키>, "to": <목적 키> }`. from/to 의 어휘는 **v1 은 `F-05` 가 이미 정의한 소스 키 35종 열거를 그대로 쓴다** — `caps lock`·`right option`·`right shift`·`right command`·`right control`·`left option`·`left shift`·`left command`·`left control`·`globe`·`menu (PC)`·`F1`~`F24`.

**근거**: 이 35종은 F-05 가 이미 문자열 카탈로그·팝업 컨트롤·keycode 표를 갖추고 있어 재사용 비용이 0이고, `left_command ↔ left_option` 스왑을 포함한 실사용 요구를 모두 덮는다.

**기각한 대안 — "HID usage 전체 개방"**: usage 어휘가 수백 종으로 늘어나 팝업 UI(스크롤 가능한 리스트 하나에 수백 항목)가 무너지고, 문자열 카탈로그가 폭증한다. 35종으로 충분한 실사용 요구(modifier 재배정·F-키 재배정)를 위해 치를 비용이 아니다.

`(미확정)`: 35종으로 못 덮는 실사용 요구가 있는지 — 예를 들어 문자 키(`a`~`z`)나 숫자 키를 소스/목적으로 하는 재배정 요구가 실제로 있는지는 이번 스파이크·조사 범위 밖이다(§9).

**저장**: §3.3 의 규약대로 `perDevice.<vid>:<pid>.keyRemap.rows`(또는 `perDevice.all.keyRemap.rows`)에 `{from, to}` 객체 배열로 저장한다. **디바이스별 배열이 있으면 공통 배열을 완전히 대체한다(병합하지 않는다)** — 이는 §3.6 이 확정하는 "경로 B 의 배열은 병합이 아니라 통째 교체"(스파이크 S-6)라는 하위 사실과 대칭적인 설계다: 저장 계층의 "리스트 하나 = 원자적 단위"라는 성질이, 경로 B 가 배열을 원자적으로 통째 교체하는 성질과 그대로 맞물린다.

**중복 `from` 검증**: 같은 디바이스(또는 공통 계층) 안에서 같은 `from` 을 두 행이 요구하면 충돌이다. `F-15` 가 이미 쓰는 **충돌 대화상자** 패턴을 따른다 — 저장 시점에 검사하고, 사용자에게 "기존 행을 끄고 새 행을 켤까요?" 류로 묻는다(정확한 문구·버튼 구성은 `F-15` 가 C1~C3 대화상자에 붙인 것과 같은 수준의 상세를 요구하며, 이 문서는 **트리거 조건**만 정의하고 상세 UI 카피는 `F-15`/`F-09` 후속 설계로 위임한다).

### 3.4.1 ⭐ 새 컨트롤 유형 — 가변 길이 목록 편집기 (F-09 확장)

기능 1 의 UI 는 `F-09` 가 지금까지 다룬 컨트롤(체크박스·팝업·슬라이더·단축키 레코더·ⓘ 팝오버, `preferences-ui.md` §3.2)과 다른 **새로운 종류**다. 각 행이 `[from ▾] → [to ▾]` + 삭제 버튼, 목록 아래에 `+ Add item`. 이것을 **"가변 길이 목록 편집기"**라 부른다.

F-09 의 기존 컨트롤과 다른 점 네 가지:

1. **컨트롤 개수가 설계 시점에 정해지지 않는다.** F-09 §3.1 의 탭별 컨트롤 개수 표(Seek 9개·Hyperkey 8개 …)는 이 탭에 고정 숫자를 쓸 수 없다 — §3.1.5 가 "고정 N개 + 가변 M행" 표기로 이를 반영한다.

2. **F-09 의 탭별 고정 리사이즈 규약과 충돌한다.** F-09 는 "탭마다 창 크기가 다르고 탭 전환 시 리사이즈"인데, 목록 편집기는 **같은 탭 안에서 행 추가·삭제로 높이가 변한다.** → 결정: **탭 최소 높이를 정하고, 목록이 그보다 길어지면 목록 영역만 세로 스크롤한다**(§3.1.4). 창이 행마다 늘었다 줄었다 하지 않는다.

3. **종속 표현 3종이 행 단위에는 그대로 적용되지 않는다.** 행은 종속이 아니라 **사용자가 만든 데이터**다. dimmed/hidden/inline 은 "디바이스가 선택되지 않았을 때 목록 전체를 어떻게 하는가" 수준에만 적용한다 — 이 탭에서는 §3.1.3 이 이를 구체화한다(`(연결 안 됨)` 배지, `+ Add item` dimmed).

4. **F-15 의 "컨트롤 단위 즉시 원자적 write-through"를 행 단위로 해석한다.** 행 추가·행 삭제·행의 from/to 변경 각각이 저장 1회다. 정확히는: 이 컨트롤의 저장 **값**은 "행 하나"가 아니라 "그 디바이스의 `rows` 배열 전체"다(§3.3) — 그러나 행 조작(추가/삭제/from-to 변경) 각각이 그 배열 전체를 즉시 다시 write-through 하므로, 사용자 관점에서는 F-15 §3.7 이 확정한 "컨트롤 단위 즉시 저장"과 동일하게 체감된다.

   ⚠️ **`+ Add item` 으로 갓 만든 빈 행(from/to 미선택)은 저장하지 않는다.** 부재 = 기본값 규약을 지키기 위해, 양쪽이 다 정해진 행만 저장 대상이다 — 빈 행이 목록에 있는 동안은 UI 상태로만 존재하고 `rows` 배열에는 반영되지 않는다.

5. **중복 `from` 검증**은 §3.4 에서 다뤘다 — F-15 의 충돌 대화상자 방식을 따른다.

6. **문자열 카탈로그(ko+en)에 새로 필요한 키**: §4.1 에 표로 정리한다. 키 이름 35종(from/to 팝업의 선택지)은 F-05 것을 재사용한다.

### 3.5 ⭐ 기능 2 — 디바이스별 Function Keys

**출력은 가능하다(확정, 실측).** 스파이크 S-8 이 키 입력으로 확인했다 — `UserKeyMapping` 의 목적지로 Consumer Page(`0x0C`) usage 를 쓰면 실제 미디어 키로 동작한다(`volume_increment` = `0xC000000E9` 실측). `NSSystemDefined` 이벤트 계층을 따로 다룰 필요가 없다.

⛔ **그러나 `fn + F1` 형태는 표현할 수 없다(확정).** `UserKeyMapping` 은 정적 usage→usage 테이블이고 modifier 조건 필드가 없다(`key-remapping-engine.md` §3-d). 경로 B 로는 조건부 판정이 불가능하다.

⭐ **그래서 우리 기능 2 는 "`fn + F1` 을 무엇에 매핑할까"가 아니라 "이 디바이스의 F1~F12 각 키가 (fn 없이) 무엇을 하는가"를 정한다.** Karabiner 와 같은 사용자 가치를 다른 의미론으로 낸다 — 이 차이는 우회가 아니라 **정직한 재정의**다. 우리는 Karabiner 를 복제하는 것이 아니다.

**전제 조건**: macOS 시스템 설정의 `Use F1, F2, etc. keys as standard function keys` 가 **켜져 있어야** 한다. 켜져 있을 때 F-키 단독 입력이 Keyboard Page usage 로 도착함을 실측했다(스파이크 S-9 말미 — F9 단독 입력이 Keyboard Page usage `0x42` 로 도착했고, 우리가 설치한 리매핑이 그것을 갈아탔다). ⚠️ **꺼져 있을 때 무엇이 도착하는지는 `(미확정)`** — 그 경우의 동작을 보증하지 않는다(§5·§9).

**시스템 기능 12종과 usage 대응표**:

| F-키 | 기능 | 근거 등급 | Consumer Page usage(0x0C, 16진) |
| :--- | :--- | :--- | :--- |
| F1 | `display_brightness_decrement` | `(미확정)` | 표준 USB HID Consumer Page 정의 기준 후보값 `0x70`(검증 안 됨) |
| F2 | `display_brightness_increment` | `(미확정)` | 후보값 `0x6F`(검증 안 됨) |

| F4 | `spotlight` | `(미확정)` | 표준 Consumer Page 대응이 자명하지 않다 — 위와 동일한 사정 |
| F5 | `dictation` | `(미확정)` | 표준 Consumer Page 대응이 자명하지 않다 — 위와 동일한 사정 |

⭐ **volume_increment 한 종만 `(실측)`이고 나머지 11종은 전부 `(미확정)`이다.** 표의 "후보값" 열은 USB HID Usage Tables 표준 정의를 참고한 **비공식 참조값**일 뿐, 이 프로젝트가 검증한 사실이 아니다 — 근거 등급은 어디까지나 `(미확정)`이며, 후보값은 구현 착수 시 검증 순서를 줄이기 위한 참고로만 둔다. `mission_control`·`spotlight`·`dictation`·`do_not_disturb` 4종은 표준 Consumer Page 대응이 있는지 자체가 불분명해 후보값조차 제시하지 않는다 — Apple 벤더 정의 usage page(비공개)를 요구할 가능성이 있다.

#### ⭐ 각 행은 "켜고 끄기"가 아니라 **"무엇을 할지 고르기"** 다

⚠️ **이 결정을 이진 토글로 축소해서는 안 된다.** F-키마다 `미디어 키로 / 표준 F-키로` 두 상태만 주면, F1 은 영원히 밝기 감소에만 묶이고 **F1 을 `mute` 로 바꾸는 것이 불가능해진다.** 그것은 이 기능이 대응하는 Karabiner `Function Keys` 가 실제로 주는 값(각 행이 12종 중 하나를 고르는 드롭다운)보다 좁고, §1 이 내건 재정의("이 디바이스의 F1~F12 각 키가 **무엇을 하는가**")와도 어긋난다.

**따라서 각 행은 선택 팝업이며 선택지는 다음과 같다:**

| 선택지 | 의미 | 저장 |
| :--- | :--- | :--- |
| `--- (공통 설정을 따름)` | 상위 계층 값을 쓴다 | **키 부재** |
| 시스템 기능 12종 중 하나 | 이 F-키가 그 기능을 낸다 | 기능 이름 문자열(예: `"mute"`) |
| `표준 F-키로 사용` | 이 디바이스에서 이 키는 그냥 F-키다(= 명시적 끔) | `null` |

⭐ **경로 B 관점에서 12종 중 무엇을 고르든 비용이 같다** — 배열 항목의 `Dst` 에 들어가는 usage 값이 달라질 뿐이다. 표현력을 좁힐 기술적 이유가 없다.

**저장**: `perDevice.<vid>:<pid>.functionKeys.f1`~`f12` 각각 **기능 이름 문자열**(디바이스별 값) / `null`(끔) / 부재(공통 따름). §3.3 의 "`값 === null` 이면 명시적 끔" 판정 규약은 그대로 유지된다.

**기본 배치**: `perDevice.all.functionKeys.*` 의 출고 기본값은 **부재**다(= 매핑을 설치하지 않는다 = 표준 F-키). 스크린샷의 `For all devices` 배치(f1 밝기↓ … f12 볼륨↑)는 **Karabiner 가 그렇게 채워 둔 것**이지 우리 출고 기본값이 아니다 — F-15 의 "부재 = 기본값"을 지키려면 우리는 아무것도 미리 쓰지 않아야 한다. 다만 사용자가 각 행을 열었을 때 **그 위치의 관례적 기능이 목록 맨 위에 오도록** 정렬해 선택 비용을 낮춘다.

**UI**: F1~F12 각 행 = 정적 라벨(F-키 번호) + 위 선택 팝업. `For all devices` 선택 시 첫 항목(`--- (공통 설정을 따름)`)은 숨겨진다(§3.1.3).

#### 3.5.1 ⭐ macOS 자체 설정과의 관계 — 왜 별도 기구가 필요한가

macOS 는 `Use F1, F2, etc. keys as standard function keys` **토글 하나**만 갖는다. **전역**이다. ⭐ **macOS 에는 디바이스별 차등 설정이 없다.** 외장 키보드는 F-키로, 내장 키보드는 미디어 키로 — 같은 Mac 에서 동시에 두는 것이 macOS 로는 불가능하다. 이것이 별도 기구가 필요한 유일하고 충분한 근거다(§1 과 동일한 문장을 여기서도 근거로 재확인한다).

UI 는 Karabiner 처럼 **현재 macOS 토글 상태를 표시하고 시스템 설정으로 가는 버튼을 둔다.** 우리가 그 값을 바꾸지는 않는다(사용자의 시스템 설정을 대신 조작하지 않는다) — `Keyboards` 탭 상단의 고정 컨트롤 하나(§3.1.5)가 이 표시줄이다.

**읽는 방법 `(미확정)`**: 이 토글은 전역 도메인의 `com.apple.keyboard.fnState` 불리언으로 추정된다(`(추정)` — 관용적으로 알려진 키 이름이며 스파이크가 직접 검증하지 않았다). `CFPreferencesCopyAppValue`(`kCFPreferencesAnyApplication` 도메인) 로 읽을 수 있을 것으로 보이나 확인되지 않았다. 시스템 설정으로 연결하는 버튼은 `open x-apple.systempreferences:com.apple.preference.keyboard` 류의 URL 스킴을 쓰는 것이 관례이나 이 역시 검증되지 않았다(`(추정)`) — §9.

### 3.6 ⭐ 자원 공존 — 경로 B 합성과 D-1 재설계

스파이크 S-5/S-6 이 실측으로 확정한 것 위에 선다: 한 배열에 규칙 여러 개는 **공존하지만**, `--set` 은 **병합이 아니라 통째 교체**라 마지막에 쓴 쪽이 앞의 것을 전부 지운다.

⚠️ **이것은 가정이 아니다. 스파이크 중에 실제로 두 번 일어났다** — 이슈 #19 워크트리의 Ultrakey 빌드가 D-1 을 **전역으로**(매칭 없이) 설치해, 스파이크가 디바이스에 걸어 둔 규칙을 파괴했다(스파이크 §6, 부록 A). 원인은 명확하다 — 확인 결과 현재 `crates/ultrakey-platform/src/hid_mapping.rs` 의 `HidutilBackend::apply()` 는 `["property", "--set", &json]` 만 호출하고 `--matching` 이 없다. **이것이 매칭 없는 전역 `--set` 이다.**

#### 규칙 1 — 단일 기록자

Ultrakey 는 자신이 관리하는 디바이스의 `UserKeyMapping` 에 대해 **유일한 기록자**다. 다른 프로세스(다른 Ultrakey 인스턴스 포함)가 같은 디바이스에 동시에 써서는 안 된다 — 이 전제가 깨지면 아래 규칙 전부가 무의미해진다.

#### 규칙 2 — ⭐ D-1 을 디바이스 한정으로 바꾼다(선행 조건)

현재 D-1(`caps lock → F18`, `../dev/architecture.md` §6.1)은 **전역으로** 쓰인다(`hid_mapping.rs` 의 매칭 없는 `--set`). 그대로 두면 **F-17 이 자기 자신을 파괴한다** — F-17 이 디바이스 A 에 `--matching {vid,pid}` 로 배열을 쓴 직후, D-1 이 매칭 없이 `--set` 을 부르면 디바이스 A 를 포함한 **모든** 디바이스의 배열이 D-1 한 줄로 갈아치워진다.

⭐ **중요한 아키텍처 함의.** D-1(경로 A 의 caps lock 홀드 판정)은 물리적으로 **어느 키보드에서 caps lock 이 눌렸는지 구분하지 않는다** — 경로 A(`CGEventTap`)는 세션 전체의 병합된 이벤트 스트림을 받으므로(`F-07` §1). 즉 D-1 이 "필요"한 것은 전역 조건(caps-lock 의존 규칙이 하나라도 켜짐)이지만, 그 **설치**는 디바이스마다 이루어져야 한다 — caps lock 물리 키가 달려 있을 수 있는 **모든** 키보드에 `caps lock → F18` 을 걸어야 하기 때문이다. 이는 D-1 이 디바이스 한정으로 바뀌는 순간, **F-07 의 엔진이 F-17 의 디바이스 열거·핫플러그 인프라(§3.2)를 그대로 가져다 써야 한다**는 뜻이다 — 두 기능이 같은 "디바이스별 합성 배열 쓰기" 구성요소를 공유하게 된다.

**F-17 은 이 선행 조건이 충족되지 않으면 착수할 수 없다.** ⚠️ **이슈 #19(물리 caps lock 버그)가 머지된 뒤에도 이 상태 그대로다** — `apply()` 는 여전히 매칭 없이 `--set` 을 부른다. 즉 #19 가 해결해 주지 않았고, **경로 B 를 여는 다음 작업이 명시적으로 처리해야 하는 별도 항목**이다(`README.md` M6 절의 "D-1 디바이스 한정화만 앞으로 당긴다" 참조).

#### 규칙 3 — ⛔ 매칭 없는 `--set` 과 VID 단독 매칭 금지

스파이크 S-3 — VID `0x5ac` 단독 매칭은 `IOHIDSystem`(VID `0x5ac`/PID `0x0`)을 함께 잡아 사실상 전역 쓰기가 된다. 매칭 사전에 **VID+PID 를 항상 함께** 넣는다(§3.2 에서 이미 확인).

#### 규칙 4 — 합성 후 단일 쓰기

한 디바이스의 최종 배열 = **D-1(해당되면) + 기능 1 + 기능 2** 를 모두 합성한 결과다. 이것을 `--matching {vid,pid} --set` **한 번**으로 쓴다. 증분 쓰기(규칙 하나씩 따로 `--set`)는 금지한다 — 스파이크 S-6 이 확정한 "통째 교체" 성질 때문에, 증분 쓰기는 매번 직전 쓰기를 지운다.

#### 규칙 5 — 소스 키 중재 우선순위: `D-1` > `기능 1` > `기능 2`

같은 소스 키를 두 이상이 요구하면 우선순위가 높은 쪽만 배열에 들어간다.

**근거**: D-1 은 엔진 정합성의 전제(caps lock down/up 정규화)라 깨지면 F-08 프리셋과 hyper 가 통째로 오동작한다 — 가장 비싼 실패다. 기능 1 은 사용자가 명시적으로 만든 규칙이라 존중되어야 한다. 기능 2 는 12개 슬롯의 기본 배치라, 양보해도 사용자가 "표준 F-키"라는 macOS 기본 동작으로 돌아갈 뿐이라 **양보 비용이 가장 낮다.**

충돌 시 `F-15` 의 충돌 대화상자로 알리고, **양보당한 쪽을 UI 에 표시한다**(예: 기능 2 의 F9 행 옆에 "이 디바이스의 다른 규칙에 밀려 비활성" 배지).

#### 규칙 6 — 잔존 매핑 정리(`F-07` §3-a2 의 디바이스 판본)

정상 종료 시 **자신이 건드린 모든 디바이스**에 빈 배열을 쓴다. ⭐ 그러려면 **건드린 디바이스 목록(원장)을 저장해 두어야 한다** — 종료 시점에 뽑혀 있는 디바이스는 그때 정리할 수 없으므로, **다음에 그 디바이스가 붙을 때 정리**한다.

**원장의 형태 — 이 문서의 설계 판단.** 별도의 내부 저장 키(예: `perDevice._managedDevices` = 관리한 `<vid>:<pid>` 목록)로 둔다. 이유: 공통 계층(`perDevice.all.*`)만으로도 특정 디바이스에 매핑이 걸릴 수 있다(예: `left_command ↔ left_option` 을 `For all devices` 에 등록하면, 지금까지 그 디바이스 전용 설정 키가 한 번도 생긴 적 없는 디바이스에도 매핑이 걸린다) — 즉 "그 디바이스에 대한 전용 설정 키가 존재하는가"만으로는 "우리가 그 디바이스에 실제로 무언가를 썼는가"를 판정할 수 없다. 그래서 설정 저장소의 키 존재 여부를 원장으로 재활용할 수 없고, **별도의 런타임 원장**이 필요하다.

**정리(cleanup)의 정본은 종료가 아니라 기동(시작 시 재조정)이다** — `F-15` §3.1.1 결정 2 와 같은 이유다: macOS 로그아웃 시 정상 종료 경로가 실행되지 않음이 이미 실측으로 확인되어 있다(`F-15` §3.1.1). 그래서:

- **시작 시**: 원장에 있는 모든 디바이스 각각에 대해 — 현재 붙어 있으면 즉시 현재 설정에서 유도한 계산된 배열을 `--matching {vid,pid} --set` 으로 덮어쓴다(잔존물을 신뢰하지 않는다). 계산된 배열이 빈 배열이면(그 디바이스에 더 이상 아무 설정도 없으면) 빈 배열을 쓰고 원장에서 제거한다.
- **핫플러그 시(규칙 8)**: 새로 붙은 디바이스가 원장에 있는데 붙어 있지 않아 정리하지 못했던 경우라면, 이 시점에 같은 절차를 수행한다.
- ⛔ **남의 매핑은 지우지 않는다** — 사용자가 Ultrakey 와 무관하게 `hidutil` 로 설정해 둔 매핑을 치우는 것은 이 앱의 권한 밖이다(`F-07` §3-a2, `key-remapping-engine.md` §3-a2 와 동일 원칙).

#### 규칙 7 — 읽기는 집계

스파이크 S-2 — 물리 디바이스 1개가 IOHID 서비스 여러 개다(F108Pro 는 3개). `--matching {vid,pid} --get` 은 서비스 수만큼 행을 준다. 잔존 감지는 이 행들을 **집계**해 판정하고, 서비스마다 값이 다른 **부분 실패** 상태도 다뤄야 한다(§5).

#### 규칙 8 — 핫플러그

디바이스가 붙으면 그 디바이스의 합성 배열을 적용한다(`F-07` §5 #10). §3.2 가 확장을 요구한 `hotplug.rs` 의 `Attached` 이벤트가 이 트리거다.

#### 규칙 9 — ⛔ 되읽기 성공을 동작 확인으로 쓰지 마라

스파이크 S-7 — IOHID 는 값을 전혀 검증하지 않아 엉터리 값 `0x9999999999` 도 그대로 저장·반환한다. 구현의 자체 검증 절차가 되읽기에 의존하면 무효다. **함의**: 이 기능의 자동 테스트는 "쓴 값이 되읽힌다"까지만 확인할 수 있고, "실제로 그 키를 눌렀을 때 의도한 동작이 난다"는 `../dev/manual-verification.md` 류의 **수동 검증**을 반드시 병행해야 한다(§8).

## 5. 엣지 케이스와 실패 모드

1. **설정된 디바이스가 뽑혀 있을 때** — 설정은 남기고 디바이스 선택 팝업에 `(연결 안 됨)` 배지로 표시한다. 삭제하지 않는다(시나리오 E).
2. **앱 비정상 종료 후 잔존 매핑** — `F-07` §3-a2 의 디바이스 판본(§3.6 규칙 6). 원장에 있는 디바이스가 다음 실행 시작 또는 재연결 시 계산된 배열로 덮어써진다.
3. **다른 HID 계층 리매퍼(Karabiner 등)와의 공존** — `F-07` §5 #19. Karabiner 는 가상 HID 디바이스를 만들어 붙이므로 **우리 디바이스 목록에 가상 디바이스가 나타날 수 있다.** 그것을 목록에 보일지는 `(미확정)` — 사용자에게 의미 없는 항목(가상 드라이버 이름)이 섞여 혼란을 줄 수도 있고, 반대로 실제로 매핑 가능한 대상이라 숨기면 안 될 수도 있다(§9).
4. **같은 `from` 을 기능 1 의 두 행이 요구** — §3.4 의 충돌 대화상자.
5. **기능 1 과 기능 2 가 같은 F-키를 요구** — 예: 기능 1 에 `F9 → volume_increment` 계열 재배정이 있고 기능 2 도 F9 를 미디어 키로 켠 경우. §3.6 규칙 5(기능 1 > 기능 2)로 결정론적으로 해소하고, 밀린 쪽을 UI 에 표시한다.
6. **macOS Function Keys 토글이 꺼져 있을 때** — 기능 2 동작 보증 안 함 `(미확정)`. UI 는 설정을 계속 편집 가능하게 두되(§3.1.3 이 이 상태를 dimmed 로 강제 잠그지 않기로 결정한 이유), 상단 상태 표시줄이 꺼짐을 알린다.
7. **디바이스가 매핑 적용 도중 뽑힘** — 쓰기(`--set`)가 디바이스 분리와 경합하면 서비스별 부분 실패가 날 수 있다(§3.6 규칙 7). 다음 재연결 시 재조정이 이를 흡수한다.
8. **동일 모델 2대 동시 연결** — VID/PID 만으로는 두 대를 구분하지 못한다(§3.2). 두 대는 설정을 공유한다 — 이는 격하가 아니라 **명시적 한계**다(§9).
9. **경로 B 잔존 매핑이 다른 이유로 이미 걸려 있는 디바이스**(예: 사용자가 직접 `hidutil` 로 매핑해 둔 경우) — §3.6 규칙 6 이 "남의 매핑은 지우지 않는다"고 명시한다. 시작 시 재조정은 **우리 원장에 있는 디바이스만** 계산된 배열로 덮어쓴다 — 원장에 없는 디바이스의 기존 매핑은 건드리지 않는다.
10. **되읽기와 실제 동작의 괴리** — §3.6 규칙 9. 자동 테스트가 "값이 저장·되읽힌다"만 확인하고 "실제로 동작한다"를 확인하지 않으면, 그 결과는 신뢰할 수 없다(§8).

## 7. 구현 접근

**판정: Rust 바인딩.**

- `IOHIDServiceClientSetProperty`/`IORegistryEntryCreateCFProperty` 계열 FFI 가 필요하고(핫플러그 콜백에 디바이스 속성을 싣는 데 `IORegistryEntryCreateCFProperty` 가 필요), 네이티브 `.m`/`.swift` 는 필요 없다 — `key-remapping-engine.md` §7 이 이미 같은 분류를 확정한 IOKit 계열 함수들이다.
- **1차 구현은 기존 `hid_mapping.rs` 처럼 `hidutil` 서브프로세스로 간다.** `key-remapping-engine.md` §7 의 판정 반전(FFI 대신 `hidutil` 1차 채택)과 같은 근거를 그대로 물려받는다 — `IOHIDServiceClientSetProperty`/`IOHIDEventSystemClientCreateSimpleClient` 는 공개 헤더에 없는 심볼이라 시그니처를 검증할 수 없고, `platform-constraints.md` P6 의 경고("시그니처를 추측으로 쓰지 말 것")가 그대로 적용된다.
- 구체적 변경 지점: `HidutilBackend::apply`/`read_current`/`clear` 가 현재 매칭 인자를 받지 않는다(§3.6) — `{VendorID, ProductID}` 매칭 사전을 받는 시그니처로 확장해야 한다. `set_mapping_json` 은 이미 임의 개수의 `KeyMapping` 을 받으므로, 합성된 배열(D-1 + 기능1 + 기능2)을 그대로 넘기면 된다(§3.6 규칙 4).
- `Keyboards` 탭 자체(디바이스 팝업, 목록 편집기, 기능 선택 팝업)는 `F-09` 가 이미 채택한 Tauri/WebView 렌더링 인프라를 그대로 쓴다 — 이 문서가 새로 판정할 렌더링 계층 플랫폼 API 는 없다.

**기각한 대안**: FFI 직접 호출을 1차로 — `key-remapping-engine.md` §7 이 이미 이 대안을 검토하고 기각했다(추측 시그니처의 `extern "C"` 호출은 컴파일·테스트를 통과한 뒤 임의 시점에 UB 를 낸다). 이 문서가 같은 결론을 다시 낼 이유가 없다.

- [ ] 디바이스 A 에 등록한 기능 1/2 설정이 디바이스 B 에 전혀 영향을 주지 않는다(스파이크 S-1 재현).
- [ ] D-1(caps lock 의존 규칙이 켜져 있는 경우)이 설치된 디바이스에서 기능 1/2 설정도 함께 정상 적용된다 — 즉 D-1 과 F-17 이 같은 디바이스의 배열에서 **공존**한다(§3.6 규칙 2·4).
- [ ] 기능 1 목록에서 행을 추가·삭제·수정하면 즉시(별도 저장 버튼 없이) 해당 디바이스의 경로 B 배열이 갱신되고, 빈 행(from/to 미선택)은 저장 파일에 반영되지 않는다.
- [ ] 같은 디바이스에서 같은 `from` 을 요구하는 행 두 개를 만들면 충돌 대화상자가 뜨고, 확인 시 하나만 활성으로 남는다.
- [ ] `Function Keys` 토글이 켜진 macOS 환경에서, 기능 2 에서 어떤 F-키에 `volume_increment` 를 지정하면 실제로 볼륨이 올라간다(스파이크 S-8 재현, **키 입력으로 확인** — 되읽기 성공만으로 판정하지 않는다).
- [ ] 기능 2 의 F-키 팝업에서 `공통 따름`을 선택한 상태(부재)는 저장 파일에 그 디바이스의 해당 키가 생기지 않는다. `끔`을 선택하면 JSON `null` 이 저장된다.
- [ ] `For all devices` 를 선택한 상태에서 기능 2 팝업에는 `공통 따름` 선택지가 나타나지 않는다.
- [ ] 설정된 디바이스를 뽑으면 `(연결 안 됨)` 배지가 나타나고 설정은 삭제되지 않으며, 다시 꽂으면 자동으로 배열이 재적용된다.
- [ ] 앱을 `kill -9` 로 강제 종료한 뒤 재실행하면, 원장에 있는 디바이스의 경로 B 배열이 현재 설정 기준으로 재조정된다(잔존물을 신뢰하지 않고 덮어쓴다).
- [ ] 매칭 사전 없이 `--set` 을 호출하는 코드 경로가 이 기능 관련 코드 전체에 하나도 없다(정적 검토로 확인 가능).
- [ ] 기능 1/기능 2/D-1 이 같은 디바이스의 같은 소스 키를 동시에 요구하면 §3.6 규칙 5 의 우선순위대로 결정론적으로 하나만 적용되고, 밀린 쪽이 UI 에 표시된다.

**폴백 정책 기록 — 검토했으나 기각한 대안들.** 디바이스 구분(§3.2)은 스파이크 S-1 이 **가능한 것으로 실측 확정**했으므로, 주 경로에 폴백은 필요 없다. 그러나 그 판단 과정을 기록으로 남긴다:

- **전역 설정으로 격하** — 기각. S-1 이 디바이스 한정 매핑을 실측으로 확정했다. 격하할 이유가 사라졌다.
- **기능 2 포기** — 기각. S-8 이 Consumer Page 목적지의 실제 동작을 키 입력으로 확인했다. 다만 `fn +` 조건은 표현할 수 없어 §3.5 가 의미론을 다시 정의하는 것으로 대응했다.
- **경로 A 로 구현** — 기각. 경로 A(`CGEventTap`)는 세션 전체 이벤트를 받아 **디바이스를 구분할 수 없다**(`F-07` §1). 표현력은 높지만 이 기능의 핵심 요구(디바이스 한정)를 원리적으로 만족할 수 없다.

**남는 한 가지 진짜 한계**: 동일 모델 2대(같은 VID+PID)는 구분되지 않아 설정을 공유한다(§3.2, §5 항목 8). 이때는 전역 격하가 아니라 **"두 대가 한 항목을 공유한다"**로 다루고, 사용자에게도 그렇게 보이도록 한다(예: 디바이스 팝업에 두 대를 하나의 항목으로만 표시) — 이는 원리적 한계이지 설계 실패가 아니다.
