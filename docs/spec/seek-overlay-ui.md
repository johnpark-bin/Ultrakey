## 1. 개요

Seek 는 사용자가 타이핑한 문자열을 화면에서 찾아 키보드만으로 클릭하는 기능이다(F-01/F-02/F-04). 이 문서는 그 **시각적 표현 계층**만을 다룬다 — 검색어를 받는 UI, 후보 매치를 화면에 표시하는 방식, 선택된 매치를 지시하는 방식이다.

오버레이의 형태는 조사에서 확정됐다. 개발자 본인의 기술 포스트(`ryanhanson.dev/posts/superkey`)가 1차 출처다:

1. **Spotlight 유사 검색 바** — "It's a way to click text that you type in a Spotlight-like search bar."
2. **화면상 매치 하이라이트** — 환경설정의 `Semicolon highlights next match` 라벨이 하이라이트 방식의 존재를 재확인한다.
3. ⭐ **검색 바 → 선택된 매치를 잇는 연결선** — "There are still a couple more shortcomings that will get ironed out in upcoming releases, like drawing the line to the selected match on a different display." 초기 버전은 **다른 디스플레이의 매치로는 선을 그리지 못했다.** v1.55 체인지로그 "Fixed broken Seek behavior on additional displays" 가 이 실패의 수정 이력이다.

이 계층의 가장 중요한 제약은 **하위 앱의 포커스를 빼앗지 않아야 한다**는 것이다 — 사용자는 Seek 를 띄운 상태에서도 원래 작업 중이던 앱에 키보드 포커스가 남아 있다고 인지하며(검색 바는 자체 텍스트 입력을 받지만 이는 F-01 이 라우팅하는 이벤트로 처리되지, macOS 차원의 키 윈도우 전환으로 처리되지 않는다), 오버레이가 열렸다고 해서 대상 앱이 배경으로 밀려나거나 다른 창이 활성화되는 일이 없어야 한다.

## 3. 동작 명세

### 3.1 오버레이 창 생명주기

| 상태 | 진입 조건 | 오버레이의 동작 | 다음 상태 |
| :--- | :--- | :--- | :--- |
| **미생성(Uninitialized)** | 앱 시작 직후 | 창 미생성. 리소스 없음 | F-01 이 최초로 Seek 세션을 열면 **생성**으로 |
| **생성(Created, 숨김)** | 첫 Seek 세션 시작, 또는 이전 세션 종료 후 유휴 | 창 인스턴스는 상주(재생성 비용을 피하기 위해 매 세션마다 파괴하지 않음 `(추정)`), `orderOut`(비표시) 상태, 검색어·하이라이트·연결선 없음 | 세션 시작 시 **표시** |

| **갱신(Active)** | F-02 가 후보 좌표 목록을 전달할 때마다(키 입력마다) | 검색 바 텍스트, 전체 후보 하이라이트, 선택 매치 강조, 연결선을 다시 그림. 이 상태에 머무르며 매 키 입력·매 순환(Tab/화살표/세미콜론)마다 재진입 | 클릭 확정 또는 취소 시 **숨김** |

### 3.3 다중 디스플레이 좌표계 — 결정

**후보안**:

- **안 A — 디스플레이마다 창 하나씩**: 각 창의 로컬 좌표계가 자기 디스플레이 프레임에 국한되어 좌표 변환이 단순하고, 창별로 레벨·collection behavior 를 독립 제어할 수 있다. 그러나 연결선이 디스플레이 경계를 넘을 때 **어느 창의 캔버스에도 선의 중간 구간이 존재하지 않는** 문제가 생긴다 — 개발자 포스트가 명시한 "다른 디스플레이의 매치로 선을 못 그렸다"는 초기 결함은 이 구조에서 나왔을 가능성이 높다.
- **안 B — 전 디스플레이를 덮는 단일 창**: `NSScreen.screens` 의 union frame 을 프레임으로 하는 창 하나를 두면, 검색 바와 모든 하이라이트·연결선이 **하나의 좌표계·하나의 드로잉 서피스**에 존재해 경계를 넘는 선도 평범한 선분 하나로 그려진다. `NSWindow` 는 여러 물리 디스플레이에 걸쳐 배치될 수 있고, 윈도우 서버가 창이 겹치는 각 디스플레이 영역을 해당 디스플레이의 `backingScaleFactor` 로 알아서 합성하므로 배율이 다른 디스플레이 혼용도 창 자체는 단일 인스턴스로 처리된다.

**결정: 안 B(단일 창, union frame)를 채택한다.** 근거:
1. 연결선이 디스플레이 경계를 넘어야 한다는 요구사항이 조사에서 **확정 사실**이다(§1). 이를 안정적으로 만족하려면 단일 좌표계가 사실상 필수다.
2. v1.55 "Fixed broken Seek behavior on additional displays" 는 정확히 이 영역의 실패 이력이며, 안 A 가 재현하기 쉬운 종류의 버그(캔버스 경계 밖으로 못 그림)와 부합한다.
3. 창별 레벨·collection behavior 를 디스플레이마다 다르게 줄 이유가 없다(모든 디스플레이에서 동일한 always-on-top·클릭 통과 정책을 원한다) — 안 A 의 장점이 실익이 적다.

**구현 함의**:
- 창 프레임 = `NSScreen.screens` 전체의 union frame. 디스플레이 추가/제거(핫플러그) 시 재계산 필요(§5).
- macOS 전역 좌표계는 **주 디스플레이 좌하단 원점, Y 축 상향**이며, 보조 디스플레이의 배치에 따라 음수 좌표가 나올 수 있다. F-02 가 넘기는 전역 좌표를 오버레이의 창-로컬 좌표(= union frame 원점 기준 오프셋)로 변환하는 단일 변환식 하나만 유지한다.
- 해상도·배율이 다른 디스플레이 간에도 창 좌표는 포인트(pt) 단위로 통일되며, 픽셀 밀도 차이는 창 서버가 `backingScaleFactor` 별로 처리한다 — 오버레이 그리기 코드는 배율을 직접 신경 쓸 필요가 없다(단, 하이라이트 테두리 두께 같은 시각 상수는 배율이 낮은 디스플레이에서 흐려 보이지 않는지 확인 필요, §9).

### 3.4 검색 바 위치 결정 규칙 `(추정)`

조사에서 검색 바의 화면상 위치는 미확정이다(Q9'). 개발자 포스트는 "연결선을 그린다"는 사실만 언급할 뿐 검색 바가 화면 중앙 고정인지, 활성 창 기준인지, 커서 위치 기준인지 밝히지 않는다.

**제안**(Spotlight 와의 명시적 유사성을 근거로): 검색 바는 **호출된 시점에 마우스 커서가 위치한 디스플레이의 화면 상단부 중앙**에 고정 표시한다 `(추정, 근거: Spotlight 의 기본 배치 관행)`. 활성 창 기준이 아닌 이유는, 활성 창이 전체화면이거나 여러 디스플레이에 걸쳐 있을 때 위치가 불안정해지기 때문이다. → 미확정이므로 §9 로 승계하고, 이 제안은 구현 시작점으로만 쓴다.

### 3.5 하이라이트와 연결선의 시각 표현

| 요소 | 표현 |
| :--- | :--- |
| 비선택 매치 | 후보 텍스트의 bounding box(F-02 제공) 를 저강도 외곽선/반투명 채움으로 표시 |
| 선택된 매치 | 비선택과 뚜렷이 구분되는 강조 색상 + 굵은 테두리. 순환(↑/↓/Tab/⇧Tab/`;`) 시 즉시 갱신 |
| 연결선 | 검색 바의 고정 지점(예: 하단 중앙)에서 선택 매치 bounding box 의 인접 지점까지 직선. 디스플레이 경계를 넘는 경우도 §3.3 의 단일 좌표계 덕에 평범한 선분 하나로 처리 |
| 다크/라이트 모드 | 시스템 외관(`NSApp.effectiveAppearance` 또는 동등 API)에 따라 하이라이트·연결선 색상 팔레트를 전환 — 배경이 아니라 **시스템 외관 모드**를 기준으로 하는 이유는, 오버레이가 실제로 얹히는 배경은 임의의 앱 화면이라 실시간 배경색 분석은 범위 밖이기 때문 |
| 접근성 대비 | WCAG 류의 최소 대비비를 하이라이트·연결선 색상에 적용 `(추정 기본값, §4)` |
| 축소된 모션 | `NSWorkspace.accessibilityDisplayShouldReduceMotion` 이 참이면 하이라이트/연결선의 등장·이동 애니메이션(트윈)을 생략하고 즉시 스냅 전환 |

### 3.6 렌더링 갱신 주기와 지연 예산

- **트리거**: 매 키 입력, 매 순환 입력(↑/↓/Tab/⇧Tab/`;`)마다 F-02 가 필터링된 후보 좌표 목록을 새로 전달 → 오버레이는 이를 받아 즉시 재렌더링한다. 오버레이 자신은 필터링을 수행하지 않는다(F-02 의 책임).
- **예산 목표** `(추정, 근거: 일반 UX 관행 — 사용자가 입력에 대한 반응을 "즉각적"으로 인지하는 상한은 대략 100ms, 60Hz 디스플레이 프레임 예산은 16.7ms)`: 좌표 수신부터 화면 갱신 완료까지 **1프레임(약 16ms) 목표, 총 체감 지연 100ms 이내**를 내부 기준으로 잡는다. 이는 SuperKey 자체에서 확인된 수치가 아니라 이 명세가 제안하는 설계 목표다.
- **⭐ 미확인 리스크(조사 노트 P3)**: 이 예산을 WKWebView 기반 렌더링(Tauri 창의 웹뷰 콘텐츠로 하이라이트를 그리는 경우)이 만족하는지는 **미확인**이다. Rust → JS IPC 왕복, DOM/Canvas 재그리기 비용이 키 입력마다 발생하며, 후보가 수백 개(S5)일 때 특히 위험하다. → §7 구현 접근의 핵심 변수, §9 로 승계.
- **디바운스**: 타이핑이 매우 빠른 구간(버스트)에서 중간 프레임을 건너뛰고 최신 후보만 그리는 코얼레싱이 필요할 수 있다 `(추정)` — 다만 F-02 의 필터링 속도 자체가 병목이면 오버레이 쪽 디바운스는 체감 개선에 한계가 있다.

## 7. 구현 접근

### ⭐ 판정: Tauri 창 생성 + `ns_window()` 네이티브 제어 (창 자체는 하이브리드가 아님) · 렌더링 콘텐츠는 조건부

이 절의 질문은 사실 두 개로 나뉜다. (A) 오버레이 **창** 자체를 Tauri 로 만들 수 있는가, (B) 그 창 **안에 그리는 내용**(검색 바, 하이라이트, 연결선)을 WKWebView 로 그릴 수 있는가. 둘의 답이 다르다.

**(A) 창: Tauri 로 만들 수 있다 — 단, 필수 속성 절반은 `ns_window()` 이스케이프 해치가 있어야 가능하다.**

§3.2 표가 근거다. `decorations`/`transparent`/`always_on_top`/`visible_on_all_workspaces`/`shadow`/클릭 통과/Dock 아이콘 없음은 Tauri v2 설정만으로 충분하다. 그러나 이 문서의 요구사항 중 가장 중요한 두 가지 — **전체화면 앱 위 표시**(window level)와 **활성화하지 않고 표시**(`canBecomeKey`/`orderFrontRegardless`) — 는 Tauri 설정에 없다. 여기에 다중 디스플레이 union frame 계산과 `NSWindowCollectionBehavior` 세부 제어까지 더하면, **Tauri 설정만으로 이 오버레이를 완성하는 것은 불가능**하다고 명확히 결론 내린다.

그러나 이것이 "네이티브 shim 이 필요하다"는 뜻은 아니다. Tauri v2 는 `WebviewWindow::ns_window()` 로 네이티브 `NSWindow` 포인터를 그대로 내주며, 이를 `objc2_app_kit::NSWindow` 로 캐스팅하면 위 네 가지 요구사항 전부를 **Rust 코드 안에서** 처리할 수 있다(§6). 별도 Swift/Objective-C 소스 파일이나 Xcode 프로젝트가 필요하지 않다 — `objc2-app-kit` 은 헤더 자동 생성 Rust 바인딩이다. 따라서 (A) 에 대한 결론은: **오버레이 창은 Tauri 로 생성하되, 표시 방식·레벨·collection behavior·다중 디스플레이 프레임은 반드시 `ns_window()` 를 거쳐 네이티브 `NSWindow` API 로 직접 설정한다.**

**(B) 콘텐츠 렌더링: WKWebView 로 충분한지는 조사 노트 P3 가 미확인으로 남겨 확정할 수 없다.**

이 오버레이는 **키 입력마다 재렌더링**되는 지연 민감 워크로드다(§3.6). Tauri 창 안에서 하이라이트·연결선을 HTML/Canvas/SVG 로 그리면 Rust(F-02 결과 수신) → IPC → JS(DOM/Canvas 갱신) 왕복이 매 키 입력마다 발생한다. 이 왕복이 §3.6 의 예산(프레임 1개, 총 100ms 체감)을 넘는지는 **실측된 바 없다**(`rust-macos-capability-notes.md` §4 P3). 후보가 수백 개인 경우(엣지케이스 10) 특히 위험이 커진다.

대안은 **오버레이만 순수 AppKit/Core Animation 으로 그리고, 환경설정 창만 Tauri 로 두는 하이브리드**다(F-09 는 Tauri 유지, F-03 만 네이티브). 이 경우 하이라이트·연결선은 `CALayer` 를 직접 조작해 그리며, 이는 IPC/DOM 갱신 왕복이 없어 지연에 유리할 것으로 예상된다 `(추정)`. 중요한 점은 이 대안도 **네이티브 shim 이 아니라 `objc2-app-kit`/`objc2-quartz-core` 를 통한 Rust 바인딩**으로 가능하다는 것이다 — Swift/ObjC 프로젝트를 별도로 두지 않아도 된다. 다만 창 생성·이벤트 루프 결합·환경설정 창과의 IPC(검색어 상태 공유 등, F-01 경유)를 손으로 구성해야 하는 비용이 추가된다.

**판정**: (A) 는 확정 — Tauri 창 + `ns_window()` 네이티브 제어. (B) 는 P3 가 실측되지 않은 이상 단정할 수 없으므로, **1차 구현은 WKWebView 렌더링으로 진행하되 렌더링 계층을 별도 모듈로 분리**해, 실측 결과 예산을 넘으면 `CALayer` 직접 그리기로 교체 가능한 구조를 권고한다. 순수 WKWebView 채택을 기본값으로 삼는 이유는 (1) 구현·유지보수 비용이 낮고, (2) 검색 바의 텍스트 입력 UI 는 어차피 웹뷰가 자연스러우며, (3) 실측 전에 순수 네이티브로 단정하는 것은 조사 규칙("사실과 추정을 엄격히 구분")에 어긋나기 때문이다.

### 기각한 대안

| 대안 | 기각 사유 |
| :--- | :--- |
| Tauri 설정만으로 완결(네이티브 API 전혀 사용 안 함) | §3.2 표에서 전체화면 레벨·포커스 없는 표시·다중 디스플레이·collection behavior 세부가 Tauri 설정에 없음이 확정됨 |
| 완전 네이티브(AppKit/CA)를 처음부터 확정 채택 | P3(WKWebView 지연)가 미실측 상태에서 더 비용이 큰 경로를 선확정하는 것은 과도한 추정 |
| 디스플레이마다 별도 창(안 A, §3.3) | 연결선의 디스플레이 경계 통과 요구사항과 정면으로 부딪히며, v1.55 실패 이력과 부합하는 실패 모드를 재현할 위험 |

## 8. 수용 기준

- [ ] 오버레이 표시 중에도 직전에 포커스가 있던 앱의 텍스트 입력 포커스가 유지된다(오버레이가 키 윈도우가 되지 않는다)
- [ ] 오버레이가 표시된 상태에서 오버레이 영역을 클릭하면 클릭이 하위 앱으로 전달된다(클릭 통과)
- [ ] 전체화면 앱 위에서 Seek 를 호출하면 오버레이가 가려지지 않고 표시된다
- [ ] 사용자가 어느 Space 에 있어도(전체화면 Space 포함) Seek 호출 시 오버레이가 나타난다
- [ ] 서로 다른 배율(`backingScaleFactor`)의 디스플레이가 혼용된 환경에서 각 디스플레이의 하이라이트가 흐려지거나 위치가 어긋나지 않는다
- [ ] 검색 바가 있는 디스플레이와 다른 디스플레이의 매치를 선택하면 연결선이 디스플레이 경계를 끊김 없이 넘어 그려진다(v1.55 회귀 방지)
- [ ] 선택된 매치와 비선택 매치가 색상·테두리로 시각적으로 뚜렷이 구분된다
- [ ] 시스템이 다크모드/라이트모드일 때 각각에 맞는 하이라이트·연결선 팔레트가 적용된다
- [ ] `accessibilityDisplayShouldReduceMotion` 이 활성화되어 있으면 하이라이트·연결선의 등장/이동 애니메이션이 생략된다
- [ ] 후보가 수백 개인 검색어에서도 화면 갱신이 눈에 띄게 끊기지 않는다(§4 상한 정책 적용 확인)
- [ ] 디스플레이를 핫플러그(연결/해제)해도 오버레이가 크래시하지 않고 새 union frame 으로 재배치된다
- [ ] Seek 세션 종료(Enter/Esc/hold 해제) 시 오버레이가 즉시 숨겨지고 하이라이트·연결선 잔상이 남지 않는다
- [ ] 앱 종료 시 오버레이 창·레이어·이벤트 구독이 모두 해제된다(리소스 누수 없음)
