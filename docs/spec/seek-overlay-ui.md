## 1. 개요

Seek 는 사용자가 타이핑한 문자열을 화면에서 찾아 키보드만으로 클릭하는 기능이다(F-01/F-02/F-04). 이 문서는 그 **시각적 표현 계층**만을 다룬다 — 검색어를 받는 UI, 후보 매치를 화면에 표시하는 방식, 선택된 매치를 지시하는 방식이다.

오버레이의 형태는 조사에서 확정됐다. 개발자 본인의 기술 포스트(`ryanhanson.dev/posts/superkey`)가 1차 출처다:

1. **Spotlight 유사 검색 바** — "It's a way to click text that you type in a Spotlight-like search bar."
2. **화면상 매치 하이라이트** — 환경설정의 `Semicolon highlights next match` 라벨이 하이라이트 방식의 존재를 재확인한다.
3. ⭐ **검색 바 → 선택된 매치를 잇는 연결선** — "There are still a couple more shortcomings that will get ironed out in upcoming releases, like drawing the line to the selected match on a different display." 초기 버전은 **다른 디스플레이의 매치로는 선을 그리지 못했다.** v1.55 체인지로그 "Fixed broken Seek behavior on additional displays" 가 이 실패의 수정 이력이다.

이 계층의 가장 중요한 제약은 **하위 앱의 포커스를 빼앗지 않아야 한다**는 것이다 — 사용자는 Seek 를 띄운 상태에서도 원래 작업 중이던 앱에 키보드 포커스가 남아 있다고 인지하며(검색 바는 자체 텍스트 입력을 받지만 이는 F-01 이 라우팅하는 이벤트로 처리되지, macOS 차원의 키 윈도우 전환으로 처리되지 않는다), 오버레이가 열렸다고 해서 대상 앱이 배경으로 밀려나거나 다른 창이 활성화되는 일이 없어야 한다.

> ⛔ **한글 조합 입력(IME)은 기본(영어 단일) 구성에서 이 오버레이의 범위 밖이다.** `canBecomeKey = false`(이 절의 핵심 제약 — 하위 앱 포커스 유지)와 IME 조합 버퍼 요구가 정면 충돌한다. `canBecomeKey = true` 로 바꾸면 오버레이가 키 윈도우가 되어 하위 앱이 포커스를 잃고, `false` 를 유지한 채 IME 를 쓰려면 Rust 쪽 한글 자모 결합 엔진이 따로 필요하다. 한/영 키 전환은 F-01(세션 라우팅)이 원본 통과로 복구한다(이슈 #76, `seek-activation-and-session.md` §3.1 한/영 키 예외).
>
> ⭐⭐ **정정 (이슈 #93, Plan §3 D2·D3 — 다국어 세션 한정 유예)**: 검색 언어 설정(`seek.searchLanguage`, `docs/spec/preferences-ui.md` Seek 탭 참조)이 **명시적 비영어**(`ko`·`zh`·`ja`·`es`)면 그 세션은 **인풋 박스 모드**로 동작한다 — 검색 바가 실제 `<input>` 이 되어 macOS IME 가 조합하고, **다국어 세션에 한해** 검색 바 창이 키 윈도우 자격을 일시 부여받는다(`NON_ACTIVATING` 등록부 해제 → `makeKeyAndOrderFront`, 세션 종료 시 재등록).
>
> - **기본(영어 단일·부재) 구성은 이 절의 원래 계약 그대로다** — `canBecomeKey = false` 유지, 포커스 무변화, 회귀 없음. 위 정정은 **명시적으로 다국어를 선택한 세션에만** 적용된다.
> - 다국어 세션의 포커스 핸드오프 비용(이전 앱이 활성 상태를 잃음)은 "클릭 없이 닫히면 이전 최전면 앱으로 복원"으로 상쇄한다(F-01 소관, `seek-activation-and-session.md` §3.2 키 상실·닫힘 행). 클릭 확정(Confirmed)은 F-04 가 이미 대상 앱을 활성화하므로 복원하지 않는다.
> - **입력 소유권 분리**: 글자 입력 = 웹뷰 `<input>`(IME), 세션 제어(Enter·Esc·↑↓·Tab·`;` 순환·`;` 설정) = Rust 상태 머신. 계층 1 게이트가 `Text`/`Backspace`(및 `⌥`+문자 = 데드키) 키를 원본 그대로 통과시키고, `⌘`/`⌃` 조합·제어 키는 계속 소비한다(`seek-activation-and-session.md` §3.1).
> - **한글 조합 자체는 여전히 범위 밖**이었던 "Rust 자모 결합 엔진"(plan 기각 대안 (d))은 그대로 기각이다 — 다국어 검색은 **실제 IME** 로 해결한다.
> - ⭐⭐ **인풋 박스 세션 중 입력 소스 전환 (이슈 #101)**: 검색 바가 실제 `<input>` 이 되어 IME 가 조합을 받는 동안에도 **입력 소스 전환은 살아 있어야** 한다 — 전환 단축키는 웹뷰가 처리하는 게 아니라 **시스템이 처리**한다(이 계층의 렌더링·`<input>` 구현과 무관). 세션 게이트(F-01 소관, `seek-activation-and-session.md` §3.1)가 ① 시스템 단축키 `⌃Space`·`⌃⌥Space` 를 원본 통과시키고 ② `⇧+Space`(F-16.1 켬)를 `⌃Space` 로 치환 발화시킨다. 이 계층이 할 일은 없다 — JS 가 전환 키를 가로채거나 `<input>` 값을 되쓰지 않는다(전환하면 웹뷰가 `compositionend` 로 조합을 flush 하고, 이후 입력은 새 입력 소스로 정상 조합된다).

### 1.1 ⭐ 신규 확정 — 오버레이는 창 여러 개로 구성된 복합체다 (실측: 번들 심볼 · defaults)

번들 분석(`app-bundle-analysis.md` §4.7, §2.1)에서 확인된 내부 타입·defaults 키가 위 3가지 확정 사실을 구조 수준에서 재구성한다. 내부 타입: `OverlayWindow` / `Superkey.OverlayWindow` / `overlayWindows`(복수) / `overlayUI` / `EntryBarWindow` / `EntryBarWindowController` / `EntryBarViewController` / `EntryOutlineView` / `EntryBarTableRowView` / `EntrySearchButton` / `EntrySearchButtonCell` / `ClickablePlaceholderView` / `AutoGrowingTextField` / `RSWidthHuggingTextField` / `RSHeightHuggingTextField` / `RSDimensionHuggingTextField` / `transparentWindow` / `EntryBarDelegate` / `EntryBarMatches` / `EntryBarOptions`.

- ⭐ **오버레이는 창 하나가 아니다.** `overlayWindows` 가 **복수형** 프로퍼티다 → 하이라이트를 그리는 오버레이 창은 **디스플레이마다 하나씩** 두는 구조로 보인다 `(미확정 — 복수형 프로퍼티명과 F-02 의 화면별 OCR 결과 보관 구조로부터의 해석. 실제 창 개수·인스턴스화 시점·좌표 통합 방식은 실행 중 관찰하지 못했다)`. 이 문서가 기존에 오버레이를 단일 창으로 전제한 서술이 있었다면, 그 서술은 §3.3 에서 정정한다.
- ⭐ **검색 바(`EntryBarWindow`)는 하이라이트 오버레이와 별개의 독립 창이며, 위치·크기가 저장된다.** 조사 시점의 `defaults` 에 `NSWindow Frame EntryBarWindow = "1692 1147 400 40 0 0 3840 1570 "` 가 남아 있다 → 검색 바 크기는 **400 × 40 pt**. 관련 키 `persistPosition`. 즉 **사용자가 검색 바를 옮길 수 있고 그 위치가 다음 세션에도 보존된다.** §1 의 "Spotlight 유사"라는 개발자 표현은 여전히 유효한 1차 근거이지만, **화면 중앙에 매 세션 고정된다는 뜻은 아니다** — 이 문서가 검색 바를 "화면 중앙 고정"으로 전제했다면 §3.4 에서 정정한다.
- ⭐ **검색 바에 매치 목록이 표(outline view) 형태로 붙는다.** `EntryOutlineView` / `EntryBarTableRowView` / `matchesList` / `matchesListFirstResponder` / `matchesShown` / `totalMatches` / `displayMatches` 타입·키가 확인된다. 화면 위 하이라이트만이 아니라 **검색 바 자체에도 매치 목록 UI 가 함께 있다** — 기존 명세에 없던 요소다. 목록 항목이 무엇을 표시하는지, 행 클릭이 선택을 바꾸는지, 스크롤 동작 등 시각적·상호작용 상세는 `(미확정)`.
- `AutoGrowingTextField` / `RSWidthHuggingTextField` / `RSHeightHuggingTextField` / `RSDimensionHuggingTextField` — 검색 바 입력 필드가 입력 내용에 따라 스스로 크기를 조절한다(고정폭 400pt 는 최소/기본값일 가능성).
- `ClickablePlaceholderView` / `EntrySearchButton` / `EntrySearchButtonCell` — 검색 바 안에 클릭 가능한 요소(버튼)가 있다. 정체(검색 아이콘? 옵션 버튼?)는 `(미확정)`.

이 절이 뜻하는 바: 이 문서가 다루는 "오버레이"는 실제로는 **검색 바 1개(독립 창, 위치 저장, 표 UI 내장) + 하이라이트 오버레이 N개(디스플레이별로 추정)** 로 구성된 복합체다. 아래 §3 이하의 구체적 창 요구사항·설계 결정은 이 복합 구조를 반영해 재검토한다.

| # | 시나리오 | 흐름 |
| :--- | :--- | :--- |
| S1 | 전역 단축키로 Seek 호출 | `⌥Space` 입력 → 오버레이 창 표시(검색 바만, 하이라이트 없음) → 사용자가 타이핑 → F-02 가 후보를 반환할 때마다 하이라이트 갱신 → ↑/↓/Tab/⇧Tab 으로 선택 매치 이동 → 연결선이 선택 매치를 따라 이동 → Enter → 클릭 트리거(F-04) → 오버레이 숨김 |

| S4 | 매치가 다른 디스플레이에 있음 | 검색 바가 디스플레이 A 에 표시된 상태에서 선택 매치가 디스플레이 B 에 있음 → 연결선이 두 디스플레이 경계를 넘어 이어짐 |
| S5 | 후보가 화면에 매우 많음(수백 개) | 짧은 검색어(예: 한 글자)로 후보 폭증 → 전체 후보에 저강도 하이라이트, 선택된 1개만 강조 하이라이트 + 연결선 |
| S6 | 다크모드에서 밝은 배경 앱 위에 오버레이 | 시스템이 다크모드여도 오버레이는 대상 화면 콘텐츠 위에 얹히므로 하이라이트·연결선의 대비가 배경과 무관하게 유지되어야 함 |
| S7 | 전체화면 앱(예: 전체화면 브라우저) 위에서 Seek 호출 | 오버레이가 전체화면 앱의 window level 위에 표시되어야 함(일반 창은 이 레벨에 도달 못 함) |
| S8 | Esc 또는 세션 취소 | F-01 이 세션 취소를 알림 → 오버레이 즉시 숨김, 하이라이트/연결선 제거, 대상 앱 포커스는 처음부터 바뀐 적이 없으므로 복원 불필요 |

⭐ **순환·확정 키가 실측으로 확정됐다** — Seek 탭 제목 옆 ⓘ 팝오버 원문(SuperKey 원문, 실측: 번들 문자열 `SeekInfoViewController`):
> "Search on screen for text."
> "Use the arrow keys or tab to cycle through matches, and press enter to execute a mouse click."

위 표 S1·S3 의 "↑/↓/Tab" 순환과 "Enter → 클릭 트리거"는 이 인용으로 확정된다. **`⇧Tab`(역방향 순환)은 팝오버에 언급이 없어 `(미확정)`으로 유지한다** — 표 안의 `⇧Tab` 표기는 자연스러운 UX 추정일 뿐 실측 확정이 아니다.

## 3. 동작 명세

### 3.1 오버레이 창 생명주기

| 상태 | 진입 조건 | 오버레이의 동작 | 다음 상태 |
| :--- | :--- | :--- | :--- |
| **미생성(Uninitialized)** | 앱 시작 직후 | 창 미생성. 리소스 없음 | F-01 이 최초로 Seek 세션을 열면 **생성**으로 |
| **생성(Created, 숨김)** | 첫 Seek 세션 시작, 또는 이전 세션 종료 후 유휴 | 창 인스턴스는 상주(재생성 비용을 피하기 위해 매 세션마다 파괴하지 않음 `(추정)`), `orderOut`(비표시) 상태, 검색어·하이라이트·연결선 없음 | 세션 시작 시 **표시** |
| **표시(Search-only)** | F-01 이 세션 시작을 알림 | 검색 바만 그려짐(빈 문자열). 하이라이트·연결선 없음. `orderFrontRegardless` 로 포커스를 뺏지 않고 최상위 표시 | 첫 글자 입력 시 **갱신** |
| **갱신(Active)** | F-02 가 후보 좌표 목록을 전달할 때마다(키 입력마다) | 검색 바 텍스트, 전체 후보 하이라이트, 선택 매치 강조, 연결선, **검색 바 내 매치 목록(표, §1.1)** 을 다시 그림. 이 상태에 머무르며 매 키 입력·매 순환(Tab/↑/↓/세미콜론)마다 재진입 | 클릭 확정 또는 취소 시 **숨김** |
| **숨김(Hidden)** | Enter(클릭 확정, F-04 로 위임) 또는 Esc/hold-키 해제/세션 취소(F-01) | `orderOut` 로 비표시 전환. 검색어·하이라이트·연결선 상태 초기화 | 다음 세션 시작 시 다시 **표시**, 앱 종료 시 **파괴** |
| **파괴(Destroyed)** | 앱 종료 | 창·레이어·이벤트 구독 해제 | — |

> 상주 vs 재생성 정책은 조사에서 확인되지 않았다 `(추정)`. 상주 쪽이 세션마다 `NSWindow` 생성 비용을 피할 수 있어 지연 예산(§3.4)에 유리하다고 보고 기본값으로 제안한다. → §9.

### 3.2 오버레이 창 요구 속성

`rust-macos-capability-notes.md` §2.6 의 판정을 그대로 채택한다. 아래 표는 **하이라이트를 그리는 오버레이 창**(§1.1 의 `overlayWindows`, 복수·디스플레이별로 추정)에 적용되는 요구사항이다. **검색 바 창**(`EntryBarWindow`)은 별개 요구사항을 갖는다 — 위치가 사용자에 의해 이동 가능하고 그 값이 저장되어야 하므로(§1.1, §3.4), "이동 불가"를 전제하는 항목(예: 다중 디스플레이 통합 좌표계에 완전히 종속되는 것)은 검색 바에는 그대로 적용하지 않는다. **활성화하지 않고 표시**는 두 창 모두에 적용된다(검색 바도 텍스트 입력을 받되 macOS 키 윈도우로 전환되지 않아야 한다는 §1 제약 때문).

⭐ **정정 (M3 2차 구현, 이슈 #34)**: **클릭 통과는 하이라이트 창에만 적용한다.** 이 문서가 원래 "두 창 모두"라고 쓴 것은 같은 문서 §8 의 수용 기준 *"검색 바를 사용자가 드래그해 옮기면 앱을 재시작해도 그 위치가 유지된다"* 와 정면으로 부딪힌다 — `ignoresMouseEvents = true` 인 창은 마우스 다운 자체를 받지 못하므로 **드래그가 원리적으로 불가능**하다. 수용 기준 쪽을 살렸다. 검색 바는 `setMovableByWindowBackground(true)` 로 배경 아무 데나 잡고 끌 수 있으며, `canBecomeKey = false` 라서 끌어도 **키 윈도우가 되지는 않는다** — §1 의 핵심 제약은 그대로 지켜진다.

### 3.3 다중 디스플레이 좌표계 — 결정

**후보안**:

- **안 A — 디스플레이마다 창 하나씩**: 각 창의 로컬 좌표계가 자기 디스플레이 프레임에 국한되어 좌표 변환이 단순하고, 창별로 레벨·collection behavior 를 독립 제어할 수 있다. 그러나 연결선이 디스플레이 경계를 넘을 때 **어느 창의 캔버스에도 선의 중간 구간이 존재하지 않는** 문제가 생긴다 — 개발자 포스트가 명시한 "다른 디스플레이의 매치로 선을 못 그렸다"는 초기 결함은 이 구조에서 나왔을 가능성이 높다.
- **안 B — 전 디스플레이를 덮는 단일 창**: `NSScreen.screens` 의 union frame 을 프레임으로 하는 창 하나를 두면, 검색 바와 모든 하이라이트·연결선이 **하나의 좌표계·하나의 드로잉 서피스**에 존재해 경계를 넘는 선도 평범한 선분 하나로 그려진다. `NSWindow` 는 여러 물리 디스플레이에 걸쳐 배치될 수 있고, 윈도우 서버가 창이 겹치는 각 디스플레이 영역을 해당 디스플레이의 `backingScaleFactor` 로 알아서 합성하므로 배율이 다른 디스플레이 혼용도 창 자체는 단일 인스턴스로 처리된다.

⭐ **실측 추가 (실측: 번들 심볼, §1.1)**: 번들 분석에서 `overlayWindows`(복수형 프로퍼티)가 확인됐다. 이는 **원본 SuperKey 의 하이라이트 오버레이가 안 A(디스플레이마다 창 하나씩)에 더 가까운 구조로 구현됐을 가능성**을 시사한다 `(미확정 — 프로퍼티명으로부터의 해석. 실제 창 개수·좌표 통합 방식·연결선을 어느 창에 그리는지는 실행 중 관찰하지 못했다)`. 이는 §1 인용("다른 디스플레이의 매치로는 선을 그리지 못했다")과도 정합적이다 — 하이라이트 창을 디스플레이별로 나누면 정확히 이런 종류의 실패(캔버스 경계를 넘는 선을 그릴 표면이 어느 창에도 없음)가 자연스럽게 발생한다. 검색 바(`EntryBarWindow`)는 이와 별개로 단일 창임이 확정돼 있다(§1.1) — 순환 배정된 것은 하이라이트 오버레이 쪽이지 검색 바가 아니다.

**결정: 클론은 안 B(단일 창, union frame)를 채택한다.** 근거:
1. 연결선이 디스플레이 경계를 넘어야 한다는 요구사항이 조사에서 **확정 사실**이다(§1). 이를 안정적으로 만족하려면 단일 좌표계가 사실상 필수다.
2. v1.55 "Fixed broken Seek behavior on additional displays" 는 정확히 이 영역의 실패 이력이며, 안 A 가 재현하기 쉬운 종류의 버그(캔버스 경계 밖으로 못 그림)와 부합한다.
3. 창별 레벨·collection behavior 를 디스플레이마다 다르게 줄 이유가 없다(모든 디스플레이에서 동일한 always-on-top·클릭 통과 정책을 원한다) — 안 A 의 장점이 실익이 적다.

⭐ **원본과의 차이를 의도적으로 남긴다**: 위 실측은 원본이 실제로는 안 A(디스플레이별 다중 창) 구조를 썼을 가능성을 시사하며, 이는 이 결정과 어긋난다. 그럼에도 안 B 를 유지하는 이유: (1) 안 A 의 대표적 약점(다른 디스플레이로 선을 못 그림)이 §1 인용으로 **실제로 발생했음이 확정된 사실**이다 — 이는 안 A 의 장점이 아니라 결함으로 보고돼 있다. (2) v1.55 체인지로그가 그 결함을 고쳤다는 사실은 있지만, **안 A 구조를 유지한 채 결함만 패치했는지, 구조 자체를 바꿨는지는 조사에서 확인되지 않았다** `(미확정)`. 클론을 처음부터 설계하는 입장에서는 결함이 실제로 보고된 안 A 를 굳이 재현하기보다, 안 B 로 그 결함 발생 여지 자체를 구조적으로 없애는 편이 안전하다고 판단해 이 결정을 유지한다. 원본의 실제 구현 방식(안 A 인지, 이후 안 B 류로 전환됐는지)은 §9 로 승계한다.

**구현 함의**:
- 창 프레임 = `NSScreen.screens` 전체의 union frame. 디스플레이 추가/제거(핫플러그) 시 재계산 필요(§5).
- macOS 전역 좌표계는 **주 디스플레이 좌하단 원점, Y 축 상향**이며, 보조 디스플레이의 배치에 따라 음수 좌표가 나올 수 있다. F-02 가 넘기는 전역 좌표를 오버레이의 창-로컬 좌표(= union frame 원점 기준 오프셋)로 변환하는 단일 변환식 하나만 유지한다.
- 해상도·배율이 다른 디스플레이 간에도 창 좌표는 포인트(pt) 단위로 통일되며, 픽셀 밀도 차이는 창 서버가 `backingScaleFactor` 별로 처리한다 — 오버레이 그리기 코드는 배율을 직접 신경 쓸 필요가 없다(단, 하이라이트 테두리 두께 같은 시각 상수는 배율이 낮은 디스플레이에서 흐려 보이지 않는지 확인 필요, §9).

⭐⭐ **재결정 (M3 2차, 이슈 #34 구현 — 이 결정이 위 "결정: 안 B" 를 대체한다)**

**클론은 안 A(디스플레이마다 창 하나씩)를 채택한다.** 위 안 B 결정을 구현 단계에서 뒤집었다. 근거는 셋이고, 그중 둘은 명세를 쓸 때 보이지 않던 것이다.

1. ⭐ **안 B 는 §8 의 수용 기준 하나를 구조적으로 만족할 수 없다.** 수용 기준: *"서로 다른 배율(`backingScaleFactor`)의 디스플레이가 혼용된 환경에서 각 디스플레이의 하이라이트가 흐려지거나 위치가 어긋나지 않는다."* 그런데 `NSWindow` 하나는 **backing store 를 하나만** 갖고, 그 배율은 창이 가장 많이 겹친 화면 하나로 정해진다. 배율 1.0 화면과 2.0 화면에 걸친 단일 창은 한쪽에서 반드시 리샘플링된다 — 즉 **흐려진다.** 위 §3.3 본문이 "창 서버가 `backingScaleFactor` 별로 알아서 합성한다"고 쓴 것은 창의 *배치*에 대해서는 맞지만 *래스터화 해상도*에 대해서는 맞지 않다. 디스플레이마다 창을 두면 각 창이 자기 화면의 네이티브 배율로 래스터화된다.
2. ⭐ **안 A 의 유일한 알려진 결함이 제거 가능하다.** 그 결함은 "연결선이 디스플레이 경계를 넘을 때 어느 캔버스에도 중간 구간이 없다"이고, 해법은 단순하다 — **연결선을 전역 좌표에서 한 번 정의하고, 창마다 자기 몫만 잘라 그린다**(Liang–Barsky 클리핑, `ultrakey_overlay::geometry::clip_segment`). 이것은 순수 함수 20줄이고 **단위 테스트로 회귀를 막을 수 있다**(v1.55 "Fixed broken Seek behavior on additional displays" 의 재발 방지 테스트가 CI 에서 돈다). 반면 안 B 의 배율 문제는 단위 테스트로 잡히지 않는다 — 실기기에서 눈으로 봐야만 보인다.
3. **실측이 안 A 를 지지한다** (`docs/dev/seek-overlay-render-spike.md` §3.2). Canvas 렌더링 비용의 대부분은 후보 수가 아니라 **서피스 크기에 비례하는 고정비**다. 안 B 의 union frame 은 이 배치에서 6400×1600(10.2 Mpx)이고, 안 A 는 6.1 Mpx + 3.7 Mpx 를 **각자** 그린다 — 게다가 매치가 없는 디스플레이는 통째로 건너뛸 수 있다.
4. 번들 실측(§1.1 `overlayWindows`, 복수형)과도 정합한다. 원본이 안 A 였을 가능성을 시사하는 유일한 실측 근거였고, 이제 그 방향과 어긋나지 않는다.

**여전히 union frame 을 계산한다** — 핫플러그 시 전체 배치를 다시 잡고(§5 #1), 연결선 클리핑의 정의역을 정하고, 검색 바가 어느 화면에도 속하지 않게 되는 경우를 판정하는 데 쓴다(§5 #14). 즉 §3.2 표의 "다중 디스플레이 통합 좌표계" 요구는 그대로 유효하다.

**남는 위험**: 창이 디스플레이 수만큼 생기므로 `orderFrontRegardless`·collection behavior 를 **창마다** 걸어야 하고, 하나라도 빠지면 그 화면에서만 오버레이가 안 뜨는 실패가 난다. → 실기기 검증 항목으로 못박는다(`manual-verification.md` 항목 9).

### 3.4 검색 바 위치 결정 규칙 — 위치 저장은 확정, 최초 기본 위치는 `(추정)`

⭐ **확정(실측: defaults, §1.1)**: 검색 바(`EntryBarWindow`)는 **위치·크기가 저장되는 독립 창**이다. 조사 시점 `defaults` 에 `NSWindow Frame EntryBarWindow = "1692 1147 400 40 0 0 3840 1570 "` 이 남아 있었다 — 크기 **400 × 40 pt**, 관련 키 `persistPosition`. 즉 **사용자가 검색 바를 드래그해 옮기면 그 위치가 다음 세션에도 유지된다.** 개발자 포스트의 "Spotlight 유사"는 외형에 대한 비유일 뿐, **화면 중앙에 매 세션 고정된다는 뜻이 아니다.** 이 문서가 검색 바를 매 세션 화면 중앙 고정으로 전제했다면 이 절에서 정정한다.

**여전히 `(추정)` 인 것 — 원본의 최초 기본 위치**: 사용자가 한 번도 옮기지 않았을 때(설정 초기화 직후, 또는 최초 실행) 검색 바가 **원본에서** 처음 나타나는 기본 위치는 조사에서 확인되지 않았다. 조사 시점 plist 값(`1692 1147`)은 이미 이전 사용 이력이 반영된 값일 수 있어 "출고 기본 위치"의 근거로 쓸 수 없다. ⭐ 클론 자신의 기본 위치 규칙은 아래 이슈 #95 확정 절에서 정한다.

**제안**(Spotlight 와의 명시적 유사성을 근거로, 최초 기본 위치에 한해): 검색 바는 **호출된 시점에 마우스 커서가 위치한 디스플레이의 화면 상단부 중앙**에 최초 표시한다 `(추정, 근거: Spotlight 의 기본 배치 관행)`. 이후 사용자가 옮기면 §1.1 의 `persistPosition` 과 동일하게 그 위치를 저장해 다음 세션에 복원한다. 활성 창 기준이 아닌 이유는, 활성 창이 전체화면이거나 여러 디스플레이에 걸쳐 있을 때 위치가 불안정해지기 때문이다. → 원본의 출고 기본 위치는 미확정이므로 §9 로 승계하고, 이 제안은 구현 시작점으로만 쓴다.

⭐⭐ **확정 (이슈 #95 — 표시 디스플레이 결정 규칙. 위 "제안" 절의 *디스플레이 선택* 부분을 이 절이 대체한다)**

사용자 피드백(2026-09-02): *"Seek 단축키 입력 시 입력창이 떠오르는 디스플레이가 항상 특정 모니터에 고정돼 있다. 마우스가 현재 있는 디스플레이에 뜨거나, 포커스된 윈도우가 있는 곳에 뜨면 사용자가 바로 인지할 수 있다."*

**결정 — 세 가지를 정한다.**

1. **표시 디스플레이는 매 활성화마다 새로 고른다.** 우선순위:
   - ① **마우스 커서가 있는 디스플레이** — 사용자의 시선이 커서를 따르고, 마우스 좌표는 활성화 시점에 읽은 가장 최신의 위치 신호다. 위 "제안" 절의 마우스 우선 기조를 유지한다.
   - ② **포커스된 윈도우가 있는 디스플레이** — 마우스가 다른 화면에 멈춰 있는 키보드 전용 작업(Seek 의 본래 사용 형태 — 세 활성화 경로 셋이 전부 키보드다)에서도 사용자의 실제 작업 위치를 가리킨다. 판정은 `NSScreen.mainScreen`(AppKit 정의: *"현재 키보드·마우스 이벤트를 받는 윈도우가 속한 스크린"*)으로 한다 — 같은 정보를 주는 `AXUIElement`(포커스 윈도우 frame → 디스플레이) 경로보다 단순하고 권한 리스크가 없다. 스냅샷은 세션이 열리기 **직전**에 찍히므로(§1 `canBecomeKey = false` — 검색 바는 아직 키 윈도우가 아님) 이 값은 사용자 앱의 포커스 위치다.
   - ③ **첫 디스플레이**(`NSScreen.screens[0]`, 메뉴바가 있는 주 디스플레이) — ①② 신호가 모두 부재할 때의 폴백(기존 구현의 동작).
2. **저장된 위치(`persistPosition`, §1.1)는 표시 디스플레이를 고르는 데 쓰이지 않는다.** 저장값(절대 좌표)은 그것이 속한 디스플레이 원점 기준 **상대 오프셋**으로만 해석돼, 1 에서 선택된 디스플레이에 적용된다(검색 바가 완전히 들어가도록 클램프). 저장값이 없거나 어느 디스플레이에도 속하지 않으면(핫플러그로 사라진 화면의 흔적) 기본 위치 — 선택된 디스플레이의 **상단부 중앙**(가로 중앙, 세로 상단 20% 지점, 위 제안의 Spotlight 관행) — 를 쓴다.
3. **하이라이트 오버레이와는 일관성 문제가 없다.** 하이라이트 창은 안 A(§3.3 재결정)로 **모든 디스플레이에 하나씩** 뜨므로 "어느 디스플레이에 표시할지"의 결정은 검색 바에만 적용된다. 검색 바가 어느 디스플레이에 뜨든 경계를 넘는 연결선은 §3.3 의 클리핑으로 계속 보장된다.

**근거**: 위 사용자 피드백. 그리고 실측(코드)에서 기존 "고정" 증상의 원인이 둘 확인됐다 — (a) 저장된 위치가 있으면 마우스 기반 결정을 무조건 우회했다(`seek.rs` 의 `stored_origin` 우선 분기). (b) 프로그램적 창 이동에도 `Moved` 이벤트가 발화해(실측: tao 0.35.3 `window_delegate.rs` — AppKit 은 `setFrameOrigin:` 에도 `NSWindowDidMoveNotification` 을 보낸다) 세션 열림마다 계산된 위치가 **사용자 드래그 없이** 저장 파일에 기록됐고, 그 뒤로 (a) 에 의해 영구 고정됐다. 결정 1·2 는 (a) 를 없애고, 구현은 (b) 도 함께 막는다(프로그램적 이동은 영속화하지 않는다 — 그렇지 않으면 매 세션이 설정 파일을 불필요하게 건드려 F-15 "부재 = 기본값" 규약을 흔든다).

**기각한 대안**:

| 대안 | 기각 사유 |
| :--- | :--- |
| 저장된 절대 위치가 계속 우선(현행 유지) | 이슈가 보고한 증상 그 자체. 저장값이 한 번 생기면(위 (b) 로 사실상 첫 세션에 생김) 마우스·포커스 신호가 영원히 무시된다 |
| 저장된 위치를 완전히 폐기(드래그 영속화 제거) | §8 수용 기준 *"드래그해 옮기면 앱을 재시작해도 그 위치가 유지된다"* 를 정면으로 깬다. 결정 2 의 상대 오프셋 해석이 두 요구를 모두 살린다 |
| 포커스 우선(② → ① 순서) | 사용자 피드백이 마우스를 먼저 제시했고, 위 "제안" 절과 Spotlight 관행도 마우스 우선이다. 마우스가 멈춰 있는 키보드 전용 케이스는 ② 가 바로 다음 순위에서 잡는다 |
| `AXUIElement` 로 포커스 윈도우 frame 을 읽어 디스플레이 판정 | `NSScreen.main` 이 같은 정보를 권한·실패 리스크 없이 준다. AX 로 얻을 추가 정보(윈도우 rect 자체)는 이 결정에 필요 없다 |

### 3.5 하이라이트와 연결선의 시각 표현

⭐ **확정: 하이라이트 형태가 매치 출처(OCR/AX)에 따라 다르다** (실측: 번들 문자열, `SeekAccessibilityViewController` ⓘ 팝오버, SuperKey 원문):
> "It's not possible to determine precise locations of text within an Accessibility element, so the entire element will be highlighted by Seek."
> "Seek matches using Optical Character Recognition (OCR) will display in place of duplicate matches from Accessibility."

즉:
- **OCR 매치**는 텍스트 자체의 위치를 알 수 있으므로 **텍스트 단위**(글자/단어 bounding box)로 하이라이트된다.
- **AX 매치**는 Accessibility 요소 내부에서 텍스트의 정확한 위치를 알 수 없으므로 **요소 전체**가 하이라이트된다 — 버튼 하나, 텍스트 필드 하나 전체 등 OCR 매치보다 하이라이트 영역이 크고 거칠 수 있다.
- **중복 시 OCR 이 AX 를 대체한다**: 같은 텍스트가 OCR·AX 양쪽에서 매치되면 화면에는 OCR 쪽(텍스트 단위) 하이라이트만 남는다. 중복되지 않는 나머지 매치에서는 **두 종류의 하이라이트가 한 화면에 공존**한다.
- `Seek using macOS accessibility` 의 출고 기본값이 ☐(꺼짐, `seek-text-detection.md` F-02 참조)이므로, **출고 기본 상태에서는 AX 매치 자체가 없어 이 구분이 나타나지 않는다** — OCR 텍스트-단위 하이라이트만 보인다. 이 구분이 실제로 관찰되려면 사용자가 `Seek using macOS accessibility` 를 켜야 한다.

클론 구현은 매치 객체의 출처(F-02 계약)에 따라 하이라이트 지오메트리 소스를 분기해야 한다 — OCR 매치는 F-02 가 산출한 텍스트 bounding box, AX 매치는 `kAXPositionAttribute`/`kAXSizeAttribute` 로 구한 요소 frame 전체. (`seek-text-detection.md` F-02 상호 참조.)

| 요소 | 표현 |
| :--- | :--- |
| 비선택 매치 (OCR 출처) | 텍스트 bounding box(F-02 제공)를 저강도 외곽선/반투명 채움으로 표시 |
| 비선택 매치 (AX 출처, OCR 과 중복 없음) | AX 요소 frame 전체를 저강도 외곽선/반투명 채움으로 표시 — OCR 매치보다 영역이 넓을 수 있음 |
| 중복 매치 (OCR·AX 동시 검출) | OCR 쪽(텍스트 단위) 하이라이트만 그린다 — AX 쪽은 대체되어 그리지 않는다. 중복 판정 자체는 F-02 책임이며 오버레이는 최종 매치 목록만 받는다 |
| 선택된 매치 | 비선택과 뚜렷이 구분되는 강조 색상 + 굵은 테두리. 순환(↑/↓/Tab/`;`) 시 즉시 갱신. 출처가 AX 든 OCR 이든 강조 표현 자체는 동일하게 적용한다 `(추정)` |
| 연결선 | 검색 바의 고정 지점(예: 하단 중앙)에서 선택 매치 bounding box(OCR) 또는 요소 frame(AX) 의 인접 지점까지 직선. 디스플레이 경계를 넘는 경우도 §3.3 의 단일 좌표계 덕에 평범한 선분 하나로 처리 |
| 다크/라이트 모드 | **세션 시작 시** 시스템 외관(`is_dark_appearance()` — `apps/ultrakey-app/src/seek.rs:144`, 원본은 `NSApp.effectiveAppearance` 또는 동등 API)에 따라 팔레트를 고른다(§4.2 확정값, UXR-11). **세션 안에서 고정**(§5 엣지 11) — 배경이 아니라 **시스템 외관 모드**를 기준으로 하는 이유는, 오버레이가 실제로 얹히는 배경은 임의의 앱 화면이라 실시간 배경색 분석은 범위 밖이기 때문 |
| 접근성 대비 | WCAG 류의 최소 대비비를 하이라이트·연결선 색상에 적용 `(추정 기본값, §4)` |
| 축소된 모션 | `NSWorkspace.accessibilityDisplayShouldReduceMotion` 이 참이면 하이라이트/연결선의 등장·이동 애니메이션(트윈)을 생략하고 즉시 스냅 전환 |

### 3.6 렌더링 갱신 주기와 지연 예산

- **트리거**: 매 키 입력, 매 순환 입력(↑/↓/Tab/⇧Tab/`;`)마다 F-02 가 필터링된 후보 좌표 목록을 새로 전달 → 오버레이는 이를 받아 즉시 재렌더링한다. 오버레이 자신은 필터링을 수행하지 않는다(F-02 의 책임).
- **예산 목표** `(추정, 근거: 일반 UX 관행 — 사용자가 입력에 대한 반응을 "즉각적"으로 인지하는 상한은 대략 100ms, 60Hz 디스플레이 프레임 예산은 16.7ms)`: 좌표 수신부터 화면 갱신 완료까지 **1프레임(약 16ms) 목표, 총 체감 지연 100ms 이내**를 내부 기준으로 잡는다. 이는 SuperKey 자체에서 확인된 수치가 아니라 이 명세가 제안하는 설계 목표다.
- ⭐⭐ **해소 — 실측했다 (M3 2차, 이슈 #34. 전문: `docs/dev/seek-overlay-render-spike.md`)**: 같은 기기·같은 듀얼 디스플레이 배치에서 `Rust emit → WKWebView 렌더 → paint → ack` 왕복을 후보 0~1000개로 쟀다. **답은 "WKWebView 가 느리다"가 아니라 "DOM 이 느리다" 였다.** `<canvas>` 2D 로 그리면 후보가 0개든 **1000개든 왕복 중앙값이 약 25 ms 로 똑같다**(p95 28.3 ms). 그 25 ms 는 그릴 것이 0개일 때도 드는 IPC + 60 Hz 더블 rAF 바닥값이므로, **후보를 그리는 데 추가로 드는 시간이 사실상 0** 이다. 같은 것을 절대배치 DOM 노드로 그리면 500개 **92.5 ms**(p95 108.6 ms), 1000개 **191.4 ms** 로 100 ms 체감 예산을 넘는다. ⭐ JS 실행 시간은 양쪽 다 1~2 ms 였다 — 비용은 스크립트가 아니라 수백 개 요소의 **레이아웃·합성**이다. Rust 쪽 직렬화는 1000개에서도 0.3 ms 다. → **결정 R-1·R-2 (스파이크 §4)**. §7 (B) 를 이 실측으로 확정했고, §9 항목 2 는 해소됐다.
- **(원래 리스크 서술, 이력으로 남김)**: 이 예산을 WKWebView 기반 렌더링(Tauri 창의 웹뷰 콘텐츠로 하이라이트를 그리는 경우)이 만족하는지는 **미확인**이다. Rust → JS IPC 왕복, DOM/Canvas 재그리기 비용이 키 입력마다 발생하며, 후보가 수백 개(S5)일 때 특히 위험하다. **⭐ 이 리스크가 새로운 실측으로 강화됐다**: 원본 SuperKey 는 `NSMainStoryboardFile = Main`(Info.plist)과 `SwiftUI.framework` 링크로 확인되듯 **AppKit + SwiftUI + Storyboard** 로 만들어져 있고, **웹뷰(WKWebView)를 전혀 쓰지 않는다**(실측: 번들 심볼, `app-bundle-analysis.md` §1, §3.1) — `QuartzCore` 가 직접 링크되어 있고 `SpriteKit` 도 강한 링크로 확인된다(용도는 `(미확정)`이나, 매 키 입력마다 재렌더링되는 하이라이트 워크로드에 웹뷰가 아닌 네이티브 드로잉 계층을 쓰는 것과 방향이 맞다). 이는 P3 의 위험이 실재할 가능성을 뒷받침하는 정황이지만, **WKWebView 지연 자체는 여전히 실측되지 않았다** — 원본이 웹뷰를 안 쓴다는 사실이 곧 웹뷰가 예산을 못 맞춘다는 증명은 아니다. → §7 구현 접근의 핵심 변수, §9 로 승계.
- **디바운스**: 타이핑이 매우 빠른 구간(버스트)에서 중간 프레임을 건너뛰고 최신 후보만 그리는 코얼레싱이 필요할 수 있다 `(추정)` — 다만 F-02 의 필터링 속도 자체가 병목이면 오버레이 쪽 디바운스는 체감 개선에 한계가 있다.

| 라벨 (원문) | 값 | 오버레이에 미치는 영향 |
| :--- | :--- | :--- |
| `Semicolon highlights next match` | **☐** (실측: AX 트리 · defaults — 저장 키 `semicolonCycleSeek`) | `;` 입력이 선택 매치를 순환시키고, 오버레이는 매 순환마다 하이라이트·연결선을 갱신(§3.6 의 트리거 중 하나) |

⭐ **기본값 오기 정정**: 이 문서가 스크린샷을 근거로 ☑ 를 출고 기본값으로 서술했다면 오독이다. `Semicolon highlights next match` 는 **홍보 스크린샷에는 ☑ 로 찍혀 있지만, 조사 시점 `defaults` 전량(§app-bundle-analysis §2.1)에 `semicolonCycleSeek` 키가 없고 AX 트리 실측도 ☐ 다.** 아무 설정도 바꾸지 않은 상태에서 키 부재가 곧 기본값이므로 **출고 기본값은 ☐(꺼짐)** 으로 확정한다. ### 4.2 내부 렌더링 상수 — 원본은 `(추정)`, 클론 출고값은 구현이 정본 (UXR-11)

조사에서 확인된 전용 설정 외에, 오버레이 렌더링에는 다음 내부 상수가 필요하다. 사용자 설정 노출 여부는 F-09 범위다.

⚠️ **원본 SuperKey 의 값은 하나도 실측되지 않았다.** Seek 를 실제로 발동시켜 오버레이를 관찰하려면 Screen Recording 권한 프롬프트와 전체 화면 캡처가 뒤따르며, 조사 시점에 관찰 이득 대비 부작용이 크다고 판단해 시도하지 않았다(`app-bundle-analysis.md` §8 항목 3). 따라서 원본 색·두께·애니메이션은 여전히 전부 `(추정)` 이다.

⭐ **클론 출고값 — 구현이 정본 (2026-09-02, UXR-11 명세 따라잡기)**: 이 표의 값은 **추정이 아니라 구현 `crates/ultrakey-overlay/src/palette.rs:66-80` 의 라이트 팔레트 출고값**(이슈 #67 `bar_fg` 포함)으로 확정한다 — 회귀 테스트 4종(`light_and_dark_palettes_differ` · `bar_fg_is_dark_on_light_and_light_on_dark` · `selected_stroke_is_same_across_appearances` · `thickness_and_animation_constants_match_spec_table`)이 그 값을 고정한다. 라이트 팔레트 원값: highlight `rgba(255,214,0,0.35)`·stroke `rgba(191,149,0,0.9)` · selected `rgba(10,132,255,0.28)`·stroke `#0A84FF` · line `#0A84FF` · label `#1A1A1A`/`rgba(255,255,255,0.85)` · **bar `rgba(255,255,255,0.72)`·`bar_fg #1A1A1A`** · border 1/2pt · line 1.5pt · animation 120ms. 다크는 같은 파일의 `Appearance::Dark`(81행~) 가 정본이고 highlight_stroke 는 `rgba(255,214,0,0.9)` 다. **외관 판정은 세션 시작 시 `is_dark_appearance()`**(`apps/ultrakey-app/src/seek.rs:144`) 이며 **한 세션 안에서 고정**된다(`ultrakey-overlay/src/session.rs:48,67` — `OverlaySession.appearance`).

**단서(실측: 번들 문자열, 존재만 — 값 단정 불가)**: 실행 파일에 `findHighlightColor` · `systemYellowColor` · `blueOnBlack` · `crosshairCursor` · `crosshairsTemplate` · `NSVisualEffectMaterial` 문자열/심볼이 있다. 이름으로 미루어 하이라이트가 노랑 계열(`systemYellowColor`)이거나 다크 배경 대비용 색(`blueOnBlack`)일 가능성, 십자선 커서(`crosshairCursor`/`crosshairsTemplate`)를 어딘가에 쓸 가능성, 반투명 재질(`NSVisualEffectMaterial`)을 오버레이 배경에 쓸 가능성을 시사하지만 **어느 것도 값으로 확정되지 않는다.** 아래 표의 클론 출고값(노랑 계열)이 `systemYellowColor` 라는 단서와 방향성이 우연히 일치하지만, 이것이 원본 Seek 하이라이트에 쓰이는 색이라는 근거는 아니다 — 원본 값은 여전히 `(추정)` 이다.

| `objc2_app_kit::NSWindow` (`objc2-app-kit` 0.3.2) | `setLevel()`(전체화면 레벨 이상), `orderFrontRegardless()`, `canBecomeKeyWindow`/`canBecomeMainWindow` 관련 제어, `setCollectionBehavior()`, `setSharingType()`(엣지케이스 12) |

## 7. 구현 접근

### ⭐ 원본의 렌더링 접근 (실측: 번들 메타데이터·심볼)

원본 SuperKey 는 **웹뷰를 전혀 쓰지 않는다.** `Info.plist` 의 `NSMainStoryboardFile = Main` 과 `SwiftUI.framework` 링크로 확인되듯, UI 전체가 **AppKit + SwiftUI + Storyboard** 로 구성돼 있다(`app-bundle-analysis.md` §1, §3.1). `QuartzCore` 가 직접 링크돼 있고 `SpriteKit` 도 강한 링크로 확인된다 — 용도는 `(미확정)`이지만, 매 키 입력마다 재렌더링되는 하이라이트 워크로드(§3.6)를 Core Animation/SpriteKit 계열의 네이티브 드로잉으로 처리했을 가능성과 방향이 맞다. 아래 (A)(B) 판정은 **클론(Tauri 기반)을 위한 설계 결정**이며, 원본이 실제로 이렇게 만들어졌다는 뜻은 아니다 — 그 반대로, 원본은 애초에 이 문제를 웹뷰 없이 풀었다.

이 절의 질문은 사실 두 개로 나뉜다. (A) 오버레이 **창** 자체를 Tauri 로 만들 수 있는가, (B) 그 창 **안에 그리는 내용**(검색 바, 하이라이트, 연결선)을 WKWebView 로 그릴 수 있는가. 둘의 답이 다르다.

**(A) 창: Tauri 로 만들 수 있다 — 단, 필수 속성 절반은 `ns_window()` 이스케이프 해치가 있어야 가능하다.**

§3.2 표가 근거다. `decorations`/`transparent`/`always_on_top`/`visible_on_all_workspaces`/`shadow`/클릭 통과/Dock 아이콘 없음은 Tauri v2 설정만으로 충분하다. 그러나 이 문서의 요구사항 중 가장 중요한 두 가지 — **전체화면 앱 위 표시**(window level)와 **활성화하지 않고 표시**(`canBecomeKey`/`orderFrontRegardless`) — 는 Tauri 설정에 없다. 여기에 다중 디스플레이 union frame 계산과 `NSWindowCollectionBehavior` 세부 제어까지 더하면, **Tauri 설정만으로 이 오버레이를 완성하는 것은 불가능**하다고 명확히 결론 내린다.

그러나 이것이 "네이티브 shim 이 필요하다"는 뜻은 아니다. Tauri v2 는 `WebviewWindow::ns_window()` 로 네이티브 `NSWindow` 포인터를 그대로 내주며, 이를 `objc2_app_kit::NSWindow` 로 캐스팅하면 위 네 가지 요구사항 전부를 **Rust 코드 안에서** 처리할 수 있다(§6). 별도 Swift/Objective-C 소스 파일이나 Xcode 프로젝트가 필요하지 않다 — `objc2-app-kit` 은 헤더 자동 생성 Rust 바인딩이다. 따라서 (A) 에 대한 결론은: **오버레이 창은 Tauri 로 생성하되, 표시 방식·레벨·collection behavior·다중 디스플레이 프레임은 반드시 `ns_window()` 를 거쳐 네이티브 `NSWindow` API 로 직접 설정한다.**

> ⭐ **`makeKeyAndOrderFront` 금지 문구의 예외(이슈 #93)**: 이 절 원래 문구는 "`makeKeyAndOrderFront:` 는 절대 부르지 않는다" 였으나 — **다국어(인풋 박스) 세션의 검색 바 창은 예외**다. 그 창만 `NON_ACTIVATING` 등록부에서 해제된 상태에서 `makeKeyAndOrderFront` 로 키 윈도우 승격(즉 §1 정정 블록). **영어 단일 세션과 하이라이트 창에는 그 금지가 그대로 적용된다.**

**(B) 콘텐츠 렌더링: WKWebView 로 충분한지는 조사 노트 P3 가 미확인으로 남겨 확정할 수 없다.**

이 오버레이는 **키 입력마다 재렌더링**되는 지연 민감 워크로드다(§3.6). Tauri 창 안에서 하이라이트·연결선을 HTML/Canvas/SVG 로 그리면 Rust(F-02 결과 수신) → IPC → JS(DOM/Canvas 갱신) 왕복이 매 키 입력마다 발생한다. 이 왕복이 §3.6 의 예산(프레임 1개, 총 100ms 체감)을 넘는지는 **실측된 바 없다**(`rust-macos-capability-notes.md` §4 P3). 후보가 수백 개인 경우(엣지케이스 10) 특히 위험이 커진다.

대안은 **오버레이만 순수 AppKit/Core Animation 으로 그리고, 환경설정 창만 Tauri 로 두는 하이브리드**다(F-09 는 Tauri 유지, F-03 만 네이티브). 이 경우 하이라이트·연결선은 `CALayer` 를 직접 조작해 그리며, 이는 IPC/DOM 갱신 왕복이 없어 지연에 유리할 것으로 예상된다 `(추정)`. 중요한 점은 이 대안도 **네이티브 shim 이 아니라 `objc2-app-kit`/`objc2-quartz-core` 를 통한 Rust 바인딩**으로 가능하다는 것이다 — Swift/ObjC 프로젝트를 별도로 두지 않아도 된다. 다만 창 생성·이벤트 루프 결합·환경설정 창과의 IPC(검색어 상태 공유 등, F-01 경유)를 손으로 구성해야 하는 비용이 추가된다.

**판정**: (A) 는 확정 — Tauri 창 + `ns_window()` 네이티브 제어. (B) 는 P3 가 실측되지 않은 이상 단정할 수 없으므로, **1차 구현은 WKWebView 렌더링으로 진행하되 렌더링 계층을 별도 모듈로 분리**해, 실측 결과 예산을 넘으면 `CALayer` 직접 그리기로 교체 가능한 구조를 권고한다. 순수 WKWebView 채택을 기본값으로 삼는 이유는 (1) 구현·유지보수 비용이 낮고, (2) 검색 바의 텍스트 입력 UI 는 어차피 웹뷰가 자연스러우며, (3) 실측 전에 순수 네이티브로 단정하는 것은 조사 규칙("사실과 추정을 엄격히 구분")에 어긋나기 때문이다.

⭐ **이 판정을 원본의 실측된 접근 앞에서 재검토한 결과, 판정 자체는 바꾸지 않는다.** 근거: 원본이 웹뷰를 쓰지 않는다는 사실은 "SuperKey 팀이 이 워크로드에 네이티브를 선택했다"는 정황일 뿐, "WKWebView 가 §3.6 의 예산(프레임 1개, 100ms 체감)을 못 맞춘다"는 증명이 아니다 — 웹뷰가 아닌 이유는 성능이 아니라 다른 설계 관성(예: 개발자가 AppKit/Swift 에 이미 익숙함, Tauri 류 도구를 애초에 쓰지 않음)일 수도 있다. 다만 이 실측은 P3 의 **우선순위를 높인다**: 클론 프로젝트는 1차 구현(WKWebView) 착수 초기에 §3.6 지연 예산 실측을 최우선 검증 항목으로 두어야 하며, 실측 없이 WKWebView 로 최종 확정해서는 안 된다. → §9 로 승계.

⭐⭐ **확정 (M3 2차 실측, 이슈 #34 — 전문 `docs/dev/seek-overlay-render-spike.md`)**

위 판정의 조건절("실측 결과 예산을 넘으면 `CALayer` 로 교체")이 **발생하지 않았다.** 실측이 P3 를 닫는다:

- **(B) 의 답: WKWebView 로 확정한다. `CALayer` 로 교체하지 않는다.** 후보 1000개에서 왕복 중앙값 24.84 ms(p95 28.3 ms) — §3.6 의 100 ms 체감 예산 안이고, 후보 0개일 때의 24.99 ms 와 **차이가 없다**(추가 비용 ≈ 0).
- ⭐ **그러나 조건이 하나 붙는다 — 반드시 `<canvas>` 2D 로 그린다.** 같은 워크로드를 절대배치 DOM 노드로 그리면 500개에서 92.5 ms(p95 108.6 ms), 1000개에서 191.4 ms 로 예산을 넘는다(§5 엣지케이스 10 이 경고한 실패가 그대로 재현됐다). ⭐ 비용은 IPC 도 JS 도 아니었다 — JS 실행 시간은 양쪽 다 1~2 ms 였고, 나머지 전부가 **수백 개 요소의 레이아웃·합성**이었다.
- **원본이 웹뷰를 안 쓴다는 사실은 정황이었고, 실측이 그 정황을 기각했다.** 이 문서가 위에서 "정황이지 증명이 아니다"라고 유보한 판단이 옳았다.
- ⭐ **그럼에도 렌더링 계층은 트레이트로 분리해 둔다**(`ultrakey_overlay::renderer::OverlayRenderer`). "지금 이 기기에서 충분하다"가 "영원히 충분하다"는 아니다 — Retina(배율 2.0)와 저사양 기기는 아직 재지 않았고(스파이크 §5), 그때 교체 지점이 없으면 이 판단을 되돌릴 수 없다. `platform-constraints.md` §4.3 이 요구한 것도 정확히 이 이음매다. → 스파이크 결정 R-3.

## 8. 수용 기준

- [ ] 오버레이 표시 중에도 직전에 포커스가 있던 앱의 텍스트 입력 포커스가 유지된다(오버레이가 키 윈도우가 되지 않는다)
- [ ] 오버레이가 표시된 상태에서 오버레이 영역을 클릭하면 클릭이 하위 앱으로 전달된다(클릭 통과)
- [ ] 전체화면 앱 위에서 Seek 를 호출하면 오버레이가 가려지지 않고 표시된다
- [ ] 사용자가 어느 Space 에 있어도(전체화면 Space 포함) Seek 호출 시 오버레이가 나타난다
- [ ] 서로 다른 배율(`backingScaleFactor`)의 디스플레이가 혼용된 환경에서 각 디스플레이의 하이라이트가 흐려지거나 위치가 어긋나지 않는다
- [ ] 검색 바가 있는 디스플레이와 다른 디스플레이의 매치를 선택하면 연결선이 디스플레이 경계를 끊김 없이 넘어 그려진다(v1.55 회귀 방지)
- [ ] 선택된 매치와 비선택 매치가 색상·테두리로 시각적으로 뚜렷이 구분된다
- [ ] 시스템이 다크모드/라이트모드일 때 각각에 맞는 하이라이트·연결선 팔레트가 적용된다
- [ ] `accessibilityDisplayShouldReduceMotion` 이 활성화되어 있으면 하이라이트·연결선의 등장/이동 애니메이션이 생략된다
- [ ] 후보가 수백 개인 검색어에서도 화면 갱신이 눈에 띄게 끊기지 않는다(§4 상한 정책 적용 확인)
- [ ] 디스플레이를 핫플러그(연결/해제)해도 오버레이가 크래시하지 않고 새 union frame 으로 재배치된다
- [ ] Seek 세션 종료(Enter/Esc/hold 해제) 시 오버레이가 즉시 숨겨지고 하이라이트·연결선 잔상이 남지 않는다
- [ ] 앱 종료 시 오버레이 창·레이어·이벤트 구독이 모두 해제된다(리소스 누수 없음)
- [ ] 검색 바를 사용자가 드래그해 옮기면 앱을 재시작해도 그 위치가 유지된다 — 단 표시 디스플레이는 §3.4(이슈 #95) 우선순위로 매 활성화마다 정해지므로, 유지되는 것은 **선택된 디스플레이 안에서의 상대 위치**다(§1.1, §3.4)
- [ ] 다중 디스플레이에서 마우스가 디스플레이 B 에 있을 때 호출하면 검색 바가 디스플레이 B 에 뜨고(특정 디스플레이에 고정되지 않음), 마우스 신호 없이 포커스만 있을 때는 포커스된 윈도우의 디스플레이에 뜬다(이슈 #95, §3.4)
- [ ] 검색 바에 매치 목록이 표 형태로 함께 표시된다(§1.1) — 표 상세 상호작용은 §9 미확정으로 남기되, 목록 자체의 존재는 검증한다
- [ ] AX 출처 매치는 요소 전체가, OCR 출처 매치는 텍스트 단위로 하이라이트되며, 두 종류가 중복될 때 OCR 쪽만 표시된다(§3.5)
- [ ] `Seek using macOS accessibility` 가 꺼진 출고 기본 상태에서는 OCR 텍스트-단위 하이라이트만 나타난다(§3.5)
