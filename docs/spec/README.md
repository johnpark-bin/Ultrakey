# Ultrakey 기능 명세 색인

Ultrakey 는 macOS 유틸리티 **SuperKey**(https://superkey.app/)의 Rust/Tauri 클론이다.
이 디렉터리는 **기능별 구현 명세**를 담는다. 명세가 확정된 뒤 기능 단위로 구현을 위임한다.

> ⭐ **명세 상태: 확정 (2026-08-30).**
> 이 명세들은 처음에 **웹 조사만으로** 작성되었고(PR #2), 이후 **SuperKey v1.66 (66) 을 실제로 설치·실행해 전수 검증**했다(이슈 #3). 검증 결과는 [`../research/spec-verification-report.md`](../research/spec-verification-report.md) 에 있고, 1차 근거는 [`../research/app-bundle-analysis.md`](../research/app-bundle-analysis.md) 와 [`../research/screenshots/`](../research/screenshots/) 에 있다.
> 각 명세 안의 사실에는 근거 등급이 붙어 있다 — `(실측: …)` 은 v1.66 에서 직접 확인한 것, `(미확정)` 은 확인하지 못해 **추측으로 메우지 않고 남겨둔 것**이다. `(추정)` 은 근거 있는 추론이되 확인되지 않은 것이다.

## 구현 접근 3분류

| 분류 | 정의 |
| :--- | :--- |
| **순수 Rust** | 안전(safe) 래퍼 크레이트만으로 커버. `unsafe` 도 네이티브 소스도 없다 |
| **Rust 바인딩** | `unsafe` FFI 직접 호출이 필요. `objc2-*` 자동 생성 바인딩이거나 수기 `extern "C"` 선언. **별도로 빌드하는 `.m`/`.swift` 파일은 없다** |
| **네이티브 shim 불가피** | Rust 에서 호출할 방법이 없어 Swift/Objective-C 소스를 별도 컴파일해 링크해야 함 |

⭐ **17개 기능 중 "네이티브 shim 불가피" 는 없다.** v1.66 실측이 이 판정을 뒤집지 않았다 — 원본이 쓰는 프레임워크는 전부 C ABI 또는 Objective-C 로 노출된다. ⭐ 나중에 추가된 **F-16**(한국어 입력 지원)도 이 판정을 바꾸지 않는다 — 새로 도입하는 플랫폼 API 가 하나도 없고, F-07·F-14 가 이미 쓰는 FFI 를 그대로 재사용한다. ⭐ **F-17**(키보드별 설정)도 마찬가지다 — 경로 B 는 `hidutil` 서브프로세스로도 닿을 수 있음이 실측으로 확인되었다([스파이크](../research/per-device-hid-spike.md)). 근거와 그럼에도 남는 위험은 [`platform-constraints.md` §0·§6](platform-constraints.md) 에 있다.

> ⭐ **v1.66 검증이 만든 변화**
> - **F-15 신설** — 설정 저장 모델("부재 = 기본값")이 실측으로 확정되었고, 명세에 없던 **설정 충돌 감지 대화상자**와 **iCloud 설정 동기화**가 실재함이 드러났다. 셋 다 "설정값을 둘러싼 무결성" 이라는 하나의 관심사라 한 문서로 묶었다. 기각한 대안: 세 개의 얇은 문서로 분리 — 근거가 얇아(대부분 실행 파일 문자열) 각각을 독립 문서로 만들면 추측으로 분량을 채우게 된다.
> - **F-10 이 앱별 비활성화를 흡수** — 메뉴바의 `Ignore <앱이름>` 항목이 그 UI 이고 F-10 이 이미 앱 수명주기를 소유하므로 독립 문서를 만들지 않았다. F-07 은 이 상태를 게이트로 구독만 한다.
> - **meh/bleh 는 F-05 에 유지** — 상태 기계가 hyper 와 동일하고 modifier 마스크만 다르다. 분리하면 같은 표를 세 번 쓰게 된다.
> - **quick press 판정은 F-07 에 유지** — caps lock·shift·hyper 세 곳이 같은 타이밍 판정을 공유하므로 엔진이 소유하는 것이 맞다.

> ⭐ **F-16 신설 (2026-08-30, 이슈 #20) — 원본에 없는 클론 고유 기능이다.**
> 지금까지 F-01~F-15 는 전부 SuperKey v1.66 을 실측해 **재현할 대상이 있는** 명세였다. F-16 은 다르다 — SuperKey 는 한국어 사용자를 대상으로 하지 않으므로 **재현할 원본이 없다.** 1차 근거는 한국어 macOS 사용자가 실제로 운용 중인 Karabiner-Elements 규칙 4종이다.
> **왜 그럼에도 만드는가**: 제품 결정 **D4**(현지화 `ko`+`en`)가 이미 "원본 추종이 아닌 클론 고유 선택"을 한 번 했다. 한국어 UI 를 내놓기로 한 이상 한국어 입력 환경의 결함을 다루는 것이 일관된다.
> ⛔ **오른쪽 command → `⌃⌥⌘` 는 F-16 범위가 아니다** — `Include shift in hyper key` 를 끈 hyper 가 정확히 그것이고, PR #14 가 실기기로 확인했다. 중복 기구를 만들지 않고 `Korean` 탭에 안내만 둔다.
> ⚠️ **F-16 의 절반은 `(미확정)` 위에 서 있다** — 한/영(`lang1`)·한자(`lang2`) 키가 `CGEventTap` 에 어떤 virtual keycode 로 도착하는지 확정하지 못했다. macOS Carbon 에는 한국어용 `kVK_*` 상수가 **아예 없고**(일본어 JIS 용 `0x66`/`0x68` 만 있다), HID usage `0x90`/`0x91` 은 다른 번호 체계다. 실측 절차는 `korean-input.md` §3.2 에 있으며, **한국어 106키 물리 키보드가 없으면 확인 자체가 불가능**하다.

## ⭐ 원본과 갈라지는 지점 (divergence)

Ultrakey 는 SuperKey 의 클론이지만 **복제가 목표는 아니다.** 목표는 원본이 주던 가치를 macOS 에서 다시 내는 것이고, 원본이 다루지 않은 곳에서 사용자가 실제로 겪는 문제가 있으면 **갈라지는 쪽을 택한다.** 갈라짐은 비용(원본과의 대조 검증이 불가능해진다)을 수반하므로 여기 한곳에 모아 근거와 함께 남긴다.

| # | 갈라짐 | 성격 | 왜 갈라지는가 | 상태 |
| :--- | :--- | :--- | :--- | :--- |
| **D4** | **F-14(A) 현지화 (ko + en)** | 횡단 — 새 기능이 아니라 기존 UI 전체에 걸침 | 원본은 영어 단일이다(실측). 한국어 사용자를 1차 대상으로 삼기로 한 제품 결정 | 확정 (이슈 #5) |
| **1** | **[F-16 한국어 입력](korean-input.md) (`Korean` 탭)** | ⭐ **새 탭** | 원본은 한/영 전환·한글 입력 상태를 전혀 다루지 않는다. 한국어 사용자에게는 매일 겪는 문제다. ⚠️ 재현할 원본이 없어 1차 근거가 Karabiner 규칙 4종이다(바로 위 블록) | **명세 확정** (이슈 #20) |
| **2** | **[F-17 키보드별 설정](per-device-settings.md) (`Keyboards` 탭)** | ⭐ **새 탭** | ⭐ **macOS 자체에 디바이스별 차등 설정이 없다.** 외장 키보드와 내장 키보드에 서로 다른 키 배치·Function Keys 를 두는 것이 macOS 로는 불가능하고, 원본도 이를 다루지 않는다. 외장 키보드를 쓰는 사용자에게는 상시 불편이다 | **명세 확정** (이슈 #21) |

**정리** — 갈라짐은 셋이지만 **새 탭을 만드는 갈라짐은 F-16 에 이어 F-17 이 두 번째다.** D4(현지화)는 기존 UI 위에 얹히는 횡단 선택이라 성격이 다르다.

⭐ **갈라짐을 정당화하는 기준** (이후의 갈라짐도 이 기준으로 판단한다):

1. **원본이 다루지 않는 문제여야 한다** — 원본에 있는 것을 다르게 만드는 것은 갈라짐이 아니라 이탈이다
2. **macOS 가 이미 해결해 주지 않아야 한다** — F-17 은 macOS 의 `Use F1, F2, etc. keys as standard function keys` 와 겹치지만, 그 설정이 **전역 하나뿐**이라 디바이스별 차등이 불가능하다는 점이 갈라짐의 근거다
3. **기존 명세의 규약 위에 서야 한다** — F-16·F-17 둘 다 F-09(UI 규약)·F-15(저장 규약)를 그대로 따른다. 갈라짐이 아키텍처의 갈라짐이 되어서는 안 된다

> ✅ M3 완료 판정: 개발자 권장 설정(Caps Lock → Seek, hold 모드, `;` 순환)이 다중 디스플레이에서 동작한다.

### M4 — 배포 (F-13 → F-12)

15. **F-13 자동 업데이트** — Sparkle appcast·EdDSA. ⚠️ 신·구 앱의 **서명 주체가 같아야 TCC 권한이 유지**된다
16. **F-12 라이선싱** — 상태 머신과 추상 인터페이스까지. ⭐ 원본은 **Paddle Classic** 이며 자체 코드 서명 검증을 병용한다 — 개발 중 자체 서명에서 막히지 않게 우회 가능한 형태로 설계한다

### M5 — 마무리와 선택 기능 (F-14(A) → F-06)

17. **F-14(A) 현지화** — ⭐ **원본에는 없는 기능이다**(영어 단일). 클론이 할지 말지는 제품 결정 D4
18. **F-06 트랙패드·Magic Mouse 제스처** — ⚠️ **최후순위**. 비공개 `MultitouchSupport` 에 의존해 OS 업데이트로 조용히 깨질 수 있다. hyper 활성화의 **대체 경로**일 뿐이므로 실패 시 격하 가능한 선택 기능으로 설계한다

### ⭐ M6 — 키보드별 설정 (F-17)

원본에 없는 클론 고유 기능이다(→ [원본과 갈라지는 지점](#-원본과-갈라지는-지점-divergence)). **M5 와 독립**이다.

> ⓘ 같은 "클론 고유" 갈라짐인 **F-16 은 여기가 아니라 M2 3차**에 있다 — F-16 이 건드리는 코드가 M2 가 방금 만든 것이라 컨텍스트가 살아 있을 때 하는 것이 싸기 때문이다(위 M2 3차 근거). F-17 은 사정이 다르다: 경로 B 의 **쓰기 구조 변경**을 요구하고 새 디바이스 열거 인프라가 필요해 얇은 층이 아니다.

19. **F-17 키보드별 설정** — ⭐ **명세는 확정되어 있다**([`per-device-settings.md`](per-device-settings.md), 이슈 #21). 실현 가능성도 실측으로 확정했다([스파이크](../research/per-device-hid-spike.md))

> ### ⚠️ M6 보다 먼저 해야 하는 것 하나 — D-1 의 디바이스 한정화
>
> F-17 은 **경로 B 쓰기가 전부 디바이스 한정이어야** 성립한다. 그러나 D-1(`caps lock → F18`)은 **매칭 없이 전역으로** 쓰인다 — ⭐ **이슈 #19 가 머지된 지금도 그렇다**(`crates/ultrakey-platform/src/hid_mapping.rs` 의 `["property", "--set", &json]` 에 `--matching` 이 없다). 그대로 두면 **F-17 의 디바이스별 매핑을 덮어써 파괴한다.** 이것은 추정이 아니라 스파이크 중 **실제로 두 번 일어난 일**이다(`per-device-hid-spike.md` §6 · 부록 A — 당시 실행 중이던 #19 빌드가 범인이었다).
>
> ⭐ **경로 B 를 손대는 다음 작업에 함께 얹는 것이 옳다** — M6 까지 미루면 그 사이 전역 쓰기를 전제한 호출부가 더 쌓이고, 나중에 전부 추적해야 한다.

| 결정 | 근거 | 기각한 대안 |

| ⭐ **M2 안에서 F-09 를 F-08 앞으로 당긴다** (2026-08-30, 이슈 #13) | M1 완료 판정 5개 중 2~5번(hyper `⌃⌥⌘⇧` 합성, `Include shift` 토글, meh/bleh)이 **환경설정 UI 가 없어서 검증 불가** 상태로 남았다 — `main.rs` 의 `HyperkeySettings::default()` 를 고쳐 재빌드해야만 hyper 를 켤 수 있었기 때문이다. F-09 를 먼저 내면 **M1 의 미검증 항목이 즉시 풀린다.** 의존 관계도 이를 허용한다: F-09 는 F-15 에만 의존하고 F-08 은 F-07·F-05 에 의존하므로 서로 막지 않는다 | ① 원래 순서(F-08 먼저) 유지 — M1 검증 부채가 M2 끝까지 남고, 그 부채 위에 프리셋 16종이 쌓인다. ② M2 를 쪼개지 않고 한 번에 위임 — 증분이 커져 리뷰가 불가능하고, M1 이 1시간 35분 만에 세션 한도로 끊긴 전례가 있다 |

| ⭐ **충돌 감지·클라우드 동기화·저장 모델을 F-15 한 문서로** | 셋 다 "설정값을 둘러싼 무결성" 이고, 뒤 둘은 근거가 얇다(실행 파일 문자열뿐, UI 미관찰). 한 문서에 모아야 그 불확실성이 한곳에 보인다 | 세 개의 얇은 독립 문서 — 근거 대비 분량을 맞추려다 추측으로 메우게 된다 |
| ⭐ **meh/bleh 를 F-05 에 유지, quick press 를 F-07 에 유지** | meh/bleh 는 hyper 와 상태 기계가 동일하고 modifier 마스크만 다르다. quick press 는 caps lock·shift·hyper 세 곳이 같은 타이밍 판정을 공유한다 | 각각 독립 문서 — 같은 표를 세 번 쓰거나, 판정 로직이 세 곳에 복제된다 |
| ⭐ **F-16 을 M2 3차로, M3 앞에 배치한다** | F-16 은 F-07·F-09·F-14·F-10 위에 얹히는 얇은 층이라 새 하부구조가 없다. 그리고 F-16 이 건드리는 코드는 M2 가 방금 만든 것이라 **컨텍스트가 살아 있을 때가 가장 싸다.** M3(Seek)은 4계층으로 가장 크고 위험해 그 뒤에 두면 F-16 이 오래 밀린다 | ① **M3 뒤로** — Seek 이 원본의 대표 기능이라는 제품 근거는 타당하지만, 두 작업 사이에 의존이 없어 **병렬 가능**하므로 순서를 강제할 이유가 없다. ② **M5(선택 기능)로** — F-16 은 이 클론의 실제 사용자가 매일 겪는 문제이고, 하부구조가 이미 있어 "선택 기능" 의 성격이 아니다 |
| ⭐ **`Korean` 탭을 신설한다 — 원본과 의도적으로 갈라진다** | 재현할 원본이 없는 최초의 기능군이다(SuperKey 는 한국어 사용자를 대상으로 하지 않는다). D4(현지화)가 이미 같은 방향으로 한 번 갈라졌으므로 일관된다. 한국어 기능 4종은 서로는 강하게 묶이고 기존 4탭 어디에도 들어가지 않는다 | ① `Presets` 탭 안 섹션 — 성격이 다른 항목이 섞이고, 이미 16종 4그룹으로 가장 큰 탭(825×527pt)이다. ② 한국어 입력기 감지 시에만 노출 — **입력 소스는 런타임에 바뀐다.** 탭이 나타났다 사라지고 탭별 창 리사이즈(F-09 §3.3)와 최악으로 겹친다. ③ 시스템 로케일이 `ko` 일 때만 노출 — 영어 UI 를 쓰면서 한국어로 입력하는 사용자를 배제한다 |

### 이 결정들이 구현 순서에 미친 영향

- **D4 만 M1 을 건드렸다.** D2·D3 는 각각 M4·M5 범위라 M1 착수를 막지 않는다.
- D4 채택으로 **로케일 목록이 확정**되었으므로, `localization-and-input-sources.md` §3.1.1 이 "클론이 정할 문제"로 되돌려 두었던 로케일 집합은 이제 **`en` + `ko` 2종**이다. 다만 §3.1.4 의 **RTL 미러링 규칙은 M1 범위 밖이다** — `ko`·`en` 둘 다 LTR 이라 M1 에서는 적용 대상이 없다. 규칙 자체는 나중에 RTL 로케일을 추가할 때를 위해 명세에 남겨 둔다.
- D3 를 "빼기"가 아니라 "최후순위"로 정했으므로 `trackpad-hyper-gesture.md` 는 폐기하지 않는다. `hyperkey.md` §3.5 의 조건부 표시 2종(`Change menu bar icon when engaged` · `Provide haptic feedback when triggered`)도 F-05 에 그대로 남는다.
