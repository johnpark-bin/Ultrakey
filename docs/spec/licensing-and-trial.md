# F-12 · 라이선싱과 트라이얼

> **한 줄 요약**: 20일 체험과 "1 라이선스 = 동시 활성 3대"라는 확정된 상업적 제약 위에서, 트라이얼 상태 머신·라이선스 활성화/비활성화/검증의 추상 계약·오프라인 유예 규칙을 정의하고, 클론 프로젝트가 Paddle 을 실제로 붙일지 라이선스 계층을 추상화만 해둘지를 결정한다.
> **의존성**: 없음(F-12 는 다른 명세의 산출물에 기술적으로 의존하지 않는다). 다만 §4 의 설정 UI 배치는 `General` 탭이 존재한다는 전제를 F-09 와 공유한다.
> **관련 명세**: 자동 업데이트(네트워크를 쓰는 나머지 한 가지 용도)는 `F-13`, 앱 상태 머신·메뉴바 표시(체험/라이선스 상태를 어떻게 노출할지의 UI 층위)는 `F-10`, 환경설정 창 전체 레이아웃은 `F-09` 를 참조한다. F-12 는 이 세 명세에 "라이선스 상태" 라는 값만 제공하고, 그 값이 메뉴바나 환경설정 창에 어떻게 그려지는지는 다루지 않는다.

## 1. 개요

Superkey 는 20일 무료 체험 후 유료 전환하는 모델이며(`superkey-inventory.md` §1.5: "Free for 20 days, purchase for ..."), 라이선스 1개는 **동시에 3대**까지 활성화할 수 있다("One license can be active on 3 devices at a time"). 결제와 Merchant of Record 는 Paddle 이 맡고("The order process is conducted by an online reseller, Paddle.com, the Merchant of Record for all our orders."), 사이트에 임베드된 `https://cdn.paddle.com/paddle/paddle.js` 로 보아 **Paddle Classic** 계열 SDK 다. 환불은 구매 후 14일이며 이메일로 접수한다("a refund can be issued within 14 days of purchase. Send an email to superkey@ryanhanson.dev.").

F-12 는 이 상업적 제약들을 **기술 명세**로 옮기는 문서다. 다루는 것은 (1) 체험 기간의 경과를 어떻게 판정하고 어디에 저장하는가, (2) 키 활성화·비활성화·재검증이 앱 내부에서 어떤 요청/응답 계약을 갖는가, (3) 오프라인일 때 무엇을 신뢰하는가, (4) 검증 요청이 서버에 무엇을 보내는가(개인정보 경계), (5) 이 모든 것을 클론 프로젝트에서 실제로 Paddle 로 구현할지 아니면 껍데기만 만들어 둘지에 대한 제품 결정이다.

**금액에 의존하지 않는다.** 정적 HTML 에는 가격 문자열이 없고 Paddle JS 가 런타임에 주입한다(`superkey-inventory.md` §4.4, Q14). 제3자 집계의 `$15.99` 는 `[3차]` 출처이므로 본 명세의 어떤 동작도 특정 금액을 전제하지 않는다.

**라이선스 키 포맷, 활성화/비활성화 API 의 실제 사양, 오프라인 유예 정책의 실제 값, 체험 기산점과 만료 후 동작의 실제 사양**은 모두 조사에서 확정되지 않았다(Q11, Q12). 이 문서는 그 공백을 **추상 인터페이스 + 합리적 기본값 + `(추정)` 표기**로 메우고, 실제 사양이 아닌 것을 사실인 것처럼 쓰지 않는다.

## 2. 사용자 시나리오

### 시나리오 A — 신규 설치, 체험 시작과 경과

1. 사용자가 앱을 처음 실행한다. 저장된 체험 기산점이 없다.
2. 앱은 이 시점을 체험 시작 시각으로 기록하고(§3.6), 상태를 **체험 중**으로 전이한다.
3. 이후 19일 동안 사용자는 아무 제약 없이 모든 기능을 쓴다. 환경설정 `General` 탭에는 "체험판 — N일 남음" 류의 상태 표시가 있다 `(추정, §4)`.
4. 20일째가 지나면 다음 실행 시 앱은 상태를 **체험 만료**로 전이한다. §3.2 에서 정의하는 만료 후 동작이 적용된다.

### 시나리오 B — 라이선스 구매와 활성화

1. 체험 중이거나 만료된 사용자가 환경설정의 라이선스 키 입력란에 구매한 키를 붙여넣고 "활성화"를 누른다.
2. 앱은 §3.3 의 활성화 요청을 서버(또는 F-12 §7 의 결정에 따라 로컬 스텁)로 보낸다.
3. 요청이 성공하면 이 기기가 활성화 슬롯 하나를 점유하고, 앱은 응답을 로컬 캐시에 저장한 뒤 상태를 **라이선스 활성**으로 전이한다.
4. 이후 재실행 시에는 캐시가 유효한 동안 네트워크 없이도 **라이선스 활성** 상태를 유지한다(§3.5 오프라인 유예).

### 시나리오 C — 기기 교체로 인한 슬롯 소진과 비활성화

1. 사용자가 이미 3대에서 같은 라이선스를 활성화해 두었다.
2. 오래된 맥북을 처분하기 전에 그 기기에서 앱을 열어 "이 기기 비활성화"를 누른다(§4). 앱은 §3.4 의 비활성화 요청을 보내고, 성공하면 슬롯 하나를 반납한다.
3. 새 기기에서 같은 키를 입력해 활성화하면 반납된 슬롯을 점유해 정상적으로 활성화된다.
4. 만약 2단계를 건너뛰고 기기를 처분했다면(비활성화를 못 한 경우), 4번째 기기에서의 활성화는 §3.2 "슬롯 초과" 실패로 거부된다 — `superkey-inventory.md` §4.3 이 실제로 보고하는 "used up activations" 문제가 이것이다. Superkey 원본은 이 상황을 앱 내 비활성화가 아니라 **새 라이선스 재발급**(Hyperkey 마이그레이션 경로)으로 우회했던 것으로 보이며, F-12 는 이를 재현하지 않고 **앱 내 비활성화 경로를 1급 기능으로 설계**해 근본 원인을 해소한다(§7, §4).

### 시나리오 D — 환불

1. 사용자가 구매 후 10일째에 `superkey@ryanhanson.dev` 상당의 지원 채널로 환불을 요청하고 처리된다(14일 이내이므로 조건 충족).
2. 다음 검증 요청(§3.3.3) 또는 다음 오프라인 유예 만료 시점에 서버가 이 라이선스 키를 무효로 응답한다.
3. 앱은 상태를 **라이선스 무효/취소**로 전이한다. 체험은 이미 소진되어 있으므로(20일 체험은 최초 1회) **체험 중으로 되돌아가지 않고 체험 만료와 동일한 제약 상태**로 귀결된다(§3.2).

## 3. 동작 명세

### 3.1 원칙

- 체험과 라이선스는 **동일한 하나의 상태 값**으로 표현되는 상태 머신이다(§3.2). 두 개의 독립된 불리언(`is_trial`, `is_licensed`)으로 쪼개면 "체험도 만료됐고 라이선스도 무효"인 상태와 "체험 중"인 상태를 구분하는 로직이 상태 머신 밖으로 새어 나간다.
- 체험은 **기기(설치)당 1회**다. 라이선스가 무효화되거나 취소돼도 체험으로 되돌아가지 않는다(시나리오 D). 이 규칙은 조사에서 직접 확인되지 않았으나, 그렇지 않으면 "구매 → 환불 → 재설치 없이 체험 재획득"이 가능해져 20일 체험이라는 제약 자체가 무의미해지므로 합리적 기본값으로 채택한다 `(추정)`.
- 네트워크는 **라이선스 검증 갱신과 자동 업데이트(F-13) 두 가지 용도로만** 쓴다(`superkey-inventory.md` §1.3: "only reaches out to the network for license validation or updates as configured"). F-12 가 만드는 어떤 요청도 이 두 용도를 벗어나지 않는다 — 예를 들어 체험 시작을 서버에 알리는 "설치 텔레메트리" 성격의 호출은 만들지 않는다(§3.6, §7 에서 근거를 자세히 다룬다).
- 모든 시각 판정은 로컬 시계에 의존할 수밖에 없다는 전제 위에서, **명백한 시계 조작만** 완화 대상으로 삼는다(§3.6, §5 "시계 되돌림"). 완벽한 방지는 목표가 아니다.

### 3.2 라이선스 상태 머신

| 상태 | 진입 조건 | 앱 동작 |
| :--- | :--- | :--- |
| **미개시** | 로컬에 체험 기산점도, 라이선스 캐시도 없음(최초 실행 직후, 상태 판정 로직이 아직 한 번도 안 돈 순간) | 즉시(같은 실행 내에서) 체험 기산점을 기록하고 **체험 중**으로 전이한다. 사용자에게 노출되는 지속 상태가 아니라 내부 경유 상태다. |
| **체험 중** | `현재 시각 − 체험 기산점 < 20일` 이고 유효한 라이선스 캐시가 없음 | 모든 기능 정상 동작. `General` 탭에 남은 일수 표시 `(추정, §4)`. |
| **체험 만료** | `현재 시각 − 체험 기산점 ≥ 20일` 이고 유효한 라이선스가 없음, 또는 라이선스가 **라이선스 무효/취소**에서 전이해 옴 | 만료 후 정확한 동작(전면 차단 vs 기능 제한)은 조사로 확정되지 않았다(Q12). §5 "체험 만료 후 동작" 에서 합리적 기본값을 정하고 `(추정)` 로 남긴다. |
| **라이선스 활성** | 활성화 요청(§3.3.1) 성공, 또는 재실행 시 로컬 캐시가 유효(§3.5) | 모든 기능 정상 동작. 체험 상태와 무관하게 최우선으로 적용된다. |
| **라이선스 무효/취소** | 검증 요청(§3.3.3)이 명시적으로 무효(환불됨·해지됨·키 오류)를 응답, 또는 오프라인 유예가 만료됐는데도 재검증에 계속 실패 | 사용자에게 사유를 노출한 뒤(§5), 다음 판정 사이클에서 **체험 만료**로 전이한다(§3.1 "체험은 되돌아가지 않는다"). |

전이는 앱 실행 시점과 §3.3.3 의 주기적 재검증 시점 두 군데에서만 평가한다. 실행 도중 자정을 넘기는 것과 같은 실시간 카운트다운은 요구되지 않는다 `(추정)` — 체험 배너의 "남은 일수"가 실시간으로 줄어들 필요는 없고, 다음 실행 시 다시 계산되면 충분하다.

### 3.3 활성화 / 비활성화 / 검증 — 추상 인터페이스

Paddle Classic 의 실제 라이선스 API 사양은 조사로 확인되지 않았다(`rust-macos-capability-notes.md` §4 P5: "Paddle Classic 의 라이선스 검증 엔드포인트 사양 — 공개 문서가 Paddle Billing 위주로 이동함"). 따라서 아래는 **앱 내부의 추상 인터페이스**로 정의하고, Paddle 로의 매핑은 별도로 `(추정)` 표시한다. 이 분리 덕분에 §7 의 결정(Paddle 을 지금 붙이지 않는다)과 무관하게 상태 머신·UI 는 이 인터페이스에만 의존해 구현할 수 있다.

#### 3.3.1 활성화 요청

| 필드 | 방향 | 설명 |
| :--- | :--- | :--- |
| `license_key` | 요청 | 사용자가 입력한 키 문자열. 포맷 미확인(Q11) — 임의의 불투명 문자열로 취급한다. |
| `device_id` | 요청 | 이 기기의 식별자(§3.7, §6). |
| `device_label` | 요청, 선택 | 슬롯 목록에서 사람이 알아볼 수 있게 하는 이름(예: "MacBook Pro"). 없어도 활성화는 가능해야 한다 — 최소 식별자 원칙(§3.7). |
| `app_version` | 요청 | 호환성 판단·지원 문의용. |
| `status` | 응답 | `activated` \| `invalid_key` \| `refunded` \| `limit_reached` \| `network_error`(클라이언트 로컬 판정) |
| `activations_used` / `activations_limit` | 응답 | 슬롯 현황. `limit_reached` 사유 표시에 쓴다(§5). |
| `cache_token` | 응답 | 오프라인 재실행 시 재검증 없이 신뢰할 서명된 캐시 값(§3.5). |
| `cache_issued_at` | 응답 | 캐시 발급 시각. 오프라인 유예 계산의 기준점. |

**Paddle 매핑 `(추정)`**: Paddle Classic 계열의 라이선스 API 는 통상 `product_id` + `license_code`(≈ `license_key`) + 클라이언트가 생성한 기기 문자열 조합으로 activate/validate/deactivate 세 엔드포인트를 제공하고, 응답에 활성화된 기기 수를 포함하는 패턴이 알려져 있다. 그러나 Superkey 가 실제로 이 패턴을 쓰는지, 필드명이 무엇인지는 이번 조사로 확인하지 못했다 — 위 표의 필드명은 SuperKey/Paddle 의 실제 필드명이 아니라 **F-12 가 정의하는 자체 계약**이다.

#### 3.3.2 비활성화 요청

| 필드 | 방향 | 설명 |
| :--- | :--- | :--- |
| `license_key` | 요청 | 대상 라이선스. |
| `device_id` | 요청 | 해제할 기기(보통 "이 기기" 자기 자신, §4). |
| `status` | 응답 | `deactivated` \| `not_found`(이미 해제됨) \| `network_error` |
| `activations_used` | 응답 | 갱신된 슬롯 사용량. UI 에 즉시 반영한다. |

비활성화는 시나리오 C 가 보여주듯 **3대 한도 때문에 반드시 필요**하다(`superkey-inventory.md` §4.3). 서버가 다운돼 있으면 로컬에서 "비활성화됨"으로 낙관적으로 처리하지 않는다 — 슬롯 반납은 서버가 확정해야 진실이다(§5 "서버 다운 중 비활성화 시도").

#### 3.3.3 검증(재검증) 요청

| 필드 | 방향 | 설명 |
| :--- | :--- | :--- |
| `license_key` | 요청 | — |
| `device_id` | 요청 | — |
| `cache_token`(있으면) | 요청 | 서버가 이전 발급 토큰을 무효화했는지 대조할 수 있게 함. |
| `status` | 응답 | `valid` \| `invalid_key` \| `refunded` \| `revoked` \| `network_error` |
| `cache_token` / `cache_issued_at` | 응답 | 갱신된 캐시(§3.5). |

재검증은 앱 실행 시 1회, 그리고 §3.5 의 오프라인 유예 창이 임박했을 때 백그라운드로 시도한다 `(추정)` — 정확한 주기는 조사로 확인되지 않았다(Q11, 자동 업데이트의 확인 주기와 유사하게 Q13 도 미확인이다).

### 3.4 오프라인 유예 규칙

라이선스 활성 상태에서 네트워크가 없어도 즉시 미인증으로 떨어지면 안 된다 — 비행기 안이나 방화벽 뒤에서 매번 라이선스가 풀리는 유틸리티는 쓸 수 없다. 그러나 정확한 유예 일수는 조사로 확정되지 않았다(Q11). F-12 는 다음을 **합리적 기본값**으로 제안한다:

- `cache_issued_at` 로부터 **N일**(구체 값 미정, 예시로 서술하되 확정하지 않음) 동안은 네트워크 없이도 **라이선스 활성**을 유지한다.
- 그 창을 넘기면 다음 실행 시 재검증을 **시도**하되, 재검증 자체가 네트워크 부재로 실패한 경우(서버 응답이 아니라 연결 자체의 실패)에는 즉시 **라이선스 무효/취소**로 떨어뜨리지 않고, 짧은 추가 유예(예: 최근 성공한 캐시로 계속 동작하되 UI 에 "재인증 필요" 경고를 표시) 후 반복 실패 시 전이한다 `(추정)`.
- 서버가 명시적으로 `refunded`/`revoked`/`invalid_key` 를 응답한 경우는 유예 대상이 아니다 — 네트워크가 되는 순간 즉시 전이한다. 유예는 "확인할 수 없음"을 봐주는 것이지 "무효로 확인됨"을 봐주는 것이 아니다.

이 절 전체가 `(추정)` 이며, 실제 값·정책은 §9 로 승계한다.

### 3.5 트라이얼 기산점 저장 — 위치와 변조 저항

원본의 "Superkey does not do anything further with any of the information it processes... None of the data that Superkey processes is stored on your disk"(`superkey-inventory.md` §1.3)는 **Seek 가 화면에서 읽어낸 텍스트·좌표 같은 처리 데이터**에 대한 약속이지, 앱의 환경설정이나 라이선스 상태에 대한 약속이 아니다. 실제로 프리셋 설정 같은 구성 값은 어딘가에 영속되어야 하고(F-09 소관), 체험 기산점과 라이선스 캐시도 마찬가지다. **F-12 는 이 약속의 명시적 예외**이며, 저장하는 값은 타임스탬프 1개 + 라이선스 캐시 몇 필드로 최소화한다.

**결정: 로컬 파일이 아니라 macOS Keychain(`Security.framework`)에 저장한다.**

| 후보 | 변조 난이도 | 비고 |
| :--- | :--- | :--- |
| 일반 파일(plist/JSON, `~/Library/Application Support/...`) | 낮음 | Finder 나 `rm` 한 줄로 삭제 가능. 앱 삭제·재설치로 자동 초기화됨 — 트라이얼을 무한 반복 가능. §5 "체험 상태 파일 삭제" 가 바로 이 취약점이다. |
| **Keychain(선택)** | 중간 | `~/Library/Application Support` 삭제나 앱 재설치만으로는 지워지지 않는다(Keychain 항목은 앱 번들과 독립적으로 살아남는다). `security delete-generic-password` 나 Keychain Access.app 조작에는 여전히 뚫린다 — 완벽한 방어는 아니다. |
| 서버에 기산점을 앵커(설치 시 서버에 "체험 시작"을 통지) | 높음 | 가장 강하지만 **최초 실행부터 네트워크를 요구**하게 되고, 이는 §3.1 의 "네트워크는 검증·업데이트 두 용도뿐" 경계와 "no telemetry or tracking" 약속(`superkey-inventory.md` §1.3, §4.1: "No user data is gathered by Superkey")을 사실상 어기는 결과가 된다. 기각한다. |

**Keychain 을 채택하는 근거**: (1) 파일 삭제·재설치라는 가장 흔한 리셋 시도를 막아 "합리적 수준"을 넘는다. (2) 같은 저장소에 §3.3 의 `cache_token` 도 함께 둘 수 있어 저장 메커니즘이 하나로 통일된다. (3) `kSecAttrSynchronizable`(iCloud Keychain 동기화)을 **명시적으로 끈다** `(추정)` — 동기화를 켜면 한 계정에 로그인한 여러 기기가 같은 체험 기산점을 공유해 "3대 동시 활성"이라는 라이선스 모델과 저장 모델이 어긋난다. (4) 완벽하지 않다는 것을 인정한다 — 새 macOS 사용자 계정을 만들거나, 클린 설치를 하거나, `security` CLI 로 항목을 지우면 체험은 초기화된다. 이 앱의 제작자 본인이 텔레메트리 없는 최소주의를 표방하므로(`superkey-inventory.md` §4.1), 서버 앵커나 하드웨어 지문 같은 공격적인 안티 파훼 기법은 제품 철학과도 맞지 않는다.

**시계 조작 완화**: 기산점 하나만 저장하면 시스템 시계를 과거로 되돌려 "아직 20일이 안 지났다"고 속일 수 있다. Keychain 항목에 기산점과 별도로 **최근 관찰 시각**(`last_seen_at`)을 함께 저장하고, 매 실행마다 `현재 시각 < last_seen_at` 이면 시계 되돌림으로 간주해 남은 일수를 보수적으로(가장 최근에 계산된 값 유지, 더 늘어나지 않게) 고정한다 `(추정)`. 이 역시 완벽한 방어는 아니며 — 부팅 전 시계를 조작하거나 네트워크 시간 동기화를 끄는 사용자는 여전히 우회할 수 있다 — §5 에서 실패 모드로 별도 다룬다.

### 3.6 기기 식별자

`device_id` 로 **하드웨어 UUID(`IOPlatformUUID`, IOKit)를 채택**하고, 앱이 생성하는 랜덤 ID는 채택하지 않는다.

- **근거**: `superkey-inventory.md` §4.3 의 "You get a new license instead of reusing your old one, which takes care of any used up activations you might have for old devices"는 **하드웨어를 교체하면 이전 활성화가 소모된 채로 남는다**는 관찰된 실제 동작이다. 이는 기기 식별자가 하드웨어에 묶여 있어야만 나오는 증상이다 — 앱이 생성해 Keychain 에 저장하는 랜덤 ID는 macOS 마이그레이션 어시스턴트가 Keychain 을 통째로 새 기기에 옮길 경우 **같은 ID 가 계속 살아남아** 하드웨어 교체가 새 슬롯 소모로 이어지지 않는다. 즉 랜덤 ID 는 원본에서 관찰된 동작과 어긋난다.
- `IOPlatformUUID` 는 시리얼 번호나 MAC 주소 같은 더 민감한 식별자가 아니라 **불투명한 UUID 하나**라는 점에서, "no telemetry or tracking" 약속과 최소 식별자 원칙(§3.7)에 부합한다.
- **기각한 대안 — 앱 생성 랜덤 ID(Keychain 저장)**: 위 이유로 마이그레이션에 의해 사실상 영구적인 ID 가 되어 "3대 한도"를 무력화할 소지가 있다. 다만 이 ID 는 온전히 로컬 생성이라 하드웨어 정보를 서버에 전혀 보내지 않는다는 장점은 있었다 — 프라이버시만 보면 더 낫지만, 라이선스 모델의 정합성(하드웨어 교체 = 새 기기)을 깨므로 채택하지 않는다.

### 3.7 개인정보 경계와 최소 식별자 원칙

원본은 "No user data is gathered by Superkey"(`superkey-inventory.md` §4.1)와 "none of my apps use any kind of telemetry or tracking"(§1.3)를 명시적으로 약속한다. F-12 는 라이선스 검증이라는, 원본 스스로 인정하는 유일한 예외적 네트워크 용도 안에서도 이 약속을 최대한 지킨다.

- **검증·활성화·비활성화 요청에 실리는 필드는 §3.3 표에 나열된 것이 전부다** — `license_key`, `device_id`(하드웨어 UUID), `device_label`(선택, 사용자가 직접 붙이는 이름일 뿐 시스템이 수집하는 정보 아님), `app_version`, 그리고 캐시 갱신에 필요한 토큰류. 사용자 이름, 이메일, macOS 사용자 계정 정보, 사용 통계, 다른 기기 목록의 상세 정보는 어떤 요청에도 포함하지 않는다.
- **이메일 주소는 F-12 의 소관이 아니다.** Paddle 체크아웃이 결제 목적으로 이메일을 수집한다면(§7 결정에 따라 실제 연동 시) 그것은 Paddle 의 결제 흐름이지, F-12 가 만드는 라이선스 검증 요청의 일부가 아니다 — 검증 요청에 이메일을 실어 보내지 않는다.
- **`device_id` 는 하드웨어 UUID 하나로 충분하다**(§3.6). MAC 주소, 시리얼 번호, 사용자 계정명처럼 더 식별력이 강하거나 여러 목적에 재사용 가능한 값은 쓰지 않는다 — 라이선스 슬롯을 구분하는 데 필요한 최소한의 불투명 식별자만 보낸다.
- 이 원칙은 §3.3 의 요청/응답 표 자체를 필드 수준에서 최소화하는 설계 근거이며, §8 수용 기준의 마지막 항목("§3.7 최소 식별자 원칙")으로 검증한다.

## 5. 엣지 케이스와 실패 모드

1. **오프라인 최초 활성화.** 인터넷이 없는 상태에서 처음으로 키를 입력하고 "활성화"를 누르면, §3.3.1 요청 자체가 실패(`network_error`)한다. 활성화되지 않은 것으로 명확히 표시하고, 키 입력값은 보존해 네트워크가 돌아오면 재시도 버튼 한 번으로 다시 시도할 수 있게 한다 `(추정)` — 오프라인 유예(§3.4)는 "이미 성공적으로 캐시된 활성화"에만 적용되고 최초 활성화에는 적용되지 않는다.
2. **유예 만료.** §3.4 의 유예 창을 넘긴 채 계속 오프라인이면, 짧은 추가 유예 후에도 재검증에 실패하면 **라이선스 무효/취소**로 전이하고 곧 **체험 만료**와 동일한 제약이 걸린다. 사용자에게는 "네트워크에 연결해 라이선스를 재확인하세요" 류의 메시지를 보여준다.
3. **슬롯 3/3 소진.** 4번째 기기에서 활성화를 시도하면 서버가 `limit_reached` 를 응답한다(§3.3.1). UI 는 단순 실패가 아니라 "이 라이선스는 이미 3대에서 사용 중입니다 — 다른 기기에서 비활성화해 주세요"처럼 원인과 해법(§4 의 비활성화 버튼)을 함께 안내한다.
4. **환불된 키.** §3.3.3 검증이 `refunded` 를 응답하면 유예 없이 즉시 **라이선스 무효/취소**로 전이한다(§3.4). 이미 로컬 캐시가 남아 있어도 서버의 명시적 무효 응답이 우선한다.
5. **시계 되돌림.** §3.6 의 `last_seen_at` 이상 탐지로 남은 일수를 더 늘리지 않는다. 다만 사용자가 부팅 전 하드웨어 시계를 조작하거나 시간 동기화를 꺼둔 채 최초 실행부터 과거 시각을 쓰면 탐지되지 않는다 `(추정)` — 완벽한 방어가 목표가 아님을 §3.6 에서 명시했다.
6. **동일 기기 재설치(앱 삭제 후 재설치).** `device_id` 가 하드웨어 UUID 이므로(§3.6) 동일 기기라면 재설치해도 같은 `device_id` 로 다시 검증되어 기존 활성화 슬롯을 그대로 재사용한다 — 새 슬롯을 소모하지 않는다. 체험 기산점도 Keychain 에 남아 있다면(§3.5) 재설치가 체험을 리셋하지 않는다.
7. **하드웨어 교체로 기기 ID 변경.** 사용자가 새 맥으로 데이터를 옮기되(예: Migration Assistant), 이전 기기에서 비활성화(§3.3.2, §4)를 하지 않은 경우 새 기기의 `IOPlatformUUID` 는 이전 기기와 다르므로 **새 슬롯**으로 취급된다. 이것이 `superkey-inventory.md` §4.3 이 보고하는 "used up activations" 문제 그 자체이며, F-12 는 이를 앱 내 비활성화 버튼(§4)으로 완화한다 — 다만 처분 전에 비활성화를 잊으면 슬롯은 여전히 소모된 채로 남는다(§3 시나리오 C 4단계).
8. **서버 다운.** 활성화·비활성화·검증 요청 모두 시간 초과 또는 5xx 로 실패할 수 있다. 활성화·비활성화는 서버의 확정 응답 없이 낙관적으로 상태를 바꾸지 않는다(§3.3.2). 검증은 §3.4 오프라인 유예 규칙을 그대로 따른다 — 서버 다운과 사용자의 네트워크 단절은 클라이언트 입장에서 구분할 수 없으므로 동일하게 처리한다.
9. **응답 위조.** 로컬 캐시(`cache_token`)나 검증 응답이 프록시·로컬 조작으로 위조될 가능성에 대해, 조사 자료는 서명 방식을 확인해 주지 않는다(Q11). F-13(자동 업데이트)이 EdDSA 서명 appcast 를 쓴다는 사실(`superkey-inventory.md` §2.3)에 비추어, 라이선스 응답에도 유사하게 **서버 측 서명 + 클라이언트 측 공개키 검증**을 캐시 토큰에 적용하는 것을 권고 설계로 제안하나, Paddle Classic 이 실제로 이런 서명을 제공하는지는 확인되지 않았다 `(추정)` → §9.
10. **체험 상태 파일 삭제.** §3.5 의 결정(Keychain 채택)에 따라, `~/Library/Application Support` 삭제나 앱 재설치는 체험을 리셋하지 못한다. 다만 Keychain 항목 자체를 `security delete-generic-password` 로 지우거나 macOS 를 클린 설치하면 리셋된다 — 이는 받아들이는 잔여 위험이다(§3.5).
11. **마이그레이션 쿠폰.** 구 Hyperkey 구매자가 이메일 주소를 쿠폰 코드로 사용해 100% 할인 구매를 완료하는 경로다(`superkey-inventory.md` §4.3). 이 흐름은 §3.3 의 활성화 계약 바깥에서 일어나는 **결제 단계의 쿠폰 적용**(Paddle 체크아웃의 몫)이며, 발급된 결과는 통상적인 새 `license_key` 로 이어져 이후에는 §3.3 의 일반 활성화 흐름과 동일하게 처리된다. 키가 "사전 발급 풀에서 꺼내지는" 방식이라는 것은 개발자 발언("I'm not generating new license keys on the fly")에서 나온 추정이며(§4.3), 클론 프로젝트가 이 쿠폰 메커니즘 자체를 구현할지는 §7 의 결정에 종속된다.

## 6. 필요한 플랫폼 API

- **HTTPS 클라이언트** — §3.3 의 세 요청을 보내는 데 필요. `rust-macos-capability-notes.md` 에는 HTTP 클라이언트 크레이트가 조사되어 있지 않다. 일반적으로 Rust 생태계에서 이 역할은 `reqwest` 가 맡지만, 이 크레이트는 조사 노트에 없으므로 이름만 표기하고 버전은 지어내지 않는다 `(추정, 조사 노트에 없음)`.
- **Keychain — `Security.framework`** — §3.5 의 트라이얼 기산점·`last_seen_at`·라이선스 캐시 저장. `rust-macos-capability-notes.md` 에는 Keychain 전용 크레이트가 조사되어 있지 않다. §2.5 가 `IOHIDCheckAccess`/`IOHIDRequestAccess` 에 대해 보여준 것과 같은 패턴("전용 크레이트가 없어 프레임워크를 직접 링크")을 따라, `Security.framework` 를 직접 링크(`#[link(name="Security", kind="framework")]`)하고 `SecItemAdd`/`SecItemCopyMatching`/`SecItemUpdate`/`SecItemDelete` 를 `extern "C"` 로 손수 선언하는 것을 기본 경로로 제안한다. 커뮤니티에 `security-framework` 라는 이름의 크레이트가 존재한다고 알려져 있으나 이 역시 조사 노트에는 없으므로 이름만 표기한다 `(추정, 조사 노트에 없음, 버전 미기재)`.
- **기기 식별자 취득 — `IOPlatformUUID`(IOKit)** — §3.6. `rust-macos-capability-notes.md` 에 전용 크레이트가 없다. §2.5 와 동일한 패턴으로 `IOKit.framework` 를 직접 링크하고 `IOServiceGetMatchingService`/`IORegistryEntryCreateCFProperty` 를 `extern "C"` 로 선언해 `kIOPlatformUUIDKey` 값을 읽는다 `(추정)`.
- 참고로 `objc2-foundation`/`objc2-core-foundation`(둘 다 조사 노트 §1.1 에서 버전 확인됨: 0.3.2)는 `CFString`/`NSDate` 등 위 FFI 호출의 타입 변환에 보조적으로 쓰일 수 있으나 F-12 의 핵심 API 는 아니다.

## 7. 구현 접근

**판정: Rust 바인딩.** 단, 다른 기능 명세들과 비중이 다르다는 점을 명시한다.

F-01(Seek 활성화)이나 F-03(오버레이) 같은 명세는 로직의 상당 부분이 `CGEventTap`·`NSWindow`·`AXUIElement` 같은 플랫폼 타입과 직접 맞닿아 있다. F-12 는 반대다 — **상태 머신(§3.2), 요청/응답 계약(§3.3), 오프라인 유예 판정(§3.4), 시계 조작 완화 로직(§3.5)은 전부 순수 애플리케이션 로직**이며 어떤 macOS 프레임워크 타입에도 의존하지 않는다. HTTPS 클라이언트도 `reqwest` 류를 쓰면 크로스플랫폼 크레이트이지 macOS 전용 바인딩이 아니다. 이 부분만 보면 F-12 는 "순수 Rust" 판정에 가깝다.

그러나 F-12 전체를 "순수 Rust" 로 판정하지 않는 이유는 좁지만 피할 수 없는 두 지점 때문이다: (1) §3.5 의 트라이얼 기산점·라이선스 캐시를 **Keychain 에 저장**하는 것, (2) §3.6 의 **하드웨어 UUID 취득**. 둘 다 §6 에서 정리했듯 조사 노트에 전용 크레이트가 없어 `Security.framework`/`IOKit.framework` 를 직접 링크하고 `extern "C"` 선언을 손으로 쓰는 `unsafe` FFI 가 필요하다. 이 두 지점이 존재하는 한 F-12 는 "Rust 바인딩" 으로 판정한다 — 다만 이 FFI 표면은 함수 4~5개 수준으로 F-01/F-03 이 다루는 표면보다 훨씬 작고, **네이티브 Swift/Objective-C shim 은 이 두 지점 어디에도 필요 없다**(Keychain·IOKit 모두 C ABI 로 직접 호출 가능).

- **기각한 대안 1 — "순수 Rust" 로 판정.** Keychain·IOKit 접근이 소량이라고 해서 무시하면, §6 의 FFI 필요성이 문서에서 실종된다. 다른 명세들과의 판정 기준 일관성을 위해 macOS 프레임워크에 대한 직접 호출이 하나라도 있으면 "Rust 바인딩" 으로 분류한다.
- **기각한 대안 2 — "네이티브 shim 불가피".** F-03 이 `ns_window()` 로도 커버되지 않는 window level·collection behavior 때문에 이 판정을 받은 것과 달리, F-12 가 다루는 Keychain·IOKit 호출은 C ABI 함수 호출일 뿐 AppKit 객체 그래프에 개입할 필요가 없다. Swift/Objective-C 소스 파일이나 Xcode 프로젝트 없이 순수 Rust 바이너리 안에서 전부 해결된다.
- **비중에 대한 메모**: F-12 의 코드량 기준으로는 네트워크·상태 머신·JSON 직렬화 같은 순수 로직이 압도적 다수를 차지하고, 플랫폼 바인딩은 "저장소 어댑터" 한 모듈에 국한된다. 이는 F-01/F-02/F-03/F-04 처럼 기능의 본질 자체가 플랫폼 API 호출인 경우와 대조적이다 — F-12 에서 플랫폼 바인딩은 로직을 감싸는 얇은 영속성 계층일 뿐이다.

### ⭐ 클론 프로젝트의 결정 — Paddle 을 지금 실제로 붙일 것인가

**결정: 붙이지 않는다.** 라이선스 계층을 §3.3 의 추상 인터페이스(`LicenseProvider`) 뒤에 두고, 초기 구현은 모든 기기를 항상 라이선스 활성으로 취급하는 **무동작(no-op) 구현체**를 기본으로 채택한다. 상태 머신·오프라인 유예·비활성화 UI(§3, §4)는 이 인터페이스를 향해 지금 그대로 구현한다 — 나중에 실제 Paddle 연동을 끼워 넣을 때 상태 머신이나 UI 를 다시 설계할 필요가 없도록.

**근거**:
1. Paddle Classic 라이선스 API 의 실제 필드·엔드포인트가 조사로 확인되지 않았다(Q11, `rust-macos-capability-notes.md` §4 P5). 확인되지 않은 사양에 맞춰 네트워크 코드를 지금 작성하면 나중에 실제 사양과 어긋날 경우 통째로 재작성해야 한다.
2. Paddle 연동은 판매자 계정·세금 설정·가격 책정이라는 **제품/사업 결정**을 전제하는데, 이는 클론 프로젝트의 "기능 동등성 구현"이라는 목표와 독립적인 별개 트랙이다. 가격조차 확정되지 않은 상태(§4.4)에서 결제 연동을 먼저 완성하는 것은 순서가 맞지 않는다.
3. 추상 인터페이스로 분리해 두면 상태 머신·UI·비활성화 흐름 같은 **F-12 의 나머지 전부**를 지금 검증할 수 있다 — 라이선싱을 통째로 미루는 것보다 훨씬 많은 가치를 지금 확보한다.

**기각한 대안**:
- **대안 1 — 지금 Paddle Classic 을 실제로 연동한다.** 위 근거 1, 2로 기각. 미확인 사양 위에 짓는 것은 재작업 위험이 크고, 판매자 계정이라는 클론 프로젝트 범위 밖의 전제가 필요하다.
- **대안 2 — 다른 결제 백엔드(Stripe, Gumroad 등)로 대체한다.** 기각 — 원본과의 기능 동등성이라는 클론의 목적에서 벗어나고, API 사양 미확인 문제를 다른 벤더로 옮길 뿐 해결하지 못한다.
- **대안 3 — 라이선싱 자체를 아예 구현하지 않는다(게이팅 없음).** 기각 — F-10(앱 상태 머신)이나 F-09(환경설정)가 참조할 "라이선스 상태" 값 자체가 없어지면 그 명세들에서 이 기능을 다시 설계해야 한다. 상태 머신과 UI 는 실제 결제 연동과 독립적으로 지금 만들 수 있는 가치이므로, 없음보다 무동작 구현체가 낫다.

## 8. 수용 기준

- [ ] 체험 기산점이 없는 최초 실행 시, 같은 실행 내에서 기산점이 Keychain 에 기록되고 상태가 **체험 중**으로 전이한다.
- [ ] `현재 시각 − 체험 기산점` 이 20일을 넘긴 다음 실행에서, 유효한 라이선스가 없으면 상태가 **체험 만료**로 전이한다.
- [ ] 앱을 완전히 삭제(`~/Library/Application Support` 포함)하고 재설치해도, 동일 기기에서는 체험 기산점이 초기화되지 않는다(§3.5, §5-10).
- [ ] 유효한 키로 활성화에 성공하면 상태가 **라이선스 활성**으로 전이하고, 로컬 캐시(`cache_token`, `cache_issued_at`)가 저장된다.
- [ ] 오프라인 상태에서 재실행해도 `cache_issued_at` 로부터 정의된 유예 창 이내면 **라이선스 활성** 상태가 유지된다(§3.4).
- [ ] 이미 3대가 활성화된 라이선스로 4번째 기기에서 활성화를 시도하면 `limit_reached` 로 실패하고, UI 는 원인과 비활성화 경로를 함께 안내한다(§5-3).
- [ ] "이 기기 비활성화"가 성공하면 이 기기의 라이선스 상태가 **체험 만료**(또는 체험이 아직 남아 있었다면 **체험 중**)로 되돌아가고, 서버 측 슬롯 카운트가 감소한다(§3.3.2, §4).
- [ ] 검증 응답이 `refunded` 또는 `revoked` 를 반환하면, 로컬 캐시가 남아 있어도 유예 없이 즉시 **라이선스 무효/취소**로 전이한다(§5-4).
- [ ] 라이선스가 **라이선스 무효/취소**를 거쳐 **체험 만료**로 재전이할 때, **체험 중**으로는 절대 되돌아가지 않는다(§3.1).
- [ ] 시스템 시계를 과거로 되돌린 뒤 재실행해도, 표시되는 남은 체험 일수가 이전 실행보다 늘어나지 않는다(§3.5, §5-5).
- [ ] 검증 요청 하나의 페이로드에 라이선스 키, 기기 식별자(`IOPlatformUUID`), 앱 버전 외의 필드(사용자 이름·이메일·사용 통계 등)가 포함되지 않는다(§3.7 최소 식별자 원칙).
- [ ] 서버가 다운되어 있는 동안 비활성화를 시도하면, 로컬 상태가 낙관적으로 "비활성화됨"으로 바뀌지 않고 실패로 표시된다(§5-8).
