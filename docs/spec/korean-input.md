# F-16 · 한국어 입력 지원

> **한 줄 요약** — `Shift + Space`·한/영 키·한자 키·`₩` 키에 대한 한국어 macOS 사용자 관행 리매핑 4종(F-16.1~F-16.4)을 새 `Korean` 탭 하나로 제공한다. ⭐ **이 기능군은 SuperKey 원본에 없는, 클론 고유의 신설 기능이다** — 재현할 원본이 없으므로 이 문서의 근거 등급은 다른 명세와 성격이 다르다(§1). ⭐⭐ F-16.2·F-16.3 의 전제였던 한/영·한자 키의 virtual keycode 는 **해소되었다**(§3.2, `0x68`/`0x66`) — 다만 등급은 `(웹 조사 확정 + SDK 헤더 실측, 실기기 미검증)` 이다.
> **의존성** — `F-07`(key-remapping-engine.md)의 중재 엔진·정본 눌림 테이블·앱별 비활성화 게이트 위에서만 동작하며, 새 이벤트 탭이나 새 중재 기구를 만들지 않는다. `F-14`(localization-and-input-sources.md)의 `TISCopyCurrentKeyboardInputSource`/`LayoutSnapshot` 을 재사용하되, §3.3 이 지적하는 한 지점에서 F-14 의 확장을 요구한다. `F-10`(menu-bar-and-lifecycle.md)의 최전면 앱 추적 알림에 얹혀 자체 게이트를 세운다. `F-09`(preferences-ui.md)가 정의한 탭 구조·설정 종속 표현 3종 규약을 그대로 따른다.
> **관련 명세** — 중재 계층·정본 눌림 테이블·엔진 마커는 `F-07`. hyper/meh/bleh 합성과의 충돌은 `F-05`(hyperkey.md). caps lock 커널 매핑 패턴(`F18`)은 `docs/dev/architecture.md` §6.1 결정 D-1. F-08 프리셋과의 충돌 검토는 `F-08`(power-user-presets.md). 입력 소스 판정 API 는 `F-14`. 설정 저장 규약("부재 = 기본값")은 `F-15`(settings-store-and-integrity.md). 탭 구조·설정 종속 표현은 `F-09`(preferences-ui.md) §3.8·§4. 클론 고유 기능이라는 제품 결정의 선례는 `README.md` "착수 전 제품 결정" D4.

## 1. 개요

이 기능군은 **원본 SuperKey 에 없는, 클론 고유의 신설 기능**이다. 다음 4종의 리매핑을 하나의 `Korean` 탭으로 묶어 제공한다.

| ID | 기능 |
| :--- | :--- |
| **F-16.1** | `Shift + Space` → 입력 소스 변경 |
| **F-16.2** | 한/영 키(`lang1`) → 입력 소스 변경 |
| **F-16.3** | 한자 키(`lang2`) → 한자 변환 |
| **F-16.4** | `₩` → `` ` `` (한국어 입력기일 때만) |

**왜 원본에 없는 기능을 만드는가.** `README.md` "착수 전 제품 결정" D4 가 이미 한 번 "원본 추종이 아니라 클론 고유의 선택"을 내렸다 — SuperKey 는 영어 단일 UI 이지만 클론은 현지화(`ko`+`en`)를 채택했다. F-16 은 그 결정의 논리적 귀결이다: 한국어 UI 를 내놓기로 한 이상, 한국어 입력 환경에서 실제로 부딪히는 결함을 다루는 것이 제품 논리로서 일관된다.

⭐ **근거의 성격이 다르다는 것을 먼저 밝힌다.** `key-remapping-engine.md`·`power-user-presets.md` 등 다른 명세의 1차 근거는 SuperKey v1.66 자체의 **실측**(번들 심볼·문자열·AX 트리 관찰)이다. F-16 에는 관찰할 원본 바이너리가 존재하지 않는다. 이 문서의 1차 근거는 **한국어 macOS 사용자가 실제로 운용 중인 Karabiner-Elements 규칙 4종**(이슈 #20)이다. 따라서 이 문서에서 `(실측: …)` 표기가 등장하면, 그것은 "SuperKey 에서 관찰했다"가 아니라 **"우리 환경(브라우저 프로브·`ioreg`·직접 조작)에서 확인했다"**는 뜻이며, 다른 명세의 같은 표기와 혼동해서는 안 된다.

⛔ **범위 밖.** 사용자의 Karabiner 규칙 5종 중 "오른쪽 command → Hyper(`⌘⌃⌥`)"는 F-16 의 범위가 아니다 — Hyperkey(F-05)의 `Include shift in hyper key` 를 끈 hyper 조합이 정확히 그것이므로, **이미 되는 기능**이다. 안내 문구를 §7 에 별도로 둔다.

⭐ **이 명세의 최대 불확실성이었던 §3.2 는 해소되었다.** 한/영 키(`lang1`)·한자 키(`lang2`)가 `CGEventTap` 에 도착할 때의 virtual keycode 는 각각 `0x68`(`kVK_JIS_Kana`)·`0x66`(`kVK_JIS_Eisu`)이다 — 서로 독립된 근거 3건이 일치한다(§3.2). ⚠️ 다만 **한국어 106키 물리 키보드로 실제 눌러 본 것은 아니다**(§5 #1). §7 의 2단계 구분은 착수 조건이 해소되었다는 뜻으로 갱신되었다.

## 2. 사용자 시나리오

### 시나리오 A — `Shift + Space` 로 입력 소스를 바꾼다

전제: 사용자가 `Korean` 탭에서 `Shift + Space 로 입력 소스 변경`(F-16.1)을 켰다. macOS 시스템 설정의 "입력 소스 선택" 단축키는 기본값 `⌃Space` 그대로다.

1. 텍스트 편집기에 포커스가 있는 상태에서 사용자가 `Shift` 를 누른 채 `Space` 를 누른다.
2. Ultrakey 는 물리 `space` keyDown 을 가로채, `shift` 를 뗀 `control`+`space` 이벤트로 치환해 방출한다.
3. macOS 가 이를 "입력 소스 선택" 단축키로 인식해 입력 소스를 전환한다.
4. 사용자는 스페이스바 옆 shift 만으로 손을 떼지 않고 입력 소스를 바꿀 수 있다 — `⌃Space` 보다 손가락 이동이 짧다.

> ⭐ **이 시나리오는 다국어 Seek 세션(인풋 박스 모드) 중에도 성립한다 (이슈 #101)** — F-16.1 은 계층 3 규칙이라 세션 중 계층 1 short-circuit 으로 원래 발화하지 않지만, 인풋 박스 모드에서는 세션 게이트가 **SPACE 키에 한해 같은 규칙을 그 자리에서 재평가**해 `⇧+Space` → `⌃Space` 치환을 그대로 수행한다(자세한 규칙은 `seek-activation-and-session.md` §3.1 ③). 검색 바 `<input>` 에 스페이스가 들어가지 않고 입력 소스만 바뀐다. 영어 단일 세션에서는 이 예외가 없다 — ⇧+Space 는 검색어 공백(기존 동작).

### 시나리오 B — 106키 외장 키보드의 한/영 키를 쓴다

전제: 사용자가 한국어 106키 외장 키보드를 쓰며 `Korean` 탭에서 `한/영 키로 입력 소스 변경`(F-16.2)을 켰다.

1. 사용자가 한/영 키를 아무 modifier 없이 누른다.
2. macOS 는 이 물리 키를 `kVK_JIS_Kana`(`0x68`)로 전달한다 — 한국어 전용 상수가 없어 같은 물리 위치의 JIS 상수를 재사용하기 때문이다(§3.2).
3. Ultrakey 가 이를 `control`+`space` 로 치환해 방출하고, macOS 가 "입력 소스 선택" 단축키로 인식해 전환한다.
4. ⭐ **현재 입력 소스가 한국어든 영문이든 똑같이 동작한다** — 이 키에는 입력 소스 조건을 걸지 않는다(§3.1). 걸면 영문에서 한국어로 되돌아올 수 없는 편도 키가 된다.

> ⚠️ **이 시나리오는 실기기로 확인되지 않았다** — 검증 기기에 한국어 106키 물리 키보드가 없다(§5 #1). keycode 자체는 근거 3중으로 확정되었으나(§3.2), 실제 하드웨어가 그 keycode 를 보내는지는 미검증이다.

### 시나리오 C — `` ` `` 를 입력하고, 곧이어 창을 전환한다

전제: 사용자가 `₩ 키로 백틱(` `) 입력`(F-16.4)을 켰고, 현재 입력 소스가 한국어 입력기다.

1. 코드 편집기에서 사용자가 `` ` ``/`₩` 키를 아무 modifier 없이 누른다.
2. Ultrakey 가 같은 keycode 에 `option` 플래그를 얹어 재주입해 백틱이 입력된다(F-16.4 발화).
3. 이어서 사용자가 같은 앱의 다른 창으로 전환하려 `⌘`+`` ` ``를 누른다.
4. 이번에는 modifier(command)가 함께 눌려 있으므로 F-16.4 의 "modifier 부재" 조건이 성립하지 않아 **개입하지 않는다**. `⌘`+`` ` `` 는 원래 뜻대로 창 전환으로 전달된다.

### 시나리오 D — 원격 데스크톱 클라이언트가 최전면일 때

전제: F-16.1~F-16.4 가 모두 켜져 있고, `원격 데스크톱 클라이언트에서 한국어 키 처리 끄기`(§4.2 항목 5, 기본 ☑)도 켜져 있다. 사용자가 원격 데스크톱 클라이언트류 앱을 최전면에 두고 있다.

1. 사용자가 `Shift + Space` 를 누른다.
2. Ultrakey 는 이 앱이 §3.5 의 기본 제외 목록에 해당함을 게이트에서 확인하고, F-16 규칙 어느 것도 평가하지 않는다.
3. 원본 `shift`+`space` 이벤트가 그대로 원격 세션에 전달된다 — 대상 시스템 쪽 입력기가 이를 처리할 기회를 잃지 않는다.

### 시나리오 E — ⭐ Karabiner-Elements 를 켜 둔 채 F-16 을 켠다

전제: 사용자가 Karabiner-Elements 를 **계속 쓰고 있다** — 이것은 가정이 아니라 이 사용자의 실제 환경이다. 그 위에 Ultrakey 의 F-16 을 전부 켠다.

1. 사용자가 한/영 키를 누른다.
2. Karabiner 가 가상 HID 장치 층에서 이미 이 키를 `space`+`left control` 로 바꿔 내보낸다 — Ultrakey 의 탭에는 원래 `lang1` keycode 가 도착하지 않는다.
3. Ultrakey 의 F-16.2 규칙은 조건이 성립하지 않아 **발화하지 않는다**(무동작).
4. 최종 동작은 Karabiner 가 이미 내던 것과 동일해, 파괴적 충돌은 없다. 그러나 사용자 입장에서는 "Ultrakey 의 설정을 켰는데 아무 효과가 없다"고 느낀다. `Korean` 탭의 안내 문구(§3.6)가 이 상태를 진단하도록 돕는다.

⭐⭐⭐ **F-16.1 행 — 이슈 #125 결정 기록 (인풋 박스 세션 중 D2 재평가 한정)**: 위 표의 "그 외 어떤 modifier 도 눌려 있지 않을 때" 조건은 세션 밖 판정(§3.4)뿐 아니라, 인풋 박스 세션 중 재평가(D2, §3.1 "세션 중 발화 예외")에서도 같은 조건을 쓴다 — 후자의 판정에 **이슈 #125 가 수정한 지점**이 있다: hyper 소스 키가 세션이 열리기 전에 hold 확정된 뒤 세션 중 물리적으로 떼어지면(§3.1 "이슈 #125" 결정 기록), FSM 슬롯이 stale 하게 `HoldConfirmed` 로 남아 "다른 modifier 없음" 조건을 그릇되게 깬다. 정본 눌림 테이블로 그 stale 을 걸러내도록 D2 판정만 좁혔다 — 세션 밖 F-16.1(이 행)의 판정 로직·조건은 무변경.

⭐⭐⭐ **F-16.1·F-16.2 행 — 이슈 #127 실측·수정 (autorepeat 재발화 억제, D2·세션 밖 공통)**: 사용자 macOS 키 반복 설정(`InitialKeyRepeat` 225ms 근방)에서 ⇧+Space 를 225ms 이상 누르면 물리 SPACE **자동 반복(autorepeat)** KeyDown 이 반복 도착한다. `evaluate_korean_rules`(D2·세션 밖 공통 함수)는 원래 `ev.autorepeat` 를 보지 않아 반복 down 마다 합성 `⌃Space` KeyDown 을 매번 새로 방출했다(래치는 "자동 반복 대비" 덮어쓰기만 함) — `SynthEvent`/플랫폼 합성에 autorepeat 플래그가 실리지 않으므로 macOS 가 매 반복을 독립된 토글로 오인해 **입력 소스가 반복마다 되토글**됐다(실기기 로그 실측 — 208ms 뒤 Korean→ABC 되돌아감). **수정**: `KoreanRule` 에 `is_input_source_toggle: bool` 필드를 추가해 F-16.1·F-16.2(출력이 시스템 `⌃Space` 토글 핫키)만 `true` 로 표시하고, 이 규칙들의 autorepeat KeyDown 은 같은 `trigger_key` 래치가 이미 서 있으면(그리고 그 래치가 지금 매칭된 규칙 자신의 것이면) **재발화하지 않고 소비만** 한다(원본도 하류로 안 보냄) — "1 press = 정확히 1 chord"(D-K6 규약)로 되돌린다. **F-16.3(한자)·F-16.4(백틱)는 대상이 아니다** — 이 두 규칙의 출력은 토글이 아니라 실제로 반복 타이핑되는 문자/제어 키라, 물리 키를 누르고 있는 동안 매 tick 재발화하는 것이 정상 동작이다(기존 재발 방지 테스트가 이미 그렇게 고정하고 있었다). F-19(`evaluate_language_rules`)는 같은 함수 구조(래치)를 쓰지만, 그 KeyDown 분기가 다루는 비-`AloneTap` 규칙(F-19.5·F-19.6)은 전부 F-16.3/F-16.4 와 같은 문자 치환류이고, 토글형 F-19 규칙(F-19.1/2/3/4/7)은 애초에 이 함수를 타지 않고 quick press FSM(autorepeat 를 이미 방어 처리함)을 거치므로 **변경 불필요**로 판정했다. 실측·대안 비교(`SynthEvent` 에 autorepeat 전파하는 대안을 영향 범위·의미론 오염을 근거로 기각)는 `docs/plan/issue-127-shiftspace-autorepeat.md`.

⭐ **F-16.3 의 입력 소스 조건은 이슈 #20 의 표가 누락한 것이다.** 원본 Karabiner 설정을 다시 확인한 결과, 한자 규칙에는 앱 제외 조건과 **입력 소스 조건(`language == ko`)이 둘 다** 걸려 있다. 이 표는 그 누락을 정정해 반영한다. 근거: F-16.3 의 출력이 `return` 이라, 조건이 느슨해 오발하면 폼 제출·의도치 않은 줄바꿈 같은 **되돌리기 어려운 부작용**이 난다 — 조건을 좁게 잡는 것이 안전한 방향이다.

⭐ **F-16.2·F-16.3 에도 "modifier 부재" 를 요구한다 — 구현 시점의 좁힘 결정.** 이슈 #20 의 표에는 이 조건이 없었으나, 근거 둘로 좁히는 쪽을 택했다. (a) 원본 Karabiner 규칙의 `from` 에는 `modifiers.optional` 이 없다 — Karabiner 의 기본 의미론상 **나열되지 않은 modifier 가 눌려 있으면 매치하지 않는다.** 즉 원본 규칙도 이미 modifier 부재를 요구하고 있었다. (b) 바로 아래 문단이 F-16.3 에 대해 이미 판정한 것과 같은 이유다 — 출력이 `return` 이라 오발하면 되돌리기 어렵다. 부수 효과로 `hyper`+한/영 같은 조합이 F-16 에 가로채이지 않는다.

⭐ **F-16.2(한/영)에는 한국어 입력기 조건을 걸지 않는다 — 걸면 기능이 깨진다.** 한/영 키는 *입력 소스를 바꾸는* 키다. "한국어 입력기 활성일 때만 발화" 를 걸면 한국어 → 영문 전환은 되지만, **영문 상태에서는 게이트가 거짓이라 발화하지 않아 한국어로 되돌아올 수 없다** — 편도 키가 된다. 위 표가 F-16.2 의 조건을 `앱 제외 목록` 만으로 두고 입력 소스 조건을 F-16.3(한자)에만 거는 것이 옳다. ⚠️ 이 구분은 놓치기 쉬워 여기 명시해 둔다.

⭐ **F-16.4 의 "modifier 부재" 조건이 이 규칙의 핵심이다.** Karabiner 규칙의 원문 의도를 우리 말로 옮기면 "`` ` `` 를 포함한 단축키 사용에 영향을 주지 않는다" — 즉 `⌘`+`` ` ``·`⌃`+`` ` `` 같은 조합에는 절대 개입하지 않는다는 뜻이다.

- 판정은 **정본 눌림 테이블**로 한다 — `ev.flags` 의 비트로 판정하지 않는다. 근거: `key-remapping-engine.md` §5 #18, `docs/dev/architecture.md` §6.4 **P3**(좌/우 shift 가 같은 비트를 공유해 `ev.flags` 만으로는 구분 불가).
- caps lock 의 `alphaShift`(`0x10000`) 비트는 **눌림이 아니라 잠금 상태**이므로 이 판정에서 제외한다(`key-remapping-engine.md` §5 #21).
- F-05 가 합성한 hyper/meh/bleh flags 가 활성이면 F-16.4 는 **발화하지 않는다**.
- ⭐ **세션 중 발화 예외 (이슈 #101)**: 위 표의 조건은 **Seek 세션 밖** 기준이다 — 세션 중에는 계층 1 이 short-circuit 하므로 F-16 규칙은 원래 평가되지 않는다. 이 원칙에 대한 **유일한 예외가 F-16.1 이다**: 다국어 Seek 세션(인풋 박스 모드) 중에는 세션 게이트가 SPACE 키에 한해 같은 규칙·조건·래치를 그 자리에서 재평가한다(F-16.2~F-16.4 는 예외가 아니며, 한/영 키는 원본 통과·한자·백틱은 세션 중 발화 금지가 그대로다 — `seek-activation-and-session.md` §3.1 ③).
- ⭐⭐ **이슈 #121 실측 — 사용자 실 설정 전량 재현 하에서도 인풋 박스 ⇧+Space 는 1번째 탭부터 발화한다 (결정 기록)**: 사용자 실기기 설정(`korean.shiftSpaceSwitchesInputSource: true`·`presets.leftRightShiftToCaps`·`presets.shiftCapsToCaps`·hyper(우⌘)·D-1 캡스락 alias)을 재현한 T-121 시리즈가 "⇧+Space 1회 탭 = ⌃Space 치환 1회 방출"을 고정한다. shift 를 소스로 쓰는 F-08 규칙이 켜져 있어도, `is_tracked`(FSM)는 **세션 게이트 뒤**라 세션 중 shift 이벤트가 FSM 에 도달할 수 없고, F-08.9(좌/우 shift 동시)·F-08.10(shift+캡스락)의 트리거 조건은 단독 ⇧+Space 와 만나지 않는다(F-08.8 double tap·F-08.11 quick press 는 사용자 설정에서 꺼짐). **"정확히 3번째 탭에만 동작"의 실기기 매커니즘은 `(미확정)`** — 탭 스레드 런타임 상태·웹뷰 IME·시스템 hotkey 후보는 `docs/plan/issue-121-seek-shiftspace-tap.md` §8 M0~M9 로 확인한다. 이 PR 의 프로덕션 변경은 트레이스 계측 필드 확장뿐(판정 로직 무변경).
- ⭐⭐⭐ **이슈 #125 실측·수정 — hyper 슬롯 잔류가 D2 를 막는 경로 확정·수정 (결정 기록)**: #121 이 `(미확정)`으로 남긴 후보 E-②(hyper 슬롯 잔류)를 코드로 확정했다. hyper source(예: RIGHT_COMMAND)가 세션이 열리기 **전**에 `HoldConfirmed` 로 확정된 뒤 세션이 열린 동안 물리적으로 뗀다 — `is_tracked`(FSM 진입)는 세션 게이트 **뒤**라(위 #121 결정 그대로) 이 릴리즈가 `handle_tracked_key_event` 에 도달하지 못해 FSM 슬롯이 `HoldConfirmed` 로 잔류한다. 정본 눌림 비트셋(`pressed`)은 세션과 무관하게 항상 정확한데(`arbitrate_with_kind` 최상단이 세션 게이트보다 앞서 갱신), D2 가드(위 조건 3, `active_synth_flags` 빈 것)는 **FSM 슬롯 상태만** 보고 있어 stale 슬롯을 "진짜 hyper 활성"으로 오판해 F-16.1 을 계속 막아 왔다. **수정**: D2 가드를 `active_synth_flags_of_pressed_slots()`(`HoldConfirmed && is_pressed(소스 키)` 인 슬롯만 합산)로 교체 — 물리적으로 눌려 있는 진짜 hyper hold(기존 테스트가 지키는 동작)는 그대로 막고, 물리적으로 뗀 stale 잔류만 통과시킨다. `active_synth_flags()` 자체와 다른 소비처는 무변경(세션 밖에서는 `HoldConfirmed ⇒ is_pressed==true` 가 항상 성립하므로 영향 없음). "정확히 3번째" 주기 수치와 stale 이 애초에 왜 생기는지(정상 해제 유실의 실기기 트리거)는 여전히 `(미확정)` — 이번 수정이 닫는 것은 hyper 합성 flags 잔류가 D2 를 막는 경로 **하나**다. 실측·판정 근거는 `docs/plan/issue-125-seek-shiftspace-hyper-stale.md`.
- ⭐⭐⭐ **이슈 #129 실기기 트레이스·수정 — 세션 중 D2 합성 `⌃Space` 가 웹뷰에 흡수돼 6:1 로 전환됐다, 전송 경로 변경 (결정 기록)**: `ULTRAKEY_TRACE_TAP=1` 실기기 트레이스가 인풋 박스 세션 중 연속 ⇧+Space 6회 **전부** D2 정상 발화(`layer=KoreanInput emitted=[KeyDown 0x31 0x40001]`)를 확정했지만, 실제 macOS 입력 소스 전환(`kTISNotifySelectedKeyboardInputSourceChanged`)은 1회뿐이었다 — 방출:전환 = 6:1. `seek-activation-and-session.md` §3.1 ②(물리 `⌃Space` 는 같은 세션 상태에서 이미 통과·전환됨)와 대조해, 흡수는 "웹뷰가 키 윈도우"가 아니라 **합성 이벤트 고유**로 판정했다. **`TISSelectInputSource` 직접 전환·관측 기반 재시도는 둘 다 기각**했다(근거는 `seek-activation-and-session.md` §3.1 이슈 #129 항목 — macOS CJK 직접 전환 버그·되토글 리스크). **수정**: `evaluate_korean_rules`(이 문단이 가리키는 D2 재평가 함수)의 판정 로직·조건·래치는 **무변경**이고, `ultrakey-engine` 이 D2 의 산출(`SynthEvent`)을 인풋 박스 세션 한정으로 탭 콜백 밖(`post()`)에서 내도록 전송 경로만 바꿨다 — 코드 근거·게이트·수용 기준은 `docs/plan/issue-129-seek-webview-inputsource.md`(§7 P2 확정), 세션 프로토콜 결정은 `seek-activation-and-session.md` §3.1 이슈 #129 항목.

⭐ **왜 출력이 "유니코드 문자 직접 주입"이 아니라 "같은 keycode + option 플래그"인가.**

1. 한국어 입력 소스 자신의 레이아웃이 `option`+`` ` `` 위치에 백틱을 두고 있다 `(추정 — 근거: 사용자의 Karabiner 규칙이 실제로 이 조합으로 동작 중이다. 실측 절차는 §5#5)`.
2. ⛔ **`localization-and-input-sources.md` §3.2.2 (i)의 역방향 탐색을 여기에 쓰면 틀린 답이 나온다.** F-14 의 `current_layout()` 은 현재 소스가 ASCII 불가일 때(한국어 입력기가 정확히 그렇다) `TISCopyCurrentASCIICapableKeyboardLayoutInputSource` 로 **레이아웃 자체를 교체**한다. 그 폴백 레이아웃(예: US)에서 백틱의 역산 결과는 "modifier 없는 grave" 이고, 그것을 실제 한국어 입력기에 보내면 **다시 `₩` 가 나온다**. 즉 F-14 의 역방향 테이블은 F-16.4 에 재사용할 수 없다.
3. `CGEventKeyboardSetUnicodeString`(F-14 §3.2.2 (ii))도 채택하지 않는다 — IME 조합 버퍼를 우회해 조합 중인 글자를 깨뜨릴 위험이 있다.

즉 이 키들은 **IME 토글 전용의 특수 이벤트**이며, `CGEventTap` 에 어떤 이벤트 종류로 도착하는지(`KeyDown` 인지 `FlagsChanged` 인지)는 여전히 확인되지 않았다.

⭐ **이 프로젝트는 정확히 이 지점에서 세 번 데였다** — M1 이 `FlagsChanged` 를 흘려보내 hyper 가 전혀 발동하지 않았고, PR #23 은 modifier **출력**을 `KeyDown`(flags 0)으로 합성했다. 두 사고의 공통 원인은 "실제 macOS 가 보내는 이벤트 모양" 을 가정한 것이다.

**결정: 도착 이벤트 종류를 가정하지 않는다.** 구현은 `Arbiter::normalize_kind()` 가 `FlagsChanged` 를 정본 눌림 테이블 기준의 `KeyDown`/`KeyUp` 으로 **환원한 뒤**의 값으로만 판정한다(이슈 #13 이 만든 기구를 그대로 쓴다 — 새 기구를 만들지 않는다). 그래서 두 모양 중 어느 쪽으로 도착해도 같은 경로를 탄다. ⭐ **자동 테스트가 두 모양을 모두 재현해 같은 결과가 나오는지 확인한다** — 그것이 위 세 사고의 재발 방지다.

> ⭐ **상호 참조 (이슈 #76, Seek 세션 중 한/영 키)**: **Seek 세션 중 한/영 키는 F-16.2 와 무관하게 원본 통과된다** — 계층 1(Seek 세션, `seek-activation-and-session.md` §3.1 한/영 키 예외)이 계층 3(F-16.2) 보다 먼저 평가되므로, **세션 중 F-16.2 가 발화하지 않는 것은 설계된 동작이다.** F-16.2 의 앱 제외 게이트(§3.5)도 세션 중 통과에는 적용되지 않는다.
>
> ⭐ **상호 참조 (이슈 #93, Seek 다국어 검색 — 이슈 #76 D2 의 "후속 작업" 해소)**: 이슈 #76 이 "한글 조합(IME)은 범위 밖·후속 작업"으로 남긴 반쪽을 이제 해소한다 — 검색 언어 설정(`seek.searchLanguage`)이 명시적 비영어면 Seek 검색 바가 실제 `<input>` 이 되어 **macOS IME 가 직접 한글(그리고 중·일·서)을 조합**한다(세션 한정 포커스 핸드오프, `seek-activation-and-session.md` §3.1 다국어 모드 행). F-16 계열의 Rust 자모 결합 엔진은 **채택하지 않는다**(plan 기각 대안 (d) — 네 언어를 실제 IME 없이 재현 불가). 다국어 세션에서도 한/영 키(`0x68`)는 여전히 원본 통과라 F-16.2 는 세션 중 발화하지 않는다 — §3.2 의 상호 참조가 그대로 성립한다.
>
> ⭐ **상호 참조 (이슈 #101, Seek 인풋 박스 세션 중 F-16.1)**: 위 두 문단과 달리 **F-16.1(⇧+Space)만은 세션 중 발화 예외**다 — 다국어(인풋 박스) 세션에서 세션 게이트가 SPACE 키에 한해 F-16.1 규칙을 그 자리에서 재평가해 `⇧+Space` → `⌃Space` 치환을 수행한다(§3.1 "세션 중 발화 예외" · `seek-activation-and-session.md` §3.1 ③). F-16.2(한/영 키)·F-16.3(한자)·F-16.4(백틱)는 예외가 아니며, 이 문단은 위 "F-16.2 는 세션 중 발화하지 않는다" 확정과 **모순되지 않는다** — 예외는 F-16.1 하나이고, 한/영 키(`0x68`)는 여전히 원본 통과다.

**⚠️ JIS 키보드와 keycode 를 공유한다는 사실의 부작용.** 같은 `0x66`/`0x68` 은 JIS 물리 키보드의 `英数`/`かな` 키도 낸다. 일본어 배열 키보드를 쓰는 사용자가 F-16.2·F-16.3 을 켜면 그 키들이 한국어 동작을 하게 된다. 두 항목의 기본값이 ☐ 이므로 **사용자가 명시적으로 켜야만** 일어나며, 그 대가로 얻는 것이 이 기능 자체이므로 허용 가능한 부작용으로 판정한다(§5 #13).

**🔴 반대 증거는 살아 있다**: ZMK 펌웨어 이슈 #1236 — "LANG1/LANG2 가 macOS 에서 동작하지 않는다(Windows 에서는 된다)"는 미해결 보고. 다만 이것은 **키보드 펌웨어가 그 usage 를 송출하는 쪽**의 문제로 보이며, 실물 106키 키보드에는 해당되지 않을 가능성이 크다. §9 #1 로 존치한다.

### 3.3 입력 소스 조건 — F-14 의 재사용과 ⭐ 재사용할 수 없는 부분

F-16.3·F-16.4 는 "한국어 입력기가 활성일 때만" 발화한다.

**이미 있는 것**(`crates/ultrakey-platform/src/text_input_source.rs`, F-14(B), M1 에서 구현됨):

- `TISCopyCurrentKeyboardInputSource()` 조회
- `kTISPropertyInputSourceIsASCIICapable` 판정
- `kTISNotifySelectedKeyboardInputSourceChanged` 구독(`InputSourceObserver`) — 입력 소스 변경 알림
- `LayoutSnapshot { source_id, is_ascii_capable, used_ascii_fallback, … }`

**⭐⭐ 그대로 재사용할 수 없는 지점 — 이 절의 핵심 발견.**
`current_layout()` 은 현재 소스가 ASCII 불가일 때 `TISCopyCurrentASCIICapableKeyboardLayoutInputSource` 로 소스를 **교체한 뒤** `source_id` 를 읽는다. 따라서 한국어 입력기가 활성일 때 `LayoutSnapshot.source_id` 는 **한국어 입력기가 아니라 폴백 레이아웃(예: US)의 ID** 다. **F-16 이 이 필드로 "한국어 입력기 활성"을 판정하면 항상 거짓이 나온다.**

**결정**: F-14 가 **교체 이전 원본 소스의 언어**를 추가로 노출해야 한다.

- `TISGetInputSourceProperty(src, kTISPropertyInputSourceLanguages)` 의 **첫 원소**가 `"ko"` 인지로 판정한다. 이것이 Karabiner 의 `input_source_if { language: "ko" }` 조건과 같은 기준이다.
- `is_ascii_capable == false` 만으로는 **불충분하다** — 일본어·중국어 IME 도 ASCII 불가다.
- `LayoutSnapshot` 에 필드를 하나 더하는 형태로 하되, **폴백 교체 전에 읽어야 한다**는 순서 제약을 명시한다. 이것은 F-14 명세의 갱신 사항이므로 §9#4 로 상호 참조를 남긴다.

**판정 시점과 임계 경로**:

- ⛔ 콜백 안에서 `TIS*` 를 호출하지 않는다 — `docs/dev/architecture.md` §2.2 의 금지 목록(할당·시스템 호출)에 걸린다.
- ✅ F-10 앱 게이트와 **정확히 같은 패턴**: `kTISNotifySelectedKeyboardInputSourceChanged` 수신 시 **메인 스레드가 판정해 `AtomicBool` 하나에 게시**하고, 콜백은 그 부울만 O(1)로 읽는다(`docs/dev/architecture.md` §2.2 표의 세 번째 행).

**입력 소스가 바뀌는 순간의 동작 — 결정**:

- 판정은 **keyDown 이 도착한 시점의 게이트 값**으로 한다.
- ⭐ **keyDown 과 keyUp 사이에 입력 소스가 바뀌는 경우**: F-16.4 는 조합이 아니라 단일 키 치환이라, keyDown 만 치환되고 keyUp 은 치환되지 않으면 **option 플래그가 걸린 채 남거나 짝이 맞지 않는 keyUp 이 나간다.** 대응: 그 keycode 에 대해 "치환 중" 표시를 정본 상태 테이블에 세우고, **대응하는 keyUp 은 조건을 다시 평가하지 않고 keyDown 의 결정을 그대로 따른다**(§5#9).
- ⭐ **자기 참조 고리**: F-16.1·F-16.2 의 출력이 곧 입력 소스 변경이므로, 발화 직후 F-16.3·F-16.4 의 게이트 값이 뒤집힌다. 알림 도착과 다음 키 입력 사이에 순서 보장은 없으나, **세 규칙의 트리거 키가 서로 다르므로**(space/lang1 vs lang2/grave) 실질적 문제를 만들지 않는다.
- ⭐ **알림 지연 중 도착한 키**: `CFNotificationCenter` 의 분산 알림은 즉시성이 보장되지 않는다. 게이트가 아직 옛 값이면 그 1회는 잘못 판정될 수 있다. **F-16.4 의 잘못된 판정은 글자 하나가 틀리는 것**이라 허용 가능하지만, **F-16.3 은 `return` 을 내므로 허용 가능하지 않다** — F-16.3 은 게이트가 참인 것을 **엄격히** 요구하고, 판정 불가 상태(스냅샷 없음)에서는 **발화하지 않는다**(fail-closed). F-16.4 도 fail-open 이 아니라 **역시 fail-closed**(원래 키를 그대로 통과 = `₩` 가 나감)로 정한다 — 사용자가 보기에 "가끔 안 먹는다"가 "가끔 엔터가 눌린다"보다 낫다.

### 3.4 중재 — 기존 기능과의 관계

**계층 배치 결정**: F-16 의 규칙 4종은 전부 `key-remapping-engine.md` §3-b 의 **계층 3(Preset 조합)** 에 배치한다.

- 근거: 계층 4(단순 리매핑)는 정의상 **조건 없는 1:1** 치환이다. F-16 규칙은 전부 조건부(modifier 부재 / 입력 소스 / 앱 제외)이므로 계층 4 가 아니다.
- 계층 3 안에서 F-16 규칙들끼리는 소스 키가 전부 다르므로(`space`·`lang1`·`lang2`·`grave`) 서로 충돌하지 않는다.
- `docs/dev/architecture.md` §6.4 의 규칙 ID 체계를 이어 **P13~P16** 을 F-16 규칙 4종에 배정할 것을 제안한다(평가 순서를 ID 로 고정하는 기존 규약).

**⭐ 소스 키 enum 35종과의 관계 — 판정: enum 을 늘리지 않는다. 별도 경로다.**

1. `SourceKey`(`crates/ultrakey-core/src/keycode.rs`) 35종은 hyper/meh/bleh·Seek 의 **소스 키 팝업에 나열되는 목록**이고, SuperKey v1.66 의 AX 실측으로 확정된 **원본의 열거형**이다(`hyperkey.md` §4). 여기에 항목을 더하면 원본 팝업과 클론 팝업이 달라진다 — F-16 이 원본과 갈라지는 범위를 **`Korean` 탭 하나로 국한한다**는 결정과 어긋난다.
2. `SourceKey` 의 의미는 "**modifier 로 승격시킬 수 있는 모멘터리 키**"다 — 그래서 caps lock·좌우 modifier·`F1`~`F24` 뿐이고 문자 키가 하나도 없다. `lang1`/`lang2` 는 modifier 가 아니라 **액션 키**라 이 열거형의 의미에 맞지 않는다.
3. `SourceKey::keycode()` 는 `Option<KeyCode>` 를 반환하고 `MenuPc`·`F21~F24` 는 `None` 이다. `lang1`/`lang2` 를 여기 넣으면 **팝업에서 고를 수는 있는데 아무 일도 일어나지 않는 항목**이 하나 더 생긴다 — 가장 나쁜 UX 다.

→ 대신 F-16 은 자신의 규칙 테이블에서 **원시 `KeyCode` 상수를 직접** 참조한다.

**⭐ `Shift + Space` 와 F-08 프리셋의 충돌 검토**:

| 상대 | 판정 |
| :--- | :--- |
| F-08.4 `Caps lock + space = enter` | **충돌 없음.** 트리거가 `caps lock`+space 이고 F-16.1 은 shift+space 다. 다만 **둘 다 켜진 상태에서 caps lock 과 shift 를 함께 누른 채 space** 를 누르면 F-16.1 의 "shift 외 modifier 부재" 조건이 깨져 F-08.4 가 이긴다 — 계층 3 안의 규칙 ID 순서로 결정론적이며, 조용한 패배가 아니다 |
| F-08.10 `Shift + caps lock = caps lock` | **충돌 없음.** 트리거 조합이 겹치지 않는다(space vs caps lock) |
| F-08.11 `Quick press left or right shift to input corresponding:` | **충돌 없음 — 오히려 기존 기구가 정확히 해소한다.** `docs/dev/architecture.md` §6.4 **P2**(`on_other_key_down`)에 따라 shift 가 `PendingDown` 인 상태에서 space 의 keyDown 이 오면 shift FSM 이 즉시 `HoldConfirmed` 로 전이해 quick press 후보에서 빠진다. 즉 `Shift+Space` 를 쓸 때 괄호가 잘못 튀어나오는 일이 구조적으로 없다 |
| **F-05 hyper/meh/bleh 소스 키 = `left shift` 또는 `right shift`** | ⚠️ **여기가 진짜 위험 지점이다.** shift 가 hyper 소스이면 shift 유지 중의 space keyDown 이 이미 hyper 합성 상태에서 계층 3 에 도달한다. F-16.1 이 그대로 발화하면 사용자가 의도한 `hyper + space` 단축키가 죽는다. **대응**: F-16.1 의 조건에 "shift 이외의 modifier 가 눌려 있지 않을 것"을 넣었으므로, hyper 합성 flags 가 활성이면 발화하지 않는다. 이것은 Karabiner 원문 규칙(`mandatory: ["shift"]` — 다른 modifier 가 있으면 불일치)의 의도와도 일치한다 |

또한 다음도 확정한다.

- **출력이 자기 탭으로 되돌아온다.** `⌃Space`·`⌥Return`·`⌥`+grave 합성 이벤트는 전부 `key-remapping-engine.md` §5 엣지 12 의 **엔진 고유 마커**를 달아 콜백 진입 즉시 통과시킨다(`docs/dev/architecture.md` §2.3 `0-a`). 기존 기구를 그대로 쓴다 — 새 기구를 만들지 않는다.
- **합성 출력에 hyper flags 를 얹지 않는다** — `docs/dev/architecture.md` §6.4 **P5** 를 그대로 따른다. 방출 flags = 필요한 modifier 만. `alphaShift` 도 제거한다(`key-remapping-engine.md` §5 #21).

### 3.5 앱별 제외 — ⭐ 판정: F-10 게이트만으로는 불충분하다

근거 2가지:

1. **F-10 게이트는 전역(all-or-nothing)이다.** `AppGate::is_remapping_disabled()` 는 부울 하나이고, `docs/dev/architecture.md` §2.3 의 `0-c` 는 그 앱에서 **계층 1~5 전부**를 통과시킨다. 그러나 사용자가 원하는 것은 "원격 데스크톱 앱에서 한국어 키 처리만 끄고 hyper 는 계속 쓴다"이다 — 원격 데스크톱 안에서 hyper 를 쓰는 것은 정당한 사용이다.
2. **F-10 목록은 사용자가 메뉴바에서 하나씩 수동으로 채운다.** F-16 의 제외 대상은 **기능 내재적**이다 — 사용자가 앱마다 문제를 겪고 나서 발견해 추가하게 만들면 안 된다.

**결정**: F-16 이 **기능군 단위의 기본 제외 목록**을 소유한다.

- **평가 시점**: `docs/dev/architecture.md` §2.3 의 `0-c`(전역 게이트)를 통과한 뒤, 계층 3 안에서 F-16 규칙을 평가하기 직전.
- **임계 경로 비용**: 전역 게이트와 동일한 패턴 — 최전면 앱이 바뀔 때 **메인 스레드가 미리 판정해 `AtomicBool` 하나에 게시**한다. 즉 게이트가 두 개가 된다(전역 1비트 + 한국어 1비트). 콜백은 부울 두 개만 읽는다.
- ⛔ **개별 앱을 명세에 열거하지 않는다.** 대신 **선정 기준**을 명세한다:

  > **키 입력을 이 맥의 입력 스택이 아니라 다른 OS·다른 세션의 입력 스택으로 그대로 전달하는 앱.** 원격 데스크톱(RDP)·화면 공유(VNC) 클라이언트, 가상 머신 콘솔이 여기 해당한다.
  > **근거**: 이 앱들 안에서 한/영·한자 키는 **대상 시스템의 입력기**가 처리해야 하는 것이다. macOS 쪽에서 `⌃Space` 로 바꿔 버리면 대상 시스템에 원래 키가 도달하지 못해, 원격 세션 안에서 한글 입력 자체가 불가능해진다.

- **기본 목록은 앱에 내장하되 명세에 열거하지 않는다.** 구현 시 위 기준으로 선정한다.
- **사용자 수단**: `Korean` 탭에 체크박스 하나 — `원격 데스크톱 클라이언트에서 한국어 키 처리 끄기`(기본 **☑**, F-16 항목 중 유일한 기본 켜짐). ~~목록 자체를 편집하는 UI 는 두지 않는다~~ ⭐ **이 결정은 이슈 #73 이 뒤집었다 — 아래 정정(2026-09-02) 참조.** 목록에 없는 클라이언트를 쓰는 사용자는 메뉴바의 `Ignore <앱>`(F-10)으로 대응한다. 이 절충의 한계는 §9#6 으로 승계한다.

> ⭐⭐ **정정 (2026-09-02, 이슈 #73 / D-K17) — "목록 편집 UI 를 두지 않는다" 결정은 폐기한다.**
>
> **무엇이 바뀌었나.** 실기기 피드백(2026-09-01)에서 `원격 데스크톱 클라이언트에서 한국어 키 처리 끄기` 옵션의 **대상 목록이 무엇인지 전혀 알 수 없고, 추가/제거/변경이 불가능하다**는 것이 사용자가 실제로 겪는 결함으로 확인됐다. 위 절충("목록에 없는 클라이언트는 메뉴바의 `Ignore <앱>` 으로 대응")이 실제로는 **동작하지 않는 절충이었다** — `Ignore <앱>`(F-10)은 **전역 게이트**라 그 앱에서 hyper 까지 함께 죽는다(§3.5 근거 1 이 지적한 그 문제). 즉 이 절충의 한계(§9#6)가 이론상 한계가 아니라 **실사용 피드백으로 확인된 결함**이 된 것이다. "목록을 모른 채 켜져 있는 스위치"는 사용자가 문제를 진단할 수 없게 만든다.
>
> **정정된 결정**:
>
> - **기본 목록은 앱에 내장한다**(변함없음 — 선정 기준도 위 문장 그대로다). ⛔ 명세에 앱을 열거하지 않는 원칙도 유지한다 — 목록 자체는 `ultrakey-korean::apps` 가 소유하며 항목마다 근거 등급을 단다(그 모듈 문서 참고).
> - **저장 모델**: `korean.excludedBundleIds` = 번들 ID 문자열의 JSON 배열. **부재(키 없음) = 기본 12종** — F-15 "부재 = 기본값" 그대로다. **존재하면(빈 배열 포함) 기본 목록을 통째로 대체한다** — 병합(합집합)하지 않는다. 근거: 사용자가 기본 항목 하나를 지웠는데 병합이 되살려 놓으면 "제거" 조작이 동작하지 않는 것이다. "리스트 하나 = 원자적 단위"라는 저장 계층의 성질(per-device-settings.md §3.4)과 맞물린다. 빈 배열은 "아무 앱도 제외하지 않음"이라는 **명시적 값**이라 부재와 다르다. 저장 키: `korean.excludedBundleIds`(`Vec<String>`, 부재 = 기본 목록).
> - **UI**: `Korean` 탭의 항목 5 아래에 **가변 길이 목록 편집기**(per-device-settings.md §3.4.1 이 확립한 컨트롤 유형 — 새 컨트롤 유형을 만들지 않고 그것을 재사용한다)를 둔다. 각 행 = 번들 ID 텍스트 입력 + 삭제 버튼, 아래 `앱 추가`·`기본 목록으로 되돌리기` 버튼. 부재(기본 목록) 중에는 기본 목록을 채워 보여주고, 행 하나라도 편집하는 순간 그 화면 목록 전체가 오버라이드로 굳는다(F-17 의 "물려받은 목록을 편집하면 전용 배열로 굳는다"와 같은 패턴). 되돌리기는 오버라이드 키 자체를 지운다(부재 = 기본). 빈 행은 저장하지 않고(§3.4.1 항목 4 규약), 오버라이드가 존재할 때만 되돌리기 버튼이 보인다(② 숨김).
> - **병합 규칙**: 오버라이드 존재 = 완전 대체. 근거: 사용자가 기본 항목 하나를 지웠는데 합집합 병합이 되살리면 "제거" 조작이 동작하지 않는다. `preferences-ui.md` §1 의 "고정된 항목의 열거이지 규칙 편집기가 아니다" 원칙은 **체크박스 항목**에 대한 것이고, 목록 데이터는 Keyboards 탭의 가변 목록 편집기가 이미 확립한 대로 편집기 컨트롤 유형의 소관이라 충돌하지 않는다.
> - **기각한 대안**: (a) 기본 12종 + 사용자 추가분만 저장(diff 모델) — 사용자가 기본 항목을 지우는 조작을 표현할 수 없어 기각. (b) F-10 목록과 하나로 합침 — 전역 게이트가 hyper 까지 죽이므로 §3.5 의 근거 1과 어긋난다. (c) 목록을 UI 에서 아예 숨김(기존 결정 유지) — 이슈 #73 피드백이 그 절충이 실패했음을 보였다.
> - **임계 경로 비용**: 변화 없음 — 여전히 최전면 앱이 바뀔 때 메인 스레드가 미리 판정해 `AtomicBool` 하나에 게시한다. 목록 편집은 설정 창에서만 일어나는 드문 이벤트라 주입 비용(목록 전체 교체)은 임계 경로 밖이다.

### 3.6 ⭐⭐ HID 계층 리매퍼와의 공존 — `key-remapping-engine.md` §5 #19 를 정면으로 다룬다

**전제**: 이 사용자는 Karabiner-Elements 를 **실제로 쓰고 있다.** 가정이 아니다.

**§5 #19 가 확정한 구조**: Karabiner 는 가상 HID 장치로 키를 바꾸므로 **경로 A(`CGEventTap`)보다 아래**에 있다. 우리 탭에는 **이미 변환된** 이벤트가 도착한다.

**그래서 무슨 일이 일어나는가**:

| Ultrakey 규칙 | 우리 탭에 실제로 도착하는 것 | 결과 |
| :--- | :--- | :--- |
| F-16.1 (shift+space) | Karabiner 규칙 2 가 이미 처리 → `space` + `left control` 이 도착하고 **shift 는 Karabiner 가 소비했다** | **발화하지 않는다.** 조건(shift 눌림)이 성립하지 않는다 |
| F-16.2 (`lang1`) | Karabiner 규칙 3 이 이미 처리 → `space` + `left control` 이 도착한다. **`lang1` keycode 자체가 오지 않는다** | **발화하지 않는다** |
| F-16.3 (`lang2`) | Karabiner 규칙 4 가 이미 처리 → `return` + `right option` 이 도착한다 | **발화하지 않는다** |
| F-16.4 (`₩`) | Karabiner 규칙 1 이 이미 처리 → `grave` + `option` 이 도착한다 | **발화하지 않는다.** 우리 조건은 "modifier 부재"인데 option 이 붙어 있다 |

**⭐ 결론 1 — 파괴적 충돌은 없다. Karabiner 가 이기고, Ultrakey 는 조용히 무동작한다.** 사용자 입장에서 최종 동작은 (Karabiner 가 켜져 있는 한) 정확히 지금과 같다.

**⭐ 결론 2 — F-16.4 의 "modifier 부재" 조건이 뜻밖의 안전장치다.** 이 조건이 없었다면 Karabiner 가 이미 붙인 option 위에 우리가 option 을 한 번 더 얹어 **이중 변환**이 일어났을 것이다. 조건을 좁게 잡은 것이 우연히 이 실패 모드를 막는다.

**⭐ 결론 3 — 그러나 §5 #19 의 원래 사례보다 나쁘다.** caps lock 사례에서는 "사용자가 리매퍼가 실제로 내보내는 키(`left control`)를 소스로 지정하면 된다"는 우회가 있었다. **F-16.2 에는 우회가 없다** — `lang1` 을 대신할 키가 존재하지 않는다. 유일한 해법은 **Karabiner 쪽 규칙을 끄는 것**이고, 그것이 곧 이 기능의 존재 이유이기도 하다(Karabiner 의존을 걷어낸다).

**진단 — 결정**: 도구 이름을 하드코딩하는 탐지가 아니라 **행동 기반 진단**을 정본으로 한다.

- **기각한 대안 ①**: `hidutil property --get UserKeyMapping` 조회 — 경로 B 만 보이고, **Karabiner 는 가상 HID 장치라 여기 잡히지 않는다.** 애초에 답을 낼 수 없다.
- **기각한 대안 ②**: 알려진 리매퍼의 프로세스·번들 ID 탐지 — 도구 이름을 하드코딩해야 하고 Karabiner 외에도 여럿이라 목록이 영원히 불완전하다.
- **채택**: F-16 을 켠 상태에서 사용자가 그 키를 실제로 눌렀을 때 **우리 탭에 무엇이 도착했는지**를 §3.2 절차 4 의 진단 모드로 기록한다. `lang1` 을 눌렀는데 `space`+control 이 도착했다면 아래층 리매퍼가 이미 처리했다는 **직접 증거**다. 도구가 무엇이든 상관없이 사실을 본다.
- **사용자 노출**: `Korean` 탭에 "이 기능이 동작하지 않는다면" 안내를 두고, 다른 리매핑 도구의 같은 규칙을 끄도록 안내한다. 상세 문구·표현은 §9#8 로 승계한다.

⚠️ **범위 밖이지만 상호 참조**: 이 사용자의 Karabiner 설정에는 `caps lock ↔ left control` 맞바꿈도 있다. 이것은 `docs/dev/architecture.md` §6.1 결정 D-1(caps lock → `F18` 커널 매핑)과 정면으로 겹치며, **이슈 #19(물리 caps lock 버그)의 원인**이다. F-16 은 caps lock 을 쓰지 않으므로 직접 영향은 없으나, 두 작업이 같은 코드를 건드리므로 이슈 #19 가 먼저 머지되어야 한다는 사실을 기록한다.

### 3.7 ⭐ K9 — modifier+문자키 단축키를 영어 소문자로 변환 (이슈 #73, D-K18) — **클론 고유 확장**

> ⭐ **원본 SuperKey 에 없는 기능이다.** 갈라짐 기준 1(원본이 다루지 않는 문제)에 해당한다 — 원본은 한국어 입력 환경을 다루지 않으므로 이 결함 자체가 원본에 존재하지 않는다. F-16 신설의 선례(§1)를 그대로 따른다: 한국어 UI 를 내놓은 이상, 한국어 입력 환경에서 실제로 겪는 결함을 다루는 것이 제품 논리로서 일관된다.

**문제**: 한국어 입력 모드에서 modifier 키(특히 `option`·`fn`)를 누른 채 문자 키를 누르면, 그 조합이 앱 단축키가 아닌 경우 한국어 입력기가 **한글 자모**로 인식해 버리는 앱이 있다. 그 결과 단축키가 정상 동작하지 않는다(이슈 #73 실기기 피드백).

**결정**: `modifier 키와 함께 누른 문자 키를 영어 소문자로 입력` 옵션(기본 **☐**)을 둔다. 켜져 있으면 **문자 키(A~Z)의 keyDown 이 도착했을 때 modifier 키가 하나 이상 눌려 있는 상태**면, 그 이벤트를 소비하고 그 문자를 **영어 소문자**로 합성해 입력한다(`Effect::TypeChar('a'~'z')` — F-08.11 quick press 괄호가 쓰는 것과 같은 `TypeChar` 기구를 재사용한다. 새 출력 경로를 만들지 않는다).

**발화 조건(전부 성립해야 한다)**:

1. `korean.modifierKeyTypesLowercase` 가 `true`.
2. 도착 이벤트가 문자 키(A~Z, `kVK_ANSI_A`..`kVK_ANSI_Z`)의 **keyDown** 이다 — 정규화된 `kind` 기준(D-K13).
3. 정본 눌림 테이블 기준으로 modifier 키가 하나 이상 눌려 있다. 아무것도 없으면 발화하지 않는다 — modifier 없는 문자 키는 그대로 통과해야 한국어 입력기가 한글을 낸다(이 옵션의 목적은 "한글 타이핑은 그대로 두고 단축키만 살린다"다).
4. ⛔ **command·control·caps lock 이 눌려 있으면 발화하지 않는다.** 근거: `⌘C`·`⌃C` 같은 조합은 거의 항상 앱·시스템 단축키다 — 그 문자를 소문자 "c" 로 바꿔 버리면 복사가 깨진다. caps lock 조합은 대문자 의도다. 즉 **변환을 유발하는 modifier 는 shift·option·fn 계열뿐**이다. 이 좁힘이 이 옵션의 안전 핵심이다.
5. 앱 제외 게이트(`§3.5`)가 이 옵션에도 적용된다 — 원격 데스크톱 안에서는 개입하지 않는다.

**판정은 정본 눌림 테이블**로 한다 — `korean.rs::lowercase_action_for`. `ev.flags` 의 비트로 판정하지 않는다(§3.1 P3 와 같은 근거).

**출력 경로**: `Effect::TypeChar(소문자)` — `ultrakey-engine` 의 `text_output::plan_text_output` 이 §3.2.2 (i) 역방향 탐색 → (ii) 유니코드 폴백 순서로 옮긴다(F-08.11 quick press 괄호와 정확히 같은 발화 경로다 — 새 출력 기구를 만들지 않는다). keyUp 은 **소비만 하고 아무것도 내지 않는다** — `Effect::TypeChar` 가 down/up 한 쌍을 이미 합성하므로 keyUp 을 재치환할 래치가 필요 없다.

**기각한 대안**:

| 대안 | 기각 사유 |
| :--- | :--- |
| ① command·control 조합도 변환 | 앱·시스템 단축키(`⌘C`·`⌃C` 등)를 통째로 깨뜨린다. modifier+문자 중 실제로 한글로 깨지는 것은 `⌥`/`⇧`/fn 계열이고, ⌘/⌃ 계열은 한국어 입력기도 대개 영어 소문자를 낸다 — 건드리면 얻는 것보다 잃는 것이 크다 |
| ② "영어 소문자"가 아니라 유니코드 직접 주입으로 한글을 뺀다 | §3.1 이 `CGEventKeyboardSetUnicodeString` 을 기각한 것과 같은 이유 — IME 조합 버퍼를 우회해 조합 중인 글자를 깨뜨린다. `TypeChar` 경로는 `plan_text_output` 이 (i) 레이아웃 역산 → (ii) 유니코드 폴백 순서를 밟으므로 안전하다 |
| ③ 규칙 테이블(`KoreanRule`)에 넣는다 | K9 은 트리거 키가 고정된 규칙이 아니라 "눌린 modifier 상태 + 문자 키 도착"이라는 **판정식**이다 — 규칙 열거가 아니라 조건 플래그(`EngineConfig::korean_modifier_lowercase`)로 중재기에 주입하는 모양이 맞다(`caps_lock_alias` 와 같은 자리다) |

**평가 순서**: 계층 3 의 **Preset 조합 앞**. 근거: K9 의 트리거는 문자 키 자체라 preset combo 의 hold 키·F-16 규칙의 트리거 키(space/lang1/lang2/grave)와 겹치지 않아 순서 충돌이 원리적으로 없고, 조건 3 이 command·control 조합을 이미 배제했으므로 Preset 앞에 두어도 앱 단축키를 삼키지 않는다. 옵션이 꺼져 있으면(기본) 이 경로는 아예 평가되지 않는다 — 기존 동작과 완전히 같다.

## 4. 설정 항목 — `Korean` 탭

### 4.1 ⭐ 왜 새 탭인가 — 원본과 갈라지는 근거

`Seek`·`Hyperkey`·`Presets` 다음, `General` 앞에 **`Korean` 탭**을 신설한다(탭 순서: `Seek`·`Hyperkey`·`Presets`·`Korean`·`General`. 근거: `General` 은 관례상 마지막이고, 기능 탭 중 마지막 자리에 신설분을 둔다).

⭐ **지금까지 모든 명세가 "원본을 클론한다"를 기준으로 삼았다. 여기가 처음으로 의도적으로 갈라지는 지점이다.**

1. **재현할 원본이 없다.** SuperKey 는 한국어 사용자를 대상으로 하지 않는다. "원본을 클론한다"는 기준이 적용될 대상 자체가 없는 최초의 기능군이다.
2. **D4 가 이미 한 번 갈라졌다.** 현지화(`ko`+`en`)는 원본에 없는 클론 고유 선택이었다(`README.md` 제품 결정 D4). F-16 은 그 결정의 논리적 귀결이다.
3. **관심사가 기존 어느 탭과도 묶이지 않는다.** 한국어 기능 4종은 서로는 강하게 묶이지만(전부 한국어 입력 환경), 기존 4탭 어디에도 자연스럽게 들어가지 않는다.
4. **영어 사용자에게도 보인다.** 숨기지 않는다 — 아래 기각한 대안 ② 참조. 따라서 **`en` 문자열도 필요하다.**

**기각한 대안**:

| 대안 | 기각 사유 |
| :--- | :--- |
| ① `Presets` 탭 안의 새 섹션 | 성격이 다른 항목이 섞이고 목록만 길어진다. `Presets` 탭은 이미 4개 그룹 16종으로 가장 큰 탭(825×527pt)이다 |
| ② 한국어 입력기 감지 시에만 탭을 노출 | 영리하지만 설정이 숨어 혼란을 준다. 더 나쁜 것은 **입력 소스가 런타임에 바뀐다**는 점이다 — 탭이 나타났다 사라지고, `preferences-ui.md` §3.3 의 탭 전환 창 리사이즈와 최악으로 겹친다 |
| ③ 시스템 로케일이 `ko` 일 때만 노출 | ②보다 안정적이지만, **영어 UI 를 쓰면서 한국어로 입력하는 사용자**를 배제한다. `localization-and-input-sources.md` §3.1.2 의 로케일 결정과 입력 소스는 서로 독립된 축이다 |

**창 크기**: 기존 4탭은 `Seek` 555×378 · `Hyperkey` 710×517 · `Presets` 825×527 · `General` 613×273pt 다. ⭐ **`Korean` 탭은 `613 × 484` 로 확정했다(실측, §9 #5)** — 마크업을 실제로 렌더해 잰 내용 416px + `.panel` 상하 패딩 40px + 타이틀바 28px 이다. ⚠️ 이 문서가 처음 제안했던 `약 320pt` 는 **모자란 값이었다** — "정확한 값은 구현 시 내용에 맞춰 확정한다" 고 남겨 둔 것이 실제로 값을 바꾼 사례다. 너비 613 은 항목이 한 줄에 들어가 `General` 과 같다. `preferences-ui.md` §3.3 의 탭별 리사이즈 규약을 그대로 따른다.

- ⭐ **정정(이슈 #73, K5)** — 항목 5-a 의 목록 편집 UI. §3.5 의 정정 본문 참고. 저장 키 `korean.excludedBundleIds` 는 **부재 = 기본 12종**이고, 존재하면(빈 배열 포함) 기본 목록을 통째로 대체한다. 목록 편집기는 F-17 이 확정한 가변 길이 목록 편집기(§3.4.1)의 컨트롤 유형을 재사용한다 — 새 컨트롤 유형을 만들지 않는다. `KoreanView` 는 오버라이드 부재 시 백엔드 기본 목록(`defaultExcludedBundleIds`)을 함께 실어 보내 UI 가 기본 목록을 그릴 수 있게 한다.
- ⭐ **정정(이슈 #73, K9)** — 원본 SuperKey 에 없는 **클론 고유 확장**이다(§3.7). 기본값 ☐(부재 = `false`)이므로 일반 "부재 = 기본값" 규약이 그대로 성립한다.

## 7. 구현 접근

**판정: `Rust 바인딩`.** 새 API 가 없고 기존 FFI 를 재사용한다(`README.md` 구현 접근 3분류 중 이것). 근거: §6 이 보이듯 F-16 이 요구하는 모든 플랫폼 접근은 F-07/F-10/F-14 가 이미 확보한 `objc2-*` 바인딩 경로 위에서 이루어지며, 별도로 빌드하는 Swift/Objective-C 소스가 없다.

**구현 순서를 2단계로 나눈다** — 이것이 이 기능의 실용적 핵심이다.

- **1단계**: F-16.1(`Shift+Space`) · F-16.4(`₩` → `` ` ``) · §3.5 앱 제외 게이트 · §4 `Korean` 탭. 필요한 모든 사실이 확정되어 있다.
- **2단계**: F-16.2(한/영) · F-16.3(한자). ⭐ **착수 조건이던 §3.2 의 keycode 가 해소되어 이제 착수 가능하다**(`0x68`/`0x66`, 근거 3중). 다만 등급이 `(실기기 미검증)` 이므로, 실기기 확인 절차는 §3.2 "해소 이전의 기록" 에 그대로 남아 있다 — 한국어 106키 키보드가 확보되면 그대로 수행해 `(실측)` 으로 승격한다.
- ⭐ **두 단계를 나누는 의미는 남는다** — 1단계는 검증 기기에서 **실기기로 확인할 수 있고**, 2단계는 그럴 수 없다. 확인의 강도가 다르다는 사실을 구현·리뷰가 계속 구분해야 한다.

⭐ **오른쪽 command → `⌃⌥⌘` 안내**

> 사용자의 Karabiner 규칙 5종 중 "오른쪽 command 를 Hyper(`⌘⌃⌥`)로"는 **F-16 의 범위가 아니다 — 이미 되는 기능이기 때문이다.**
> `Include shift in hyper key` 를 끈 hyper 가 정확히 `⌃⌥⌘` 다. 코드에서 확인된다:
> ```rust
> // crates/ultrakey-core/src/flags.rs
> pub const HYPER_NO_SHIFT: EventFlags =
>     EventFlags(Self::CONTROL.0 | Self::ALTERNATE.0 | Self::COMMAND.0);
> ```
> PR #14 가 실기기로 확인했다 — "shift 포함을 끄면 `⌃⌥⌘` 3개만, 재시작 없이".
> **사용자 절차**: `Hyperkey` 탭 → `Remap key to hyper key` 켜기 → 소스 `right command` → `Include shift in hyper key` 끄기.
> ⛔ **중복 기구를 만들지 않는다.** `Korean` 탭에는 이 안내 텍스트만 두고, 같은 일을 하는 두 번째 설정을 만들지 않는다.

**기각한 대안**:

| # | 대안 | 기각 사유 |
| :--- | :--- | :--- |
| ① | `lang1`/`lang2` 를 `SourceKey` enum 에 추가 | §3.4 "소스 키 enum 과의 관계" 근거 3가지(원본 열거형 오염, 의미 불일치, `None` 항목이 늘어 UX 최악) |
| ② | 유니코드 직접 주입으로 백틱 출력 | §3.1 — IME 조합 버퍼를 우회해 조합 중 텍스트를 깨뜨릴 위험 |
| ③ | F-10 게이트만으로 앱 제외 처리 | §3.5 — 전역 게이트는 hyper 까지 함께 죽이고, 목록이 사용자 수동 관리라 기능 내재적 제외에 맞지 않는다 |
| ④ | 리매퍼 프로세스 탐지로 진단 | §3.6 — 도구 이름 하드코딩, Karabiner 는 가상 HID 라 탐지 자체가 불가능한 경우도 있다 |
| ⑤ | 한국어 입력기 감지 시에만 탭 노출 | §4.1 — 런타임에 나타났다 사라지는 탭은 창 리사이즈와 최악으로 겹치고, 영어 UI + 한국어 입력 사용자를 배제한다 |

## 8. 수용 기준

- [ ] `Shift + Space`(F-16.1)가 켜져 있고 다른 modifier 가 없을 때, `space` keyDown 이 `control`+`space` 로 치환되어 방출된다.
- [ ] `₩`(F-16.4)가 켜져 있고 한국어 입력기가 활성일 때, modifier 없는 `` ` ``/`₩` keyDown 이 `option`+같은 keycode 로 치환된다.
- [ ] ⭐ **`⌘`+`` ` ``·`⌃`+`` ` ``·`⇧`+`` ` `` 를 눌렀을 때 F-16.4 가 개입하지 않는다** — 이 부정형 기준이 §3.1 원문 의도의 정본이다.
- [ ] ⭐ **hyper 소스가 `right shift` 인 구성에서 `hyper + space` 가 정상 동작한다**(F-16.1 이 개입하지 않는다).
- [ ] ⭐ **한국어 입력기가 아닐 때 `` ` `` 키가 그대로 `` ` `` 를 낸다**(F-16.4 가 발화하지 않는다).
- [ ] 원격 데스크톱 클라이언트류가 최전면일 때 F-16 전체가 통과된다. **같은 상태에서 hyper 는 계속 동작한다**(F-10 전역 게이트와 구분되는 지점).
- [ ] `원격 데스크톱 클라이언트에서 한국어 키 처리 끄기`(항목 5)를 끄면, 그 앱에서도 F-16 규칙이 정상 평가된다.
- [ ] ⭐ **K5(이슈 #73)** — `Korean` 탭에서 기본 제외 목록 12종이 **보인다**. 오버라이드 부재 시 기본 목록이 그대로 편집기에 채워진다.
- [ ] ⭐ **K5** — 행을 하나 추가·제거·변경하면 `korean.excludedBundleIds` 가 저장되고, 게이트가 즉시 새 목록으로 바뀐다(부재 → 오버라이드 굳기).
- [ ] ⭐ **K5** — `기본 목록으로 되돌리기` 를 누르면 오버라이드 키가 **삭제**되고(부재 = 기본), 편집기가 기본 12종으로 다시 채워진다.
- [ ] ⭐ **K5** — 오버라이드를 전부 지우면(빈 배열) 어떤 앱에서도 한국어 게이트가 걸리지 않는다 — 빈 배열은 "아무 앱도 제외 안 함"이라는 명시적 값이다.
- [ ] ⭐ **K9** — 옵션을 켜고 `option`+`A` 를 누르면 `a`(소문자)가 입력된다(한국어 입력기에서 한글로 깨지지 않는다).
- [ ] ⭐ **K9** — `⌘`+`C`·`⌃`+`C`·caps lock+`A` 를 눌렀을 때 K9 이 개입하지 않는다(앱 단축키·대문자 의도 보호).
- [ ] ⭐ **K9** — 옵션이 꺼져 있으면(기본) modifier+문자 조합은 기존 동작 그대로다.
- [ ] F-16.2·F-16.3 은 §3.2 실측 전까지 **UI 에서 dimmed 이고, 설정 파일에 켜져 있어도 발화하지 않는다.** ⭐ **정정(2단계, D-K14)** — 이 기준은 §3.2 의 keycode 가 근거 3중으로 해소되어 **달성 완료**다. 두 항목은 이제 활성 규칙이다.
- [ ] F-16.3 은 앱 제외 조건과 한국어 입력기 활성 조건이 **둘 다** 성립할 때만 발화한다(§3.1 정정 사항).
- [ ] 한국어 입력기 변경 알림이 아직 도착하지 않아 판정 불가 상태일 때, F-16.3 은 발화하지 않고 F-16.4 는 원래 키를 통과시킨다(fail-closed, §3.3).
- [ ] `Shift + caps lock = caps lock`(F-08.10)과 F-16.1 을 동시에 켜고 caps lock+shift+space 를 누르면 F-08.10 이 결정론적으로 이긴다(§3.4 표).
- [ ] 자동 테스트: v1.20/v1.62 회귀 테스트가 있는 `ultrakey-core` `arbitration` 테스트에 F-16 규칙 4종의 중재 시나리오를 추가한다. 특히 §3.4 표의 4개 조합.
- [ ] `Korean` 탭의 모든 문자열이 `ko`·`en` 양쪽 카탈로그에 존재한다(누락 시 §5 의 혼합 언어 표시가 난다).
