# 이슈 #76 — Seek 검색창 한국어(IME) 입력 지원 — 설계 초안 + 작업 분해

> **성격**: `docs/plan/` 은 구현 위임 전 **계획 문서**를 두는 자리다. 이 문서는 중급(계획 초안)이 작성한 **초안**이며, 확정은 상급(호출 세션)의 리뷰 후 이루어진다. 리뷰가 끝나면 "결정 목록(D1~D6)"이 정본이 되고, §5 의 명세 갱신 초안이 `docs/spec/` 에 반영된 뒤 구현이 위임된다.
>
> **범위 제약**: 한글 조합 입력(자모 결합) 자체의 구현, 검색창을 `<input>` 으로 교체하는 재설계, F-02 검출 파이프라인의 한국어 OCR 언어 추가 — 전부 이 문서의 범위 밖(기각/후속으로만 언급한다).

---

## 1. 요약

실기기 피드백(2026-09-01)의 두 문제 — **① Seek 검색창에서 한국어 입력이 안 됨, ② 한/영 전환키가 세션 중 동작하지 않음** — 중 이번 작업이 해결하는 것은 **②** 다. 근본 원인은 코드 실측으로 확정되어 있다: 세션 중 모든 키가 계층 1 게이트(`arbitration.rs:340-347`)에서 `Consume` → `Effect::SeekKey` 로 라우팅되어, 한/영 키(`KeyCode::JIS_KANA` = `0x68`)도 예외 없이 소비되기 때문이다. **①(한글 조합)은 `canBecomeKey = false`(overlay-searchbar.html:84-90)와 IME 조합 버퍼 부재(seek.rs:411-491)로 원리적으로 불가능하며, 이번 범위에서 해결하지 않는다** — 옵션 B(입력 필드 교체)는 §1 의 핵심 제약(하위 앱 포커스 유지)과 정면 충돌하고, Rust 쪽 한글 IME 재구현은 대형 작업이라 별도 이슈로 분리한다.

**결정 요지**: 계층 1 게이트에서 **한/영 키(`0x68`)만 원본 이벤트 그대로 통과(Pass)** 시킨다. macOS 가 원본 키를 받아 입력 소스를 전환한다. KeyDown/KeyUp/FlagsChanged 어느 모양으로 도착해도 통과시킨다(도착 형태는 `(미확정)` — korean-input.md §3.2). 한자 키(`0x66`)는 통과하지 않는다. 세션 중 다른 키의 소비는 그대로 유지한다. 변경 파일은 `arbitration.rs` 1곳 + 명세 2~3곳이며, 새 플랫폼 API·새 크레이트·UI 변경이 없다.

---

## 2. 결정 목록 D1~D6

### D1 — 옵션 분기: **A(한/영 키만 계층 1 통과)를 채택한다. B(IME 가능한 입력 필드로 교체)는 기각한다**

**결정**: 이슈 #76 본문이 제시한 두 옵션 중 **A** 를 채택한다. 세션 중 한/영 키(`0x68`)만 계층 1 게이트에서 통과시켜 macOS 의 기본 입력 소스 전환을 복구한다.

**근거**:
- 피드백의 두 문제 중 **②(한/영 전환키)는 옵션 A 로 즉시 해결**된다. 한/영 키는 macOS 에서 입력 소스 전환 키 자체이므로, 원본 이벤트를 하위 앱(포커스는 오버레이가 뺏지 않았으므로 원래 앱에 그대로 있음)에 전달하면 macOS 가 전환을 처리한다. F-16.2(`space`+control 치환)를 거칠 필요가 없다.
- **①(한글 조합)은 옵션 B 로도 해결되지 않는다.** B 의 전제는 "실제 IME 가능한 입력 필드로 교체"인데, 이는 `canBecomeKey = false`(seek-overlay-ui.md §1 의 **가장 중요한 요구사항** — 하위 앱 포커스 유지)를 뒤집어야 한다. `canBecomeKey = true` 로 바꾸면 오버레이가 키 윈도우가 되어 하위 앱이 포커스를 잃고, §1 의 핵심 제약이 무너진다. `canBecomeKey = false` 를 유지한 채 IME 를 쓰려면 Rust 쪽에서 한글 자모 결합 엔진을 직접 구현해야 하는데, 이는 "한글 IME 재구현" 수준의 대형 작업이다.
- **Seek 의 검색 대상 특성상 한글 조합의 가치가 낮다.** Seek 는 화면 텍스트(OCR + AX)를 쿼리해 클릭하는 기능이다. 화면의 코드·URL·UI 라벨·문서 제목은 대부분 영문/로마자다 `(추정 — 근거: 개발자 포스트의 사용 예시가 전부 영문이고, F-02 의 OCR 언어 목록이 UI 로케일에서 계산된다는 seek.rs:498-499 의 주석. 한글 화면 텍스트 검색 수요의 크기는 실측되지 않았다)`. 한글 조합을 지원하려면 F-02 검출 파이프라인의 OCR 언어에 `ko` 추가까지 따라붙어 범위가 더 커진다.
- **옵션 A 의 비용이 극히 작다.** 변경은 `arbitration.rs` 계층 1 게이트의 분기 하나 + 단위 테스트다. 새 플랫폼 API·새 크레이트·UI 변경·설정 항목이 없다.

**기각한 대안**:

| 대안 | 기각 사유 |
| :--- | :--- |
| **B — 검색 입력을 실제 IME 가능한 텍스트 입력 필드로 교체** | `canBecomeKey = false` 와 정면 충돌(§1 핵심 제약 위반). `<input>` 을 두어도 키 윈도우가 될 수 없어 타이핑이 씹힌다(overlay-searchbar.html:84-90 주석이 이미 이 사실을 못박음). `canBecomeKey = true` 로 바꾸면 하위 앱 포커스 상실 — Seek 의 존재 이유(원래 작업 중이던 앱에 포커스 유지)가 무너진다. 게다가 IME 조합 버퍼는 macOS 가 키 윈도우에만 부여하므로, 필드 교체만으로는 한글 조합이 되지 않는다 |
| **B' — canBecomeKey=false 유지 + Rust 쪽 한글 자모 결합 엔진 구현** | "한글 IME 재구현" 수준의 대형 작업(초성/중성/종성 결합 규칙, 조합 버퍼 상태, Backspace 의 조합 단계 처리, 한국어 입력기 활성 판정과 원본 레이아웃 자모 읽기 — 현재 `resolve_typed_char` 는 ASCII 폴백 테이블을 쓰므로 자모 자체가 안 나온다). 이번 이슈의 피드백 ②(전환키)와는 무관한 별개 작업이다. 후속 이슈로 분리한다 |
| **A' — 세션 중 한/영 키를 F-16.2 규칙(space+control 치환)으로 라우팅** | F-16.2 는 계층 3 에 있고 세션 중에는 계층 1 이 먼저라, 라우팅하려면 계층 1 에서 F-16.2 규칙을 직접 호출하는 특수 경로가 필요하다. 그런데 F-16.2 의 출력(`space`+control)은 macOS 의 "입력 소스 선택" 단축키를 흉내내는 것일 뿐이고, 한/영 키 자체가 이미 입력 소스 전환 키다 — 원본 통과가 더 단순하고 결과도 같다. F-16.2 가 꺼져 있어도(기본 ☐) 통과는 동작해야 하므로, F-16.2 설정에 종속시키는 것은 오히려 결함이다 |

### D2 — 한글 조합 입력 자체는 **이번 범위 밖**으로 확정한다. 후속 이슈로 분리한다

**결정**: 이번 이슈는 "한/영 전환키 복구"로 범위를 한정한다. 한글 조합(자모 결합) 입력은 지원하지 않는다 — 세션 중 한/영 키로 입력 소스를 한국어로 바꾼 뒤 타이핑해도, `resolve_typed_char`(seek.rs:411-491)가 ASCII 폴백 테이블을 쓰므로 검색어에는 **영문자**가 들어간다. 이것은 이번 작업의 기대 동작이다.

**근거**:
- 한글 조합을 지원하려면 D1 의 기각 대안 B' 가 요구하는 전부(자모 결합 엔진 + 조합 버퍼 + 원본 레이아웃 자모 읽기)가 필요하다. `ultrakey-layout` 의 `char_for` 는 `forward` 맵 조회일 뿐이고, 한국어 입력기 활성 시에는 `used_ascii_fallback` 이 true 가 되어 **ASCII 폴백 레이아웃(US)의 테이블**이 게시된다(lib.rs:206-210, F-14 §3.2.2 (i) — ASCII 불가 소스를 폴백으로 교체). 즉 현재 구조에서는 한국어 입력기 활성 상태에서도 자모가 나오지 않는다.
- 한글 조합을 지원하려면 F-02 검출 파이프라인도 한국어 후보를 찾을 수 있어야 한다(OCR `recognitionLanguages` 에 `ko` 추가 여부 — seek.rs:498-499). 이는 F-02 명세·구현의 별도 변경이다.
- **범위를 한정해도 피드백의 핵심 불만(② 전환키)은 해결된다.** ①(한글 입력)은 후속 이슈에서 "한글 조합 엔진"을 별도로 설계할 때 다룬다. 이 문서 §6 리스크에 후속 이슈의 설계 전제를 남긴다.

**기각한 대안**:
- **이번에 한글 조합까지 구현**: D1 기각 대안 B' 와 같은 근거. 작업량이 3~4배로 늘고, F-02·F-14·세션 상태 머신을 동시에 건드려 리뷰·검증 단위가 무너진다. "전환키 복구"라는 작고 완결적인 문제를 먼저 닫는 것이 이 저장소의 증분 위임 관례(명세 1개 = 위임 1건)와 맞는다.

### D3 — 통과 방식: **원본 이벤트를 그대로 Pass 한다. KeyDown/KeyUp/FlagsChanged 어느 모양이든 통과시킨다**

**결정**: 계층 1 게이트에서 `ev.keycode == KeyCode::JIS_KANA` 이면 `Outcome::pass(Layer::SeekSession)` 을 반환한다. `normalize_kind` 로 환원된 kind 가 아니라 **원본 `ev.kind` 를 그대로** 통과시킨다 — `Outcome::pass` 는 이벤트를 소비하지 않으므로 원본 이벤트(KeyDown 이든 FlagsChanged 이든)가 그대로 하위 앱으로 전달된다.

**근거**:
- 한/영 키의 도착 형태는 `(미확정)`(korean-input.md §3.2 — "CGEventTap 에 어떤 이벤트 종류로 도착하는지(KeyDown 인지 FlagsChanged 인지)는 여전히 확인되지 않았다"). korean-input.md §3.2 의 결정("도착 이벤트 종류를 가정하지 않는다")을 그대로 따른다 — **원본 통과는 어느 모양으로 도착해도 macOS 의 기본 처리에 맡기므로 안전하다.** KeyDown 으로 오면 macOS 가 입력 소스 전환으로 처리하고, FlagsChanged 로 오면 역시 그렇게 처리한다 `(추정 — macOS 의 한/영 키 처리 경로. 어느 쪽이든 원본을 그대로 보내는 것이므로 우리가 가정을 세울 필요가 없다)`.
- **KeyUp 도 통과시켜야 한다.** KeyDown 만 통과시키고 KeyUp 을 소비하면 하위 앱이 눌림 상태를 놓치거나, 반대로 우리가 소비한 KeyUp 이 남아 상태 불일치가 생길 수 있다. 한/영 키는 모멘터리 키라 down/up 이 한 쌍으로 처리되어야 한다.
- **자동 테스트가 두 모양을 모두 재현한다** — korean-input.md §3.2 가 세 사고(M1 FlagsChanged 유실, PR #23 modifier 출력)의 재발 방지로 못박은 절차다.

**기각한 대안**:
- **환원된 kind(KeyDown)만 통과**: `normalize_kind` 는 FlagsChanged 를 down/up 으로 환원하지만, 통과시킬 때 환원된 kind 로 새 이벤트를 만들면 원본 이벤트 모양이 바뀐다. 원본을 그대로 보내는 것이 macOS 처리에 가장 안전하다.
- **KeyDown 만 통과, KeyUp 은 소비**: 위 근거. stuck modifier 류 상태 불일치 위험.

### D4 — 한자 키(`0x66` = `JIS_EISU`)는 **통과시키지 않는다. 소비 유지**

**결정**: 예외는 한/영 키(`0x68`) 하나뿐이다. 한자 키(`0x66`)는 세션 중 계속 `Consume` → `SeekKey` 로 라우팅된다.

**근거**:
- 한자 키는 IME 조합 중 한자 변환을 트리거하는 키다. 세션 중에는 IME 조합 버퍼가 없으므로(이번 범위 밖, D2) 한자 키가 통과되어도 의미가 없다. 통과시키면 하위 앱에 도달해 예상치 못한 동작(예: 조합 중이던 하위 앱 텍스트의 한자 변환)이 일어날 수 있다.
- 이슈 #76 피드백도 한/영 키만 언급한다. 범위를 피드백이 요구한 것에 한정한다.
- JIS 키보드 사용자의 `英数` 키(같은 `0x66`)도 세션 중 소비된다 — 이는 기존 동작 그대로다.

### D5 — 세션 중 통과는 **F-16.2 설정·앱 제외 게이트와 무관하게 항상 동작**한다

**결정**: 세션 중 한/영 키 통과는 F-16.2(`한/영 키로 입력 소스 변경`, 기본 ☐)가 꺼져 있어도 동작한다. F-16.2 의 앱 제외 게이트(원격 데스크톱 클라이언트, korean-input.md §3.5)도 세션 중 통과에는 적용하지 않는다.

**근거**:
- F-16.2 는 "한/영 키를 `space`+control 로 치환해 입력 소스 전환"을 재현하는 기능이다. 세션 중 통과는 원본 키를 그대로 보내 macOS 가 직접 전환하게 하는 것 — **결과 동작(입력 소스 전환)이 같다.** F-16.2 가 꺼져 있어도 macOS 의 기본 한/영 키 동작은 살아 있으므로, 통과는 F-16.2 설정에 종속될 이유가 없다.
- **원격 데스크톱 앱에서 세션 중 통과는 오히려 올바른 동작이다.** korean-input.md §3.5 의 제외 기준은 "키 입력을 이 맥의 입력 스택이 아니라 다른 OS·다른 세션의 입력 스택으로 그대로 전달하는 앱"이다 — 원격 세션 안의 입력기는 **대상 시스템**이 처리해야 한다. 세션 중 원본 한/영 키를 통과시키면 정확히 그렇게 된다. F-16.2 의 치환(space+control)을 세션 중에 적용하면 오히려 대상 시스템에 원래 키가 도달하지 못한다.
- **회귀 위험 최소화**: F-16.2 의 계층 3 규칙·앱 게이트·설정 저장은 전혀 건드리지 않는다. 세션 밖 동작은 완전히 기존 그대로다.

**기각한 대안**:
- **세션 중 통과를 F-16.2 설정에 종속**: F-16.2 가 꺼져 있으면(기본) 한/영 키가 다시 소비되어 피드백 ②가 재발한다. "기본 설정에서도 동작해야 하는 macOS 기본 키"를 설정에 종속시키는 것은 잘못된 방향이다.
- **세션 중 통과에 F-16.2 앱 제외 게이트 적용**: 위 근거 — 원격 데스크톱에서 통과가 오히려 정답이다. 게이트를 적용하면 원격 세션 안에서 한글 입력이 불가능해진다(§3.5 가 막으려던 바로 그 문제).

### D6 — 명세 갱신 범위: **`seek-activation-and-session.md`(필수) · `seek-overlay-ui.md`(필수) · `korean-input.md`(선택)**

## 7. 상급 리뷰 요청 사항

1. **D1 의 옵션 A 채택** — 옵션 B(입력 필드 교체) 기각이 타당한가. 특히 "한글 조합은 이번 범위 밖"이라는 범위 한정이 피드백 ①을 남겨 두는 것에 대한 판단.

### ⚠️ 구현 시 고정할 것 (리뷰가 지목)

- 계층 1 게이트의 한/영 예외 분기는 `ev.kind.is_key()` 통과 판정 **뒤**에 둔다(마우스 통과와 겹치지 않게).
- 한자 키(`0x66`)는 예외가 아니다 — 계속 `Consume` → `SeekKey`(T5 로 고정).
- 세션 중 다른 키(`ANSI_A` 등)는 여전히 `Consume` + `SeekKey`(T4 로 고정).
- T3(FlagsChanged) 는 korean-input.md §3.2 의 "두 모양 모두 재현" 절차를 그대로 따른다.
