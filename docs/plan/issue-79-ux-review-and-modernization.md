# 이슈 #79 — UI/UX 전문 리뷰 에이전트 + 전체 UI/UX 현대화 — 계획 초안

> **성격**: `docs/plan/` 은 구현 위임 전 **계획 문서**를 두는 자리다. 이 문서는 중급(계획 초안)이 작성한 **초안**이다. 확정은 상급(호출 세션) 리뷰 → 반영 순서로 이루어진다. 확정 후 이 문서의 "결정 목록(D1~Dn)"이 정본이 되고, §3 의 단계가 위임 순서가 된다. 리뷰 과정에서 바뀌면 D 번호는 그대로 두고 근거를 갱신한다.
>
> **정본 흐름**: 초안(중급, 이 문서) → `ultrakey-review`(상급, Qwen3.8 Max) → 호출 세션 확정 → 실행.

---

## 1. 요약

이슈 #79 는 ① **UI/UX 를 전문적으로 리뷰하는 서브에이전트 신설**과 ② 그 리뷰를 받아 **현대적 macOS 앱 표준으로 전체 UI/UX 를 개선**하는 두 개의 작업을 **하나의 업무 태스크**(이 이슈 그 자체)로 묶는다. ⚠️ 핵심 제약은 세 번째 요구다 — **원본 SuperKey/HyperKey 의 UI/UX 모사 가정을 금지**하며, 클론을 **독립적인 앱**으로서 발전시키는 방향으로만 요구사항을 만든다.

산출물은 세 가지다:

| 산출물 | 위치 | 내용 |
| :--- | :--- | :--- |
| **에이전트 파일** | `.opencode/agent/ultrakey-uxreview.md` (신규) | UI/UX 리뷰 전용 서브에이전트. **중급(Effort High)** 모델을 쓴다 (D1) |
| **요구사항 문서** | `docs/plan/issue-79-ux-requirements.md` (신규) | 현재 UI 전수 리뷰 결과 + 현대화 요구사항. **리뷰가 끝난 뒤 이 계획과 별도로** 에이전트가 산출한다 (D2) |
| **명세 반영** | `docs/spec/preferences-ui.md` 갱신 + 기타 UI 명세 | 요구사항에서 확정된 것만 명세로 승격 (D3·D4) |

이 초안이 세운 작업 분해 요지: **에이전트 도입 → 전수 리뷰 → 요구사항 확정 → 명세 갱신 → 1차 현대화 구현(이슈 #79 로 PR) → 제품 개선·창 틀 교체(별도 이슈)**. 범위 제어로 1차 현대화는 **시각·인터랙션 체감**에 한정하고, 제품 기능(설정 항목 추가·삭제·재배열)과 네이티브 창 틀 교체는 후속으로 미룬다 (D5).

이 초안을 만들며 확정한 사실 근거는 §3 조사 표에 있고, 갈림길(에이전트 모델 등급·요구사항 분류·범위 컷)의 권장안과 기각 대안은 각 D 에 남겼다.

## 2. 결정 목록 D1~Dn

### D1 — UI/UX 리뷰 에이전트: **중급(Effort High) 모델, 읽기 전용, `ultrakey-uxreview`**

**결정**: `.opencode/agent/ultrakey-uxreview.md` 신설. 모델은 **`alibaba-token-plan/deepseek-v4-flash-0731` + `options.reasoningEffort: "high"`**(중급·구현과 같은 모델). `permission: edit: deny`(읽기 전용), `bash: allow`(검증·조회만). description 은 "UI/UX 리뷰 전용"으로 좁힌다. 폴백 2순위 `qwen3.8-flash` 는 설정에 고정하지 않는다(기존 에이전트들과 같은 관례).

**근거**:
- **속도 우선 운용 원칙(AGENTS.md §2)** 에 따른다 — "기본 작업은 중급 모델부터 시작"·"빠른 중급 모델이 반복해서 결과물을 뽑아내고, 상급 모델의 사용량은 최소로 제한". UI/UX 리뷰는 **반복 작업**(탭→에이전트→요구사항→명세→구현 초안이 각 단계에서 산출물을 리뷰·교정)이라 중급이 주체가 맞다.
- **리뷰 성격 분석**: UI/UX 리뷰가 요구하는 것은 ① 스크린샷·마크업·CSS 를 읽는 시각 판단 ② macOS HIG·모던 앱 관례 지식 ③ 요구사항 문서로의 조직화다. 이것은 deepseek-v4-flash 의 강점 영역이며(시각 자산의 이미지 이해 + 문서 조직), "중급이 초안을 잡고 상급이 교정" 하는 전체 라우팅 구조와 정확히 같은 분업이 된다.
- **경계 (기존 `ultrakey-review` 와의 분업)**: `ultrakey-review` 는 **상급·평가자** — 중급이 낸 계획·구현 산출물의 **결함 판정**을 목적으로 호출한다(디자인 리뷰를 하지 않는다). `ultrakey-uxreview` 는 **중급·생산자** — 리뷰 그 자체를 산출물로 만드는 주체다. 즉 "디자인 리뷰"와 "코드 리뷰"의 구분이 아니라 **"산출물을 생산" vs "산출물을 판정"** 의 구분이다. uxreview 의 산출물도 계획/구현 산출물이므로, 검증이 필요하면 `ultrakey-review` 가 리뷰한다.

**기각한 대안**:
- **상급(qwen3.8-max)**: 리뷰가 "한 번 최대로" 하면 된다면 상급이 맞지만, 반복 작업을 상급에 돌리면 속도 원칙에 어긋난다. 그리고 상급은 평가자 역할로 **유보**해야 한다 — 이 작업의 최종 확정(요구사항 채택)과 주요 갈림길 리뷰에 상급을 남겨 둔다. (초안 요청 문의 "리뷰 성격상 어느 쪽이 맞는지" → **중급**이 맞다.)
- **uxreview 를 별도 에이전트 파일로 만들지 않고 기존 plan 에 역할로만 추가**: description 에서 역할을 넓히면 plan 에이전트의 초점이 흐려진다(계획 초안 vs UI 리뷰는 위임 주체가 다르다 — 헤드리스 세션에서 호출 대상이 달라져야 한다).
- **모델 없이(현재 세션 하급)**: 전수 리뷰는 문서·HTML·스크린샷을 가로질러 비교·판단해야 해 하급(Effort Low)의 출력으로는 요구사항 품질이 나오지 않는다.

### D2 — 리뷰 방법론: **"현재 실측 전수 조사 → 현대 macOS 표준과 대조 → 갈라짐 3분류" 후 요구사항만 남긴다**

**결정**: `ultrakey-uxreview` 에게 아래 절차를 시킨다 (프롬프트 초안 §4).

1. **전수 실측 (1단계)**: `settings.html` 6탭 전부(DOM·CSS 클래스·`applyStrings()` 배선)·`index.html`(권한 온보딩)·`overlay-searchbar.html`·`overlay-highlight.html`·`eventviewer.html`·트레이 메뉴의 현재 상태를 **탭/화면별로 적는다**. 문자열 카탈로그 5언어(`resources/i18n/{en,ko,zh,es,ja}.json`)에서 **탭·화면별 사용 키를 추출**해 "현재 어떤 문구가 어느 화면에 있는가"의 목록을 만든다. **스크린샷 촬영은 하지 않는다** — `docs/research/screenshots/` 의 v1.66 5장은 **원본 비교용**이지 현재 UI 의 실측이 아니다(현재 UI 는 소스가 정본).
2. **현대 macOS 표준과 대조 (2단계)**: macOS HIG(모달시트·설정 UI 관례·컬러/타이포그래피/간격·`prefers-color-scheme`)와 Material(Seek 검색 UX)·모던 macOS 유틸리티(레이아키·알프레드·RectPro 등)의 관례를 **정성적 기준**으로 대조한다. ⚠️ **새 웹 조사를 요구하지 않는다** — 이 저장소의 "원본 실측이 사실의 근거" 원칙이 웹 조사보다 무겁고, HIG 대조는 지식 기반 판단으로 충분하다. 근거 없는 새 사실은 요구사항에 싣지 않는다.
3. **갈라짐 3분류 (3단계)**: 조사 결과를 세 통으로 나눈다 — ① **현대화(1차 범위)**: 시각·인터랙션 체감 개선(컬러·타이포·간격·포커스·애니메이션·컨트롤 스타일) ② **제품 개선(후속)**: 기능·구조 변경(설정 항목 재배열·새 설정 추가·창 크기 재결정 등) ③ **유지(불변)**: D5(단일 고정 크기)·원본 실측 기록 보존. ③은 리뷰가 "바꾸고 싶다"로 분류해도 **우리 규약과 충돌하므로 후속·재판정 대상으로** 넘긴다.
4. **요구사항 문서 산출 (4단계)**: `docs/plan/issue-79-ux-requirements.md` 에 **요구사항만** 남긴다 — 조사 과정 기록은 문서에 남기지 않는다(이 저장소의 원칙: 근거만 남기고 과정을 나열하지 않음). 각 요구사항은 **수용 기준**(눈으로 확인 가능한 항목)을 붙인다.

**근거**:
- 리뷰가 "원본과의 차이"가 아니라 "독립 앱으로서의 품질"을 기준으로 해야 한다는 이슈 요구 ③에 맞춘 절차다 — 원본 스크린샷은 **비교 대상이 아니라 오염원 방지용 참고**로만 쓴다(§2 D1 "비교 대상으로만 사용" 이슈 고려사항).
- ④에서 과정을 버리는 이유: `docs/plan/` 의 전례로 이 문서(issue-47)는 "현재 구성 조사 — 검증 완료" 표만 남기고 조사 방법을 본문에 두지 않는다.

**기각한 대안**:
- **원본 UI 캡처와 나란히 배치 대조 → "원본과 다른 것 = 개선 후보"**: 이슈 요구 ③과 정면으로 충돌하는 방법이다 — 원본과 같아지게 만드는 방향을 유도한다.
- **웹 조사 기반(HIG 공식 문서·모던 앱 스크린샷 링크 수집)**: 이 저장소의 사실 계층에서 웹 조사는 원본 실측보다 약하다. 또한 컨텍스트 오염(여러 출처 덤프)이 생긴다. 지식 기반 대조로 충분하다.

### D3 — 명세 반영: **요구사항 문서와 `preferences-ui.md` 를 동기화하고, 요구사항에서 우선순위를 잰다**

**결정**: `issue-79-ux-requirements.md` 의 각 요구사항을 **우선순위(P0~P2)** 와 **명세 연동 여부**로 태그한다.

- **시각·인터랙션 요구사항 전부**는 `preferences-ui.md` §3.1(탭 구조)·§3.2(컨트롤 카탈로그)·§3.4(접근성)·§3.8(종속 표현)에 **인라인 반영**(컨트롤 추가가 아니라 스타일·동작 규약 확장)한다.
- **제품 개선 요구사항**은 기존 기능 명세(F-01~F-17)에 각각 귀속시킨다.
- ⚠️ **단일 고정 크기 창**(D5) · 종속 표현 3종(F-09 §3.2·§3.8) · 저장 규약(F-15) · i18n 5언어 키 구조(F-14)는 **전면 고정 제약**으로 요구사항 문서에 명시 — 리뷰가 "재설계 대상"으로 분류해도 바꾸려면 이 계획의 별도 갈림길(D9)에서 판정한다.

**근거**:
- `preferences-ui.md` 는 "창의 골격"·"컨트롤 타입 카탈로그"를 정의하는 문서다. 시각 스타일 변경은 골격이 아니라 그 카탈로그의 **속성(컬러·간격·타이포)** 변경이라, 전면 재작성 없이 §3.2·§3.4 의 확장으로 반영하는 것이 기존 결정과의 충돌을 최소화한다.
- 갈라짐 원칙(README "기준 3: 기존 명세의 규약 위에 선다")에 의한 우선순위 배치다.

**기각한 대안**:
- **전용 "design-system.md" 신설 후 F-09 가 참조**: 현재 카탈로그가 41개 컨트롤·종속 표현 3종의 정본이고, 스타일 변경이 전면 재작성이라면 별도 문서가 좋다. 그러나 1차 범위가 "개별 컨트롤 스타일 개선"이라 (명세 구조를 바꾸지 않는) 인라인 확장이 비용이 낮고, 필요 시 후속에서 design-system 문서로 승격한다.

### D4 — 요구사항 문서 위치·형태: **`docs/plan/` 계열, `issue-79-ux-requirements.md`**

**결정**: 요구사항은 `docs/plan/issue-79-ux-requirements.md` 에 둔다. `docs/plan/` 의 기존 문서 3건(`issue-46`·`issue-47`)이 구현 위임 전 **계획**을 두는 자리라는 관례를 따른다. 문서의 마지막 절에는 "확정 후 명세 반영 → 구현 위임" 순서와 우선순위 태깅 규칙을 고정한다. ⚠️ **에이전트가 이 문서를 직접 쓰게 한다** — `ultrakey-uxreview` 의 산출물이 바로 이 파일이다.

**근거**: 요구사항은 명세(`docs/spec/`)의 상위 단계(어떤 명세를 만들어야 하는가)이므로, `docs/spec/` 에 넣으면 명세와 역할이 겹친다. `docs/plan/` 이 계획 단계 산출물의 자리이므로 거기에 둔다. (기존 `issue-46`·`issue-47` 의 산출물은 명세 갱신으로 직접 승격되었으나, 이번은 **범위가 더 크고 우선순위 결정이 필요**하므로 별도 문서가 정본이 된다.)

**기각한 대안**:
- `docs/spec/` 에 넣기: 위 근거. 요구사항 문서(무엇을 바꾸는가)를 "정본 명세와 동등"으로 두면 갱신 경로가 모호해진다.
- `docs/` 루트에 넣기: 루트 문서는 이미 `doc*` 계열(목차·아키텍처·검증)만 있고, 프로젝트는 계획을 `docs/plan/` 에 두는 관례를 만들었다. 관례에 합치시킨다.

### D5 — 범위 제어: **1차 = 시각·인터랙션 체감, 2차 = 제품 개선, 3차 = 창 틀 교체(재판정)**

**결정**: 현대화 작업을 세 층으로 나누고, **1차 구현은 "시각·인터랙션 체감 개선"** 에만 국한한다.

| 층 | 내용 | 구현 주체 | 판정 권 |
| :--- | :--- | :--- | :--- |
| **1차 — 1현대화** | CSS 시각(컬러·타이포·간격·포커스·transition·호버) · 컨트롤 스타일(체크박스·select·버튼·슬라이더) · 트레이 메뉴/온보딩/오버레이 일관성 · 시각 접근성(대비) | `ultrakey-implement` | 상급 → 이슈 #79 PR |
| **2차 — 제품 개선** | 설정 항목 추가·삭제·재배열 · 새 정보 아키텍처 · 창 크기·위치 영속 재조정 | 명세 후속 갱신(F-xx) → 구현 | 상급 → 별도 이슈(들) |
| **3차 — 창 틀 교체** | `decorations`·`transparent`·새 타이틀바·SF Symbols 전면 적용 등 **Tauri 창 틀 수준** 변경 | 별도 스파이크 후 판정 | 상급 |

**근거**:
- 1차는 **DOM/컨트롤 구조를 바꾸지 않으므로** 기존 테스트(컨트롤 배선·카탈로그 키 집합·i18n 검사)를 거의 그대로 통과한다 — 증분이 작고 회귀 위험이 낮다. CSS 변경은 i18n 키 0 개·저장 키 0 개·컨트롤 0 개를 전제하므로 기존 회귀 장치(`frontend_wiring.rs` 등)에 영향이 없다.
- 2차(항목 재배열·추가)는 F-09 수용 기준·기능 명세 §4 표·여러 테스트가 건드리는 곳이라 명세 갱신이 반드시 선행되어야 한다. 1차와 분리한다.
- 3차(창 틀 교체)는 `overlay-searchbar` 가 쓰는 `transparent: true` 설정(기존에 검증됨)과 창 생명주기 로직(F-09 §3.3)까지 건드려 **별도 스파이크가 필요**하다.
- "1차 현대화"의 완료 정의는 §7 실기기 확인 항목 — 스크린샷 6개(6탭/라이트/다크 각 1)를 사용자가 직접 봐서 **"이전보다 현대적이다"** 가 판정 기준이다.

**기각한 대안**:
- **전면 재설계 (한 PR 로)**: 6탭 + 5개 화면 + 창 틀 전체를 한 번에 바꾸면 리뷰·검증이 불가능한 증분이 된다. 이 저장소의 관례(기능 단위 위임·작은 증분)와 어긋난다.
- **"현대화" 를 창 틀 교체로만 정의**: 창 틀(SF Symbols·decorations)은 체감 반전의 핵심이지만 **스파이크가 필요**하고, WebView 가 네이티브 틀과 어긋나는 방식으로 구현되면 오히려 위험하다. 우선 1차(안전) → 3차(스파이크 후) 순서.

### D6 — 기존 결정과의 충돌 처리: **"갈라짐" 이 아니라 "이탈" → 전면 고정 제약 4종 + 재판정 절차**

**결정**:
1. **`docs/research/screenshots/` 의 v1.66 실측 기록은 지우지 않는다** (README "갈라짐 표" 원칙 그대로 — 지우는 것이 아니라 "우리는 다르게 간다"를 옆에 붙인다).
2. 리뷰에서 "D5(단일 고정 크기)를 바꾸고 싶다" 가 나오면 **요구사항 문서에 후속 태그**로 남기고, 2차 이후에 **별도 갈림길(D9)** 로 판정한다 — 이 계획에서는 "바꾸지 않는다"가 기본.
3. i18n 5언어가 걸리는 작업(새 설정 항목·문구 추가)은 **전수 리뷰에서 "영향"으로 표기만**하고 1차에서는 건드리지 않는다. (D5 근거 — 1차는 문자열 카탈로그를 건드리지 않는다.)

**근거**: README 갈라짐 판정 기준 1 ~ 3("원본에 있는 것을 다르게 만드는 것은 갈라짐이 아니라 이탈"·"사용자가 명시적으로 요구했을 때만").

**기각한 대안**: "D5 를 이슈 #79 에서 직접 뒤집는다" — 사용자가 D5 를 결정한(이슈 #32) 전례가 있고, 이번 이슈는 "현대화"를 요구했지 "단일 고정 크기를 바꿔라"를 요구하지 않았다. 재결정은 별도 판정이 필요하다.

### D7 — i18n 5언어 영향: **1차 = 카탈로그 무변경, 요구사항 작성 = "새 문자열" 검토 항목**

**결정**:
- 1차는 문자열 카탈로그(`resources/i18n/{en,ko,zh,es,ja}.json`)를 **바꾸지 않는다** — i18n 은 5개 파일·키 집합 일치·위치 인자 검사에 걸려 있어 한 파일만 바꿔도 테스트가 깨진다(알려진 장치).
- 요구사항 문서에는 "현존하는 문자열 중 **번역 품질 이슈**(문맥·정확도) 또는 **새로 필요한 문구**" 섹션을 두어, 2차 이후에만 반영한다.
- ⚠️ **라벨 문구 변경**(예: "Hide menu bar icon" → 더 짧은 문구)은 1차가 아니라 2차(제품 개선)로 분류한다 — 문구 변경은 카탈로그 키·테스트 표면을 건드린다.

**근거**: D5 근거와 동일, 그리고 이 저장소의 i18n 테스트(`all_catalogs_*`·`frontend_wiring` 리터럴 검사)가 카탈로그 변경 시 즉시 잡아내는 장치를 역이용한다.

**기각한 대안**: "1차에서 라벨 톤 통일(문구 교정 포함)" — 기존에 확정된 키 집합을 건드리면 모든 탭 리뷰가 카탈로그 검사와 겹친다.

### D8 — 리뷰 순서: **우선순위 = 설정 창 > 온보딩 > 오버레이 > Event Viewer > 트레이**

**결정**: `ultrakey-uxreview` 가 리뷰하는 순서를 정한다 — 사용 노출 빈도·제품 핵심(키보드 앱의 "설정 체감") 순으로: ① `settings.html` (6탭 전부) ② `index.html` (권한 온보딩 — 신규 사용자가 처음 보는 화면) ③ `overlay-searchbar.html` (+ `overlay-highlight.html`) ④ `eventviewer.html` ⑤ 트레이 메뉴(네이티브 — 리뷰 가능 영역은 항목 구성·라벨뿐).

**근거**: Seek·Hyperkey 는 설정 없이는 동작하지 않고, 온보딩은 첫인상을 결정한다. 트레이 메뉴는 Tauri 네이티브라 CSS 적용이 불가능해 리뷰 항목이 제한된다(항목 구성·라벨·아이콘만).

### D9 — (재판정용) 단일 고정 크기 창: **이 계획에서는 "바꾸지 않는다" 기본, 후속 이슈로만 판정**

**결정**: D6 의 "재판정 절차"를 구체화한다 — 요구사항 리뷰가 D5 를 바꾸고 싶다는 갈림길을 남기면, `ultrakey-review` → 호출 세션이 **별도 이슈**로 분리한다(이슈 #79 PR 의 지연 사유가 되지 않는다).

## 9. ⭐ 상급 리뷰 반영 (2026-09-02, `ultrakey-review`)

> 판정: **조건부 통과.** 아래 수정을 반영한다.

### 리뷰 판정 요지

**D1(에이전트 모델 등급: 중급) — 승인.** 이 에이전트는 "리뷰"라는 단어와 달리 요구사항 문서라는 **산출물을 생산**하는 주체이고, 채택 확정은 호출 세션 + `ultrakey-review` 가 한다 — AGENTS.md §2 의 "중급 = 생산, 상급 = 평가자·사용량 최소" 분업과 정확히 일치. 반복 작업(전수 리뷰 → 요구사항 → 명세 → 구현 리뷰)을 상급에 올리면 속도 원칙에 어긋난다. 모델 ID(`alibaba-token-plan/deepseek-v4-flash-0731` + effort `high`)는 기존 중급 정의와 일치. `ultrakey-review`(판정)와의 분업 경계 서술("산출물 생산 vs 산출물 판정")도 명확.

**② "원본 UI 모사 가정 금지" 반영 — 확인됨(1곳 강화).** §4 프롬프트 ⛔ 조항 · D2 3분류 ③유지 · D3 전면 고정 제약 · D6(실측 기록 미삭제 + 재판정 절차)에 반영되어 있으나, "스크린샷은 참고" 문구는 오히려 참고를 허용하는 방향으로 읽혀 모사 금지와 어긋날 여지가 있다 → 아래 2 번으로 강화.
