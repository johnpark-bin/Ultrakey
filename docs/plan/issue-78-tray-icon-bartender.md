# 이슈 #78 — 트레이 아이콘이 Bartender 환경에서 반복적으로 사라졌다 나타난다 — 계획 초안

> **성격**: `docs/plan/` 은 구현 위임 전 **계획 문서**를 두는 자리다. 이 문서는 중급(계획 초안)이 작성하고 상급(호출 세션)이 리뷰·교정해 **확정**한 판이다. "결정 목록(D1~Dn)"이 정본이고, §3 의 작업 분해가 구현 위임(`ultrakey-implement`)의 지시서다.
>
> **상태**: 초안. 상급 리뷰(`ultrakey-review`) 대기.

---

## 1. 요약

**결론부터**: 이 현상은 **우리 코드가 유발하는 "아이콘 재생성" 패턴이 아니다.** 코드 조사와 `tray-icon` 0.24.2 macOS 구현 실측으로 다음이 확정됐다.

| 확인한 것 | 근거 |
| :--- | :--- |
| `TrayIcon`(NSStatusItem)은 부팅 시 **한 번만** 생성되고, 이후 **재생성·`set_icon` 호출이 전혀 없다** | `main.rs:5081-5137`(`setup_tray`), `set_icon` 호출 지점 0건(grep) |
| `set_visible` 은 **기본 상황에서는 호출되지 않는다** — 부팅 시 `hideMenuBarIcon == true` 일 때만(`main.rs:5126`), 토글 시(`main.rs:5621`) | `main.rs` + `menu-bar-and-lifecycle.md` §4(기본값 ☐) |
| `set_menu` 는 NSStatusItem 을 **유지한 채** 메뉴만 교체한다 — 아이콘 리페인트를 유발하지 않는다 | `tray-icon` 0.24.2 `platform_impl/macos/mod.rs:125-142` — `ns_status_item.setMenu(...)` 만 호출 |
| `set_visible(false)` 는 `NSStatusBar::removeStatusItem` 으로 **아이템을 완전히 제거**하고, `set_visible(true)` 는 **새 NSStatusItem 을 생성**한다 | `tray-icon` 0.24.2 `mod.rs:193-205` — `remove()` / `create()` 재호출 |

즉 **"우리가 아이콘을 다시 만들거나 숨겼다 보여주는" 경로는 기본 설정에서 존재하지 않는다.** 따라서 깜빡임의 원인은 (a) Bartender 가 NSStatusItem 을 숨기고 복원하는 과정에서의 상태 어긋남, (b) Bartender 의 메뉴바 공간 재배치, (c) `set_menu` 교체 시점과 Bartender 의 메뉴 추적이 겹치는 타이밍 문제 중 하나일 가능성이 높다 — **셋 다 Bartender 가 설치된 실기기에서만 재현·판정 가능하다.**

**이 계획의 핵심 판단**: 실기기(Bartender 설치)가 없으면 **원인 확정이 원리적으로 불가능**하다. 따라서 이 작업은 ① 실측 계측을 먼저 넣고(조사 단계), ② 실기기 재현이 가능해지면 원인을 확정한 뒤에만 수정에 들어가며, ③ 재현 불가 시 **수정 없이 문서화 후 연기**하는 3단 구조로 분해한다. "추정 수정"을 지금 넣는 것은 기각한다 — 근거가 없다.

## 2. 가설과 실측 절차 (D1~Dn)

### D1 — 원인 후보 가설 목록과 우선순위

| # | 가설 | 성격 | 근거 | 우선순위 |
| :--- | :--- | :--- | :--- | :--- |
| **H1** | Bartender 가 아이콘을 숨겼다 복원하는 과정에서 NSStatusItem 의 **상태(메뉴·아이콘)가 어긋난다** | Bartender 측 동작 | 우리 코드는 기본 상황에서 `set_visible`/`set_icon` 을 부르지 않으므로, 숨김·복원을 하는 쪽은 Bartender 뿐이다. Bartender 내부 동작은 1차 출처 확인 불가 `(추정)` | **1순위** — 가장 단순한 설명 |
| **H2** | `set_menu` 교체 시점(권한 전이·언어 변경)과 Bartender 의 메뉴 추적이 겹쳐 **재배치 시점에 깜빡임**이 생긴다 | 상호작용 | `set_menu` 는 NSStatusItem 을 유지하므로 이론상 아이콘은 안전하다(실측). 그러나 Bartender 가 메뉴 구조를 추적 중이면 교체 순간에 아이콘을 다시 그릴 수 있다 `(추정)` | **2순위** — 빈도가 낮다(권한 전이·언어 변경은 드문 이벤트) |
| **H3** | 최전면 앱 변경 시 `refresh_ignore_menu_item`(`main.rs:5257-5269`)의 `set_text`/`set_enabled`/`set_checked` 가 아이콘 깜빡임을 유발한다 | 우리 코드 | 이 호출들은 **NSMenuItem 수준**이고 NSStatusItem 의 아이콘·가시성과 무관하다(실측: `tray-icon` `set_menu` 경로와 분리). 깜빡임과 인과가 성립하려면 Bartender 가 메뉴 항목 변경까지 추적해 아이콘을 다시 그려야 한다 `(추정)` | **3순위** — 최전면 앱 변경은 잦지만 메커니즘이 간접적 |
| **H4** | Bartender 의 **메뉴바 공간 부족 자동 숨김**이 원인이다 | Bartender 측 동작 | `menu-bar-and-lifecycle.md` §5 항목 2 — macOS 자체도 공간 부족 시 상태 아이템을 숨긴다. Bartender 는 이 동작을 확장한 도구다. 사용자가 "반복적으로 사라졌다 나타난다"고 한 것은 이 숨김·복원이 잦다는 뜻일 수 있다 `(추정)` | 1순위와 병행 — H1 과 같은 관찰로 판정 가능 |

**기각한 가설**:
- **"아이콘 재생성으로 인한 사라짐"** — 코드상 재생성 경로가 없다(§1). 이슈 본문의 기존 조사와 동일한 결론.
- **"`icon_as_template(true)` 가 원인"** — 템플릿 모드는 빌더에서 한 번 설정되고 런타임에 `set_icon_as_template` 호출이 없다(grep 0건). 템플릿 리페인트는 macOS 가 외관 변경 시 수행하는 정상 동작이고, Bartender 복원과의 충돌은 H1 의 하위 사례로 본다.

### D2 — 실측 계측: 무엇을, 어떻게 기록할 것인가

**판정**: 로그 계측을 먼저 넣는다. 화면 캡처(AX 트리)는 Bartender 가 설치된 실기기에서만 의미가 있고, 로그는 Bartender 없이도 코드 경로가 정상인지 확인할 수 있다.

| 계측 | 위치 | 기록 내용 | 판정에 쓰는 방법 |
| :--- | :--- | :--- | :--- |
| `set_visible` 호출 | `main.rs:5126`(부팅), `main.rs:5621`(토글) | `tray set_visible 호출 visible=...` + **호출 스택의 트리거 출처**(부팅/토글) | Bartender 가 숨김·복원할 때 우리 코드가 개입하는지 배제 |
| `set_menu` 교체 | `main.rs:5160`(`apply_tray_menu_for_permission`), `main.rs:5176-5218`(`rebuild_tray_menu`) | `tray set_menu 교체 reason=permission|language` | 깜빡임 발생 시각과 `set_menu` 시각의 **시간적 상관** |
| `refresh_ignore_menu_item` | `main.rs:5257-5269` | `ignore 항목 갱신 front=...` (기존 로그에 시각 추가) | H3 판정 |
| NSStatusItem 상태 스냅샷 | `tray-icon` 의 `ns_status_item()` 접근자로 **주기적 폴링**(예: 1초) | `status_item 존재=... button.image 존재=...` | Bartender 가 아이콘을 숨긴 동안 NSStatusItem 이 살아 있는지(제거인지 숨김인지) 구분 |

> ⚠️ **계측은 `tracing::debug` 가 아니라 `info` 로 남긴다** — `manual-verification.md` §0 의 선례(이슈 #10): `debug` 면 기본 레벨에서 안 보여 검증자가 "동작했다"와 "로직이 없다"를 구분할 수 없다. 다만 `set_visible`/`set_menu` 는 빈도가 낮아 `info` 로 해도 로그 오염이 없다. 주기적 폴링(1초)은 `debug` 로 남기고, `ULTRAKEY_LOG=debug` 로 켤 때만 기록한다.

**기각한 대안**:
- **화면 캡처를 1차 수단으로**: Bartender 가 설치된 실기기가 없으면 캡처 자체가 불가능하다. 로그 계측은 Bartender 없이도 코드 경로 검증이 가능하므로 선행한다.
- **`log stream`(OSLog)**: `manual-verification.md` §0 에 이미 "동작하지 않는다"고 실측으로 기록됨 — 앱 로그는 파일(`~/Library/Logs/Ultrakey/ultrakey.log`)로 남긴다.

### D3 — Bartender 특정 동작 가설의 검증법

Bartender 내부 동작은 1차 출처 확인 불가이므로, **실기기에서의 관찰로만 판정**한다. 검증법:

| 관찰 | 방법 | 판정 |
| :--- | :--- | :--- |
| Bartender 가 아이콘을 숨길 때 NSStatusItem 이 **제거되는가, 숨김 처리되는가** | D2 의 주기적 폴링 로그 — 숨김 구간에 `status_item 존재` 값이 `false` 면 제거, `true` 면 숨김 | H1/H4 판정의 핵심 |
| 깜빡임 발생 시각과 `set_menu`/`set_visible` 시각의 상관 | 로그 타임스탬프 대조 | 상관이 **없으면** H2/H3 기각 → Bartender 단독 동작(H1/H4)으로 좁혀짐 |
| Bartender 설정에서 Ultrakey 를 **제외 목록에 넣었을 때** 깜빡임이 사라지는가 | 사용자 실기기 조작 | 사라지면 Bartender 의 숨김·복원이 원인 확정 |
| Bartender 를 **완전히 종료**했을 때 깜빡임이 사라지는가 | 사용자 실기기 조작 | 위와 동일한 확정 경로 |

> ⛔ **검증자가 시스템 설정을 바꾸는 조작(Bartender 설정 변경·종료)은 위임 경계 밖이다** — `manual-verification.md` 의 기존 규약(사용자 세션·시스템 설정 변경 금지)을 따른다. 절차는 문서로 남기고 **사용자가 직접 수행**한다.

### D4 — 완화 수단 후보 (근거 있는 것만)

원인 확정 **이후에만** 적용한다. 현재 시점에서 근거가 있는 후보:

| 후보 | 근거 | 적용 조건 |
| :--- | :--- | :--- |
| **`set_menu` 교체 빈도 감소** — 언어 변경 시 `rebuild_tray_menu` 가 두 벌을 재조립하는데, 권한 상태가 바뀌지 않았으면 `set_menu` 를 부르지 않는다 | `main.rs:5206-5216` — 현재는 언어 변경 시 **무조건** `apply_tray_menu_for_permission` 을 불러 `set_menu` 를 실행한다. 메뉴 내용이 바뀌었으므로 교체 자체는 정당하지만, **권한 상태가 그대로인데도** `set_menu` 가 실행되는 것은 불필요한 교체다 | H2 가 실측으로 확정됐을 때만 |
| **아이콘 identity 유지** — `set_icon`/`set_icon_as_template` 을 런타임에 부르지 않는다(현재 상태 유지) | 이미 유지 중(§1). **변경할 것이 없다** | — |
| **`set_visible` 최소화** — 현재 기본 상황에서 호출되지 않으므로 이미 최소화됨 | §1 | — |
| **Bartender 제외 목록 안내** — 사용자에게 "Bartender 설정에서 Ultrakey 를 제외하면 깜빡임이 사라질 수 있다"는 안내를 문서로 제공 | H1/H4 가 확정되면 이 안내가 유일한 실질적 완화 수단이다 — 우리 코드로는 Bartender 의 숨김·복원을 제어할 수 없다 | H1/H4 확정 시 |
| **`menu_on_left_click` 재검토** — `main.rs:5118` `show_menu_on_left_click(true)` | 이슈 본문이 후보로 언급했으나 **근거가 없다** — 이 옵션은 클릭 동작(메뉴 열기)만 바꾸고 아이콘 가시성과 무관하다(실측: `tray-icon` `set_show_menu_on_left_click` 은 `TrayTarget` 의 ivar 플래그만 바꾼다, `mod.rs:240-245`). **기각** | — |

### D5 — 재현 불가 시 처리: 문서화 후 연기 (실험 브랜치 기각)

**판정**: 실기기(Bartender 설치)가 없으면 **원인 확정이 불가능**하므로, 이번 회차에서 수정을 강행하지 않는다. 처리 순서:

1. **D2 의 로그 계측을 구현**하고, Bartender 없이도 코드 경로가 정상임을 확인한다(회귀 없음).
2. **수동 검증 절차를 문서화**한다(§5) — 사용자가 Bartender 실기기에서 수행할 절차.
3. **이슈를 "실기기 재현 대기" 상태로 남긴다** — 사용자가 절차를 수행해 로그를 회신하면 원인 확정 → 수정 단계로 진행.

**기각한 대안 — 실험 브랜치에서 추정 수정**: Bartender 가 설치되지 않은 환경에서 "추정 수정"(예: `set_menu` 호출 제거)을 넣으면, (a) 검증할 수단이 없고, (b) 실제 원인이 H1/H4(Bartender 단독 동작)라면 수정이 무의미하며, (c) `set_menu` 교체는 권한 전이·언어 변경이라는 **정상 기능**에 묶여 있어 제거 시 회귀 위험이 있다. 근거 없는 수정은 이 저장소의 "확인하지 못한 동작을 지어내지 않는다" 규약에 어긋난다.

## 4. 테스트/실기기 계획

### 자동화 가능한 것 (`cargo test`)

- 계측 추가로 인한 회귀 없음 — 기존 테스트 전량 통과.
- ⭐ **신규 테스트 후보**: `rebuild_tray_menu` 가 권한 상태가 그대로일 때 `set_menu` 를 부르는지 여부를 **단위 테스트로 고정**할 수 없다 — `TrayIcon` 은 AppKit 객체라 테스트에서 생성 불가. 대신 **판정 로직(권한 상태가 바뀌었는가)을 순수 함수로 분리**하면 테스트 가능하다. 이 분리는 H2 확정 후(단계 3)에만 수행한다 — 지금 분리하면 근거 없는 리팩터링이 된다.

### 실기기에서만 가능한 것

| 항목 | 왜 자동화 불가인가 | 수행자 |
| :--- | :--- | :--- |
| Bartender 환경에서의 깜빡임 재현 | Bartender 가 설치된 실기기가 필요 | 사용자 |
| Bartender 제외 목록·종료 대조 실험 | 시스템 설정·타사 앱 조작 | 사용자 |
| NSStatusItem 숨김 구간 상태 관찰 | D2 폴링 로그가 실기기에서만 의미 있음 | 사용자(로그 회신) |
