## 1. ⭐ 한 줄 결론

**WKWebView 로 그려도 된다 — 단 `<canvas>` 2D 로 그릴 때만이다.**

Canvas 로 그리면 후보가 **0개든 1000개든 왕복 중앙값이 약 25 ms 로 같다** —
후보 수에 **전혀** 반응하지 않는다. 같은 것을 절대배치 DOM 노드로 그리면 후보
500개에서 **92.5 ms**(p95 108.6 ms), 1000개에서 **191.4 ms** 로 §3.6 의 100 ms
체감 예산을 넘긴다.

즉 P3 의 답은 "WKWebView 가 느리다"가 아니라 **"DOM 이 느리다"** 였다.
`platform-constraints.md` §4.3 이 예비해 둔 `CALayer` 교체는 **필요 없다.**

| **Canvas** | 1000 | ✅ **24.84 ms** | 28.30 ms | 29.53 ms | 5.00 ms | 316.2 µs |

읽는 법:

- **왕복**은 Rust 의 `emit` 직전부터 두 창이 *모두* 그리고 `invoke` 로 되돌아온
  ack 을 받을 때까지다. 사용자가 실제로 기다리는 것은 편도(emit → paint)이므로
  **이 표는 체감 지연을 과대평가한다.** 바닥값은 `n = 0` 행이 보여 준다 —
  그릴 것이 없을 때 남는 것은 IPC 왕복과 **두 창 중 느린 쪽(60 Hz)의 더블 rAF
  대기**다(2프레임 ≈ 33 ms 상한).
- **JS build** 는 JS 가 DOM/Canvas 를 갱신하는 **동기 구간**만이다.
  (`performance.now()` 가 WKWebView 에서 0.5 ms 단위로 양자화되어 0.00/0.50 이
  섞여 나온다.)
- **직렬화**는 두 창 몫 페이로드를 `serde_json` 으로 만드는 Rust 시간이다.

### 2.1 ⚠️ 이 표는 **두 번째** 측정이다 — 첫 번째는 버렸다

첫 실행의 숫자를 폐기하고 다시 쟀다. 이유를 남긴다(§6 항목 5 와 같은 결함이다):

**JS 의 `tauri.event.listen(...)` 은 리스너를 `target: Any` 로 등록한다.** 그래서
Rust 가 `emit_to(EventTarget::webview_window(label), …)` 로 **대상을 지정해
보내도 모든 창이 다 받는다.** 하네스는 창마다 다른 페이로드를 보내므로, 창
하나가 남의 프레임까지 그리고 ack 을 두 번 보냈다 — 즉 첫 측정은 **창당 작업량이
2배**이면서 동시에 **ack 을 먼저 온 2개로 세어** 바닥값이 과소평가된, 두 방향으로
오염된 숫자였다.

`getCurrentWebviewWindow().listen(…)` 으로 바꿔 창별 격리를 확보한 뒤 다시 쟀고,
위 표가 그 결과다. **결론의 방향은 바뀌지 않았고 오히려 더 뚜렷해졌다** — Canvas
는 후보 수에 완전히 무반응이 됐고(0개 24.99 ms vs 1000개 24.84 ms), DOM 은 더
나빠졌다(500개 92 ms, p95 108 ms).

⭐ 같은 결함이 **제품 코드에도 있었고**, 실기기 검증이 그것을 잡아냈다 —
디스플레이 3 의 창이 디스플레이 2 의 프레임을 그려 연결선이 엉뚱한 화면에
그려졌다. §6 항목 5 참조.

## 3. ⭐⭐ 이 숫자들이 실제로 말하는 것

### 3.1 병목은 JS 가 아니라 **레이아웃·합성**이다

DOM 1000개 행을 보라 — 왕복 191.4 ms 인데 **JS build 는 2.0 ms** 다. 즉 JS 가
`style.transform` 을 1000번 쓰는 데 든 시간은 전체의 **1 %** 다. 나머지 190 ms
는 JS 가 반환한 **뒤에** WebKit 이 절대배치 요소 1000개(+라벨 1000개, 총 2000
노드)의 레이아웃과 레이어 합성을 하는 시간이다.

⭐ **이것이 P3 의 진짜 답이다.** "Rust → IPC → JS" 왕복이 비싼 것이 아니다.
직렬화는 후보 1000개에서도 0.3 ms 이고, `n = 0` 행이 보여주듯 왕복 바닥값
15~25 ms 의 대부분은 **60 Hz 디스플레이의 더블 rAF 대기**다. 비싼 것은
**DOM 을 그리기 표면으로 쓴 것** 하나뿐이었다.

### 3.2 Canvas 는 후보 수에 **전혀** 반응하지 않는다

0개 24.99 ms → 1000개 24.84 ms. 후보가 0에서 1000으로 가는 동안 왕복 중앙값이
**늘지 않았다**(측정 잡음 안이다). JS build 만 0 → 5 ms 로 늘 뿐, 그 5 ms 는
프레임 예산 안에 그대로 흡수된다.

즉 Canvas 경로의 비용은 사실상 **고정비(IPC + vsync + 화면 크기만큼의 서피스
클리어)** 이고, 후보 수는 예산에 영향을 주지 않는다.

역으로 `n = 0` 에서 Canvas(24.99 ms)가 DOM(15.40 ms)보다 **느리다** — 아무것도
안 그려도 3840×1600 캔버스를 `clearRect` 하고 합성하기 때문이다. 이 고정비는
후보가 10개만 넘어가면 즉시 회수된다(10개에서 이미 DOM 24.82 ≈ Canvas 25.09).

### 3.3 예산 판정 (§3.6)

| 기준 | Canvas | DOM |
| :--- | :--- | :--- |
| **편도**(왕복 − `n=0` 바닥) — 후보를 그리는 데 실제로 더 드는 시간 | ✅ **후보 1000개에서 0 ms** (24.84 − 24.99 ≈ 0) | ⛔ 1000개에서 **176 ms** (191.35 − 15.40) |
| 총 체감 100 ms | ✅ **후보 1000개까지 여유** (p95 28.3 ms) | ⛔ 500개 p95 108.6 ms, 1000개 195 ms |
| 프레임 1개(≈16 ms) — 왕복 기준 | ⚠️ 바닥값 자체가 25 ms(60 Hz 더블 rAF) — **후보 수와 무관하게** 못 맞춘다 | ⚠️ 상동 |

⚠️ **"프레임 1개(16 ms)" 목표는 이 측정 방식으로는 어느 렌더러도 못 맞춘다** —
바닥값이 60 Hz 디스플레이의 더블 rAF(최대 33 ms)와 ack 왕복으로 이미 차 있기
때문이다. 그러나 그것은 렌더러의 문제가 아니라 **측정이 커밋 완료까지 기다리기
때문**이고, 사용자가 실제로 기다리는 것은 다음 vsync 한 번이다. 판정에 쓸 수
있는 것은 **"후보를 그리는 데 추가로 드는 시간"** 이며, Canvas 는 그것이
1000개에서도 **0에 가깝다.**

⭐ **명세 §4.2 의 "동시 렌더링 200개 상한"은 Canvas 에서는 성능상 필요 없다**
(200개 24.72 ms vs 1000개 24.84 ms). 그럼에도 **상한은 유지한다**: 근거가
성능에서 **가독성**으로 바뀔 뿐이다. 화면에 하이라이트 1000개를 동시에 칠하면
화면이 통째로 노랗게 되어 아무것도 못 고른다. → 결정 **R-4**.

## 6. 하네스 자체가 밟은 함정 (재현하려는 사람을 위해)

숫자가 나오기 전에 세 번 막혔다. 전부 **측정과 무관한 배선 문제**였고, 같은
곳에 다시 빠지지 말라고 남긴다.

1. ⛔ **`WebviewUrl::App` 에 쿼리 문자열을 붙이면 404 다.** `PathBuf` 라 `?` 가
   경로의 일부로 퍼센트 인코딩된다. 창 이름은 JS 쪽에서
   `getCurrentWebviewWindow().label` 로 읽어야 한다.
2. ⛔ **capabilities 파일이 하나도 없으면 `plugin:event|listen` 이 ACL 로
   막힌다.** 증상은 조용하다 — 페이지는 뜨는데 이벤트가 영영 안 온다.
   `apps/ultrakey-app/capabilities/overlay.json` 이 이것을 연다.
3. ⛔ **`Emitter::emit` 은 브로드캐스트다.** 창마다 다른 페이로드를 보내는
   하네스에서 이걸 쓰면 창 하나가 남의 프레임까지 그려 ack 이 창 수의 제곱만큼
   온다. `emit_to(EventTarget::webview_window(label), …)` 이어야 한다.
5. ⛔⭐ **그런데 `emit_to` 만으로는 부족하다 — JS 쪽도 고쳐야 한다.**
   `tauri.event.listen(…)` 은 리스너를 **`target: Any`** 로 등록해서, Rust 가
   대상을 지정해 보내도 **모든 창이 다 받는다.** 항목 3 을 고친 뒤에도 격리가
   안 되는 이유가 이것이었다. **`getCurrentWebviewWindow().listen(…)`** 을
   써야 리스너가 그 창으로 등록된다.
   ⭐ 이 결함은 스파이크뿐 아니라 **제품 렌더러에도 그대로 있었고**, 증상이
   교묘했다 — 하이라이트는 맞는 화면에 그려지는데(마지막에 도착한 프레임이
   덮어쓰기 전에 그려진 프레임이 남아) **연결선만 엉뚱한 화면에 나타나** 다중
   디스플레이 연결선이 끊긴 것처럼 보였다. 픽셀을 직접 세어 보고 나서야
   창 배치가 아니라 **이벤트 배달**이 문제임을 알았다(임시로 캔버스에 창
   이름·`display_id` 배지를 그려 확정했다). **실기기 검증이 아니었으면
   찾지 못했을 종류의 버그다.**
4. `transparent: true` 창은 Tauri 의 `macos-private-api` 기능이 없으면 아예
   **컴파일되지 않는다**(`WebviewWindowBuilder::transparent` 가 없다).
   이 제품은 비샌드박스 직접 배포라 App Store 배타성은 잃을 것이 없다.
