## 1. ⭐ 한 줄 결론

**수정 전**, 동글 재삽입 뒤 경로 B 재적용이 탭 스레드에서 `elapsed_ms=179`(디바이스 1대) 걸렸고,
그 완료 순간 probe 샘플 14개가 한꺼번에 풀리며 **최대 180.88 ms** 지연이 관측됐다 —
곧 그 179 ms 동안 키보드·마우스 입력이 전부 정지했다는 뜻이다.

**수정 후**, 재적용은 지연 스케줄러 스레드(`ultrakey-delay-scheduler`)로 옮겨졌고, 동글 재삽입 2회에서
재적용이 `elapsed_ms=102`·`91` 걸리는 동안 probe 지연은 **max 4.16 ms·5.29 ms**(각 창 67 샘플, 누락 0)로
②(유휴) 수준에 머물렀다 — 재적용 시간이 더 이상 입력 정지 시간이 아니다.

## 2. 측정 방법

### probe 원리 (`latency_probe`)

- 별도 스레드가 `--interval-ms` 간격으로 **현재 커서 위치의 `MouseMoved`** 이벤트를 `CGEventSource(HIDSystemState)` 로 만들어
  `EventSourceUserData` 에 `(TAG<<56) | ns_since_start` 를 실어 `CGEvent::post(HIDEventTap)` 으로 발행한다.
- 마커에 `ULTRAKEY_MAGIC` 을 쓰지 않는다 — 그 값을 쓰면 Ultrakey 엔진의 0-a(자기 합성 이벤트 마커 확인) 분기가
  probe 이벤트를 즉시 통과시켜 버려 탭 통과 경로를 실측하지 못한다.
- 발행된 이벤트는 `HIDEventTap` → **Ultrakey 세션 탭**(`SessionEventTap`) 을 실제로 통과한 뒤 → probe 의 수신 탭
  (`TailAppendEventTap` + `ListenOnly`, `MouseMoved` 만 마스킹)에 도착한다. 수신 시각(`now_ns`)에서 인코딩된
  발행 시각(`encoded_ns`)을 빼 지연을 계산한다.
- TAG 가 다른(즉 실제 사용자 마우스 움직임) 이벤트는 무시한다.

### ③ 절차

1. probe 를 지정 시간(180 s 또는 60 s) 실행 상태로 둔다.
2. 사용자에게 동글 재삽입을 요청한다.
3. 재삽입(attach) 약 1.5 s 뒤 재적용(`ReapplyHidMapping`/스케줄러 재적용)이 실행된다(`keyboard_connect_delay_ms=1500`).
4. 앱 로그의 재적용 완료 시각·`elapsed_ms` 와 probe 가 출력한 스파이크 벽시계 시각을 대조한다 — **둘 다 UTC** 다.

## 4. ③ 상관 분석

수정 전 ③ 의 실제 재삽입 1회에 대해:

- `attach 23:09:23.034` → `completed 23:09:24.720 thread=ultrakey-tap elapsed_ms=179 devices=1`
- probe: `23:09:24.720~.721` 구간에 14 샘플이 한꺼번에 도착. 지연값이
  `180.88, 169.56, 157.05, …, 33.76, 21.24 ms` 로 **약 12 ms 간격 계단**을 이룬다(설정 `--interval-ms 10` 에 발행 스레드 sleep 오차가 더해진 **실측** 발행 간격 ≈ 12 ms — 14979 샘플/180 s, §6 참고) —
  정지 구간(179 ms) 동안 큐에 쌓였던 이벤트가 정지 해제 순간 일괄 방출된 모양으로 해석된다.
- 직전 `23:09:24.454~.493` 구간의 6 샘플(25~49 ms)은 **원인 미확인 (추정: 핫플러그 직후 IOKit 재열거 또는 시스템 부하)**.
- 첫 시도(`23:06:47` attach, `elapsed_ms=114`)는 probe 측정 창 밖이라 표본에서 **제외**했다.
- 수정 전 ② 의 4개 스파이크(max 33.24 ms, 기동 직후 30 s 구간)는 **원인 미확인**.

수정 후 ③ 의 재삽입 2회에 대해(로그 스레드가 `ultrakey-delay-scheduler` 로 바뀐 것을 로그 실물로 확인):

| 회 | attach | completed (thread=`ultrakey-delay-scheduler`) | `elapsed_ms` | probe (attach→completed+0.7 s) | probe (completed±0.4 s) |
| :--- | :--- | :--- | ---: | :--- | :--- |
| 1 | 04:50:02.596 | 04:50:04.202 | 102 | n=199, max **8.68 ms** | n=67, max **4.16 ms** |
| 2 | 04:50:22.087 | 04:50:23.724 | 91 | n=211, max **5.58 ms** | n=67, max **5.29 ms** |

- 같은 창에서 수정 전에는 14 샘플이 일괄 방출되며 max 180.88 ms 였다. 수정 후에는 샘플이 12 ms 간격으로
  빠짐없이 도착했고(n=67 ≈ 0.8 s/12 ms) 지연은 유휴 수준이다 — **재적용 시간(91~102 ms)이 입력 지연으로
  전이되지 않았다.**
- 재적용 `elapsed_ms` 자체는 수정 전(114·179)보다 작게 나왔다(91·102). 표본이 적어 QoS·스레드 이전의 효과인지
  편차인지는 **판단 불가**(추정: hidutil 3회 + fsync 2회의 자연 편차).

## 5. QoS 확인 (A3)

기동 로그:

```
tap thread QoS set to USER_INTERACTIVE qos_before=Some(Default) qos_after=Some(UserInteractive) thread=ultrakey-tap
```

`ps -M` 은 스레드 이름을 보여주지 않아 `ultrakey-tap` 스레드로 귀속할 수 없다 — 이번 판정 근거로 쓰지 않았다.

### A8 — 재삽입 뒤 D-1·per-device 매핑 유지 (수정 후)

재삽입 2회 뒤 `hidutil property --matching '{"VendorID":0x5ac,"ProductID":0x24f}' --get UserKeyMapping` 에
D-1(`Src 0x700000039 → Dst 0x70000006D`, caps lock → F18)이 실려 있음을 확인했다. 절전→깨어남 트리거는 미측정(§7).

### A4 — Seek 세션 키 라우팅 (수정 후, 실기기 수동 + `ULTRAKEY_TRACE_TAP=1`)

## 6. 함께 관찰된 것

- `~/Library/Logs/Ultrakey/` 는 계측 빌드를 `open` 하자 즉시 생성됐다 — `init_logging` 자체는 정상 동작이다.
  설치본(0.1.2) 실행 중에는 이 디렉터리가 없었다. **원인 미확인 (추정: 설치본 실행 환경 차이)** — 이 문서의
  범위 밖이라 별도 이슈로 제안한다.
- posted 수 차이(수정 전 ~2500 vs 수정 후 ~2200, 30 s 창)는 probe 발행 스레드의 sleep 정밀도 차이로 보인다
  (추정). 각 샘플이 자기 발행 시각을 실어 지연을 계산하므로 이 차이는 지연값 자체에는 영향이 없다.

## 7. 한계

- 표본이 적다(③ 수정 전 재삽입 1회, 수정 후 2회).
- 유휴 조건(②)은 "기동 직후 30 s" 로만 정의했다.
- probe 자체가 `MouseMoved` 를 100 Hz(=`--interval-ms 10`)로 주입해 측정 대상 시스템에 부하를 더한다.
- 절전→깨어남 트리거(전체 재적용, 대상 디바이스 2대)는 **미측정** — 사유: 세션 연결을 유지하기 위해
  이번 세션에서는 절전 트리거를 걸지 않았다.
- 수정 후 ③ 창(240 s) 동안 사용자가 Seek 를 사용하고 있어 창 전체 통계(max 72.68 ms)는 재적용과 무관한 부하를 포함한다 — 재적용 영향은 재적용 창 부분집합으로만 판단했다.

## 8. 2차(이슈 #140) — 마우스 이벤트 마스크 제외

`latency_probe` 는 `MouseMoved` 를 100 Hz 로 주입해 지연을 측정한다(§2). 이 주입 자체가 §3 ②(유휴)의
수정 후 기준선을 만든 원인이다 — 기본 구성(모디파이어 규칙 없음·트랙패드 제스처 off)에서는
`mouse_event_needs` 가 `MouseMoved` 를 포함해 아무것도 요구하지 않지만, 이슈 #140 이전에는 마스크가
키 3종 + 마우스 11종으로 고정돼 있어 probe 의 `MouseMoved` 가 매번 Ultrakey 의 탭까지 WindowServer ⇄
탭 스레드 동기 왕복을 거쳤다. 이 이슈로 도출된 마스크가 `MouseMoved` 를 제외하면, probe 가 주입하는
이벤트는 Ultrakey 탭을 아예 거치지 않는다 — 즉 ②(유휴)가 ①(Ultrakey 미실행) 수준으로 **수렴**할 것으로
예상한다.

| ② 유휴, 이번 빌드 1회차(기본 구성, `mask=7168`=키 3종) | 2511 | 2511 | 0 | 0.28 | 2.41 | 6.02 | 9.32 | 0 |

**판독.** 이번 빌드의 ②(p50 0.28·0.30 ms)는 같은 세션에서 잰 ①(p50 0.27 ms)과 사실상 같다 — 기대값
"①로 수렴" 이 실측으로 확인됐다. #139 기준선(p50 0.83 ms)과 비교해 중앙값이 약 1/3 로 줄었고, 그 차이가
곧 커서 이동 1건당 WindowServer ⇄ 탭 스레드 동기 왕복 비용이다. p95·p99 는 세 조건 모두 2~6 ms 범위로
같은 세션의 시스템 노이즈 안에 있다(2026-09-06 밤 측정은 #139 낮 측정과 시스템 부하가 달라 절대값 직접
비교는 ① 기준으로만 한다). 실기기 확인 근거: 이번 빌드 기동 로그
`tap created mouse_click=false mouse_drag=false mouse_move=false mouse_scroll=false mask=7168`
(`0x1C00` = `KeyDown|KeyUp|FlagsChanged` 비트만). 사용자 설정 파일에는 `hyperkey.*`·`presets.*` 키가 없어
출고 기본 구성 그대로다.

측정 조건: M4 Pro, 설치본이 아니라 메인 체크아웃의 #139 빌드가 떠 있던 것을 사용자 동의 뒤 종료하고 이
브랜치의 `scripts/build-signed.sh` 산출물을 `open` 으로 띄워 측정, 끝난 뒤 원래 빌드로 복구했다.

### 수동 확인 체크리스트

사용자가 이 세션에서 수동 확인을 수행하지 않기로 해 아래 항목은 **미측정**으로 남긴다. 설정 토글은
문서화된 수단(설정 UI)으로만 해야 하고, 설정 파일 편집·Tauri 커맨드 직접 호출은 작업 경계 밖이다.

- [ ] 트랙패드 제스처 토글 시 재생성 로그(`recreating the tap because the required event mask changed
