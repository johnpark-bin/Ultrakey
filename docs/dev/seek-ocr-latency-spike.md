# ⭐ F-02 OCR 지연 스파이크 — 실측 결과와 그 해석

> **무엇인가**: `docs/spec/seek-text-detection.md` 가 M3 의 **첫 일**로 지목한 실측이다.
> Seek 은 세션을 열 때 화면 전체를 캡처해 OCR 하므로, 그 지연이 곧 제품 성립 여부다.
> **이 문서가 해소하는 것**: 명세 §9 **Q-m**(전체 화면 OCR 지연 실측치), §5 #8,
> `platform-constraints.md` **P3** 의 절반(F-02 쪽), 명세 §3.2.1 **Q-k**(전처리 필터 선택),
> 명세 §3.2.2 · §9 **Q-h/Q-j** 의 `recognitionLanguages` 부분.
> **재현**: `cargo run -p ultrakey-platform --release --example seek_ocr_spike`
> (그 외 `seek_ocr_spike2` · `seek_preset_quality` · `seek_language_check`)

## 1. ⭐ 한 줄 결론

**전체 화면(2개 디스플레이) `.accurate` OCR 은 중앙값 약 775 ms 다.** 이것은 세션을
열 때 **한 번** 드는 비용이고, 매 키 입력마다 드는 비용이 아니다(입력마다 하는 일은
이미 만들어진 후보 목록에 대한 순수 문자열 필터링이다).

따라서 **지연 예산은 "세션 개시 → 첫 후보 표시"에 걸리며, 775 ms 를 동기로 막고 있으면
제품이 성립하지 않는다.** 아래 §5 의 설계 요구가 여기서 나온다.

## 2. 단계별 실측

### 2.1 캡처 — `CGDisplayCreateImage`

| 디스플레이 | 이미지 | 배율 | 캡처 시간(중앙값) |
| :--- | :--- | :--- | ---: |
| id=3 3840×1600 | 3840×1600 px | 1.00 | **19.5 ms** |
| id=2 2560×1440 | 2560×1440 px | 1.00 | **11.9 ms** |
| **합계** | | | **≈ 31 ms** |

캡처는 전체 예산의 **4 %** 에 불과하다. 병목이 아니다.

### 2.2 전처리 — CoreImage

| 프리셋 | 그래프 구성(중앙값) |
| :--- | ---: |
| None / Noir / MaximumComponent / Downscale / NoirDownscale | **0.0 ms** |

⚠️ **이 숫자를 "전처리가 공짜" 로 읽으면 안 된다.** CoreImage 는 지연 평가라
`imageByApplyingFilter` 는 필터 그래프만 만든다. 실제 픽셀 계산은 Vision 이 픽셀을
요구할 때 일어나므로, **전처리 비용은 §2.3 의 OCR 시간에 흡수되어 나타난다.**

### 2.3 OCR 왕복 — `VNRecognizeTextRequest` (전처리 + 인식)

`.accurate` (명세 §3.2.2 가 고른 레벨):

| 전처리 | id=3 | id=2 | **합계(순차)** | 후보 수 (3 / 2) |
| :--- | ---: | ---: | ---: | :--- |
| None | 335 ms | 448 ms | **774 ms** | 45 / 102 |
| Noir | 320 ms | 475 ms | 797 ms | 53 / 111 |
| MaximumComponent | 320 ms | 437 ms | 757 ms | 52 / 101 |
| Downscale(0.5) | 347 ms | 392 ms | 737 ms | 36 / 65 |
| NoirDownscale(0.5) | 288 ms | 391 ms | 679 ms | 36 / 69 |

`.fast` (참고용, 명세가 고르지 않은 레벨):

| 전처리 | **합계(순차)** | 후보 수 (3 / 2) |
| :--- | ---: | :--- |
| None | **241 ms** | 191 / 160 |
| Noir | 228 ms | 181 / 174 |
| Downscale(0.5) | 67 ms | 13 / 3 |

> `.fast` 가 `.accurate` 보다 후보 *수* 가 많은 것은 인식률이 더 좋아서가 아니라
> 텍스트를 더 잘게 쪼개기 때문이다. 개수로 두 레벨을 비교하면 안 된다.

### 2.4 ⭐ 지연은 화면 크기가 아니라 **텍스트 밀도**를 따른다

id=3 은 6.1 Mpx 인데 335 ms, id=2 는 3.7 Mpx 인데 448 ms 다 — **더 작은 화면이 더
오래 걸렸다.** 후보 수는 45 vs 102 였다. 즉 **비용은 픽셀 수가 아니라 인식된 텍스트
양에 비례한다.** 명세 §5 #8 이 "`.accurate` 의 비용이 화면 크기에 비례해 커진다"고
쓴 것은 **부정확하다** — 텍스트가 빽빽한 작은 화면이 텅 빈 큰 화면보다 비싸다.

### 2.5 워밍업 — 프로세스 첫 OCR 이 비싸다

| 회차 | 시간 |
| :--- | ---: |
| 0 (콜드) | **418.6 ms** |
| 1~5 (웜) | 283 ~ 317 ms (중앙값 ≈ 299 ms) |

첫 호출이 **약 120 ms** 비싸다 (Vision 모델 로드로 보인다). 후보 개수는 회차와
무관하게 48개로 동일했으므로 결과 차이가 아니라 순수 초기화 비용이다.

### 2.6 ⭐⭐ Vision OCR 은 **병렬화되지 않는다** — 명세 §5 #8 의 완화책을 반증한다

명세 §5 #8 은 "디스플레이별 병렬 처리로 완화 가능" 이라고 적었다. **측정은 이것을
반증한다.**

| 실험 | 순차 | 병렬(2 스레드) | 이득 |
| :--- | ---: | ---: | ---: |
| 두 디스플레이(3840×1600 + 2560×1440) | 774 ms | **779 ms** | **0 %** |
| 같은 이미지 2장(교차 확인) | 605 ms | **607 ms** | **0 %** |

두 실험 모두 이득이 **정확히 0** 이다. `VNRecognizeTextRequest` 는 공유 자원
(ANE/GPU 로 추정)에서 직렬 실행되며, 스레드를 더 쓰는 것은 **낭비일 뿐 아니라
결과 도착을 오히려 늦춘다** — 병렬로 돌리면 두 디스플레이의 후보가 *둘 다* 779 ms
뒤에 도착하지만, 순차로 돌리면 첫 디스플레이 후보가 335 ms 에 이미 나온다.

> **→ 설계 결정 S-1 (§5).**

### 2.7 영역 한정 캡처 — `Only Seek in the frontmost window` (§3.3.2)

주 디스플레이(3840×1600)에서 캡처+OCR 을 영역 크기별로:

| 영역 | 캡처+OCR | 후보 수 |
| :--- | ---: | ---: |
| 전체 화면 3840×1600 | 332 ms | 51 |
| 1600×1000 | **163 ms** | 53 |
| 1200×800 | 121 ms | 34 |
| 800×600 | 88 ms | 23 |

일반적인 창 크기(1600×1000)로 좁히면 **약 절반**이 된다. 다만 이 설정은 기본이
꺼짐이고(명세 §4), 다른 디스플레이의 후보를 통째로 버리는 대가가 있다.

## 3. ⭐⭐ 새로 드러난 것 — `recognitionLanguages` 기본값으로는 **한글이 전혀 인식되지 않는다**

이것은 스파이크가 찾으려던 것이 아니라 품질 비교 중에 드러난 것이고, 이 클론에
직접 영향이 있다(1차 사용자가 한국어 사용자다).

| `recognitionLanguages` | id=3 시간 | 관측 | **한글 포함** | 평균 신뢰도 |
| :--- | ---: | ---: | ---: | ---: |
| 기본값(미설정) | 457 ms | 53 | **0** | 0.832 |
| `["en-US"]` | 400 ms | 53 | **0** | 0.832 |
| `["ko-KR", "en-US"]` | **1246 ms** | 92 | **49** | 0.596 |
| `["en-US", "ko-KR"]` | 389 ms | 53 | **0** | 0.832 |

id=2 도 같은 방향이다 (기본값 443 ms/한글 0개 → `ko-KR` 우선 1844 ms/한글 93개).

확정되는 것:

1. **Vision 의 기본 인식 언어는 영어뿐이다.** 화면에 한글이 가득해도 후보가 하나도
   안 나온다 — 조용한 실패다.
2. **`ko-KR` 을 넣되 목록의 첫 번째여야 한다.** `["en-US", "ko-KR"]` 는 결과가
   `["en-US"]` 와 **완전히 동일**했다(관측 수·시간·신뢰도 전부). 즉 순서가 단순한
   선호도가 아니라 **어느 모델을 쓸지를 가른다**.
3. ⚠️ **대가가 크다 — 약 3~4배 느려진다.** 전체 화면 합계가 775 ms → **약 3.1 s** 다.
   평균 신뢰도도 0.83 → 0.59 로 떨어진다(영어가 다수인 화면을 한국어 우선 모델로
   읽기 때문으로 보인다).

한글 인식 표본(`["ko-KR","en-US"]`, 실제 출력):
`"아직 만들지 않음"`, `"Merge pull request #29 from johnpark-bin/feat/per-device-settings … F-17 키보드별 설정 - 경로 B 전체를 디바이스 한정으로 재설게"`

**→ 설계 결정 S-4 (§5).**

## 4. 전처리 프리셋 — Q-k 에 대한 답은 "차이가 재현되지 않는다"

후보 *수* 만 보면 Noir 가 None 보다 10~18 % 많다. 그러나 실제 문자열을 집합으로
비교하면 **추가된 것과 사라진 것이 거의 같은 수**다(id=3: Noir 는 +52 / −46).
내용을 보면 대부분 **같은 텍스트의 다른 오인식**이다:

```
None :  "# A brief tan on either Shift {vnes a brackt ЭХ"
Noir :  "# A brief tan on either Shift twnes a hracket ЭХ"
```

평균 신뢰도로 보면 오히려 Noir 가 가장 낮다 (id=3: None 0.829 / Noir 0.823 /
MaximumComponent 0.867 / MinimumComponent 0.845).

**결론**: 일반적인 데스크톱 화면에서 전처리 프리셋의 차이는 **OCR 지터에 묻힌다.**
명세 §5 #12 가 지목한 실패 사례(극소 텍스트, 검정 배경 위 특정 파란색, 인접 줄)는
이 임의 화면 표본에 들어 있지 않으므로 **이 스파이크는 그 사례들에 대해서는 아무것도
말하지 못한다.**

**→ 설계 결정 S-3 (§5).**

## 5. ⭐ 설계 결정 — 이 숫자들이 강제하는 것

| # | 결정 | 근거 | 기각한 대안 |
| :--- | :--- | :--- | :--- |
| **S-1** | **디스플레이별로 순차 OCR 하되, 결과를 디스플레이 단위로 하나씩 내보낸다.** 스레드를 늘리지 않는다 | §2.6 — 병렬 이득이 정확히 0 이고, 병렬은 첫 결과 도착을 335 ms → 779 ms 로 **늦춘다** | ① 명세 §5 #8 이 제안한 디스플레이별 병렬 — 측정으로 반증됐다. ② 전부 모아서 한 번에 내보내기 — 첫 후보가 775 ms 뒤에야 보인다 |
| **S-2** | **캡처는 OCR 보다 먼저, 모든 디스플레이를 한 번에 끝낸다** (≈31 ms) | 캡처가 전체의 4 % 뿐이고, 디스플레이 1 을 OCR 하는 335 ms 동안 화면이 바뀌면 디스플레이 2 의 캡처는 **다른 시점의 화면**이 된다(§5 #9) | 디스플레이마다 "캡처 → OCR" 을 반복 — 화면들의 시점이 최대 775 ms 어긋난다 |
| **S-3** | **전처리 기본값은 `None`.** 프리셋은 남겨 두되 켜지 않는다 | §4 — 일반 화면에서 이득이 지터에 묻히고, 신뢰도는 오히려 떨어지기도 한다. **이득이 측정되지 않은 비용을 기본으로 켜지 않는다** | 항상 Noir 적용 — 후보 수는 늘지만 같은 텍스트의 다른 오인식이고 평균 신뢰도가 내려간다 |
| **S-4** | **`recognitionLanguages` 기본값은 Vision 기본(영어).** 한국어는 **사용자가 켜는 설정**으로 노출하고, 켜면 느려진다는 것을 UI 에 밝힌다 | §3 — ko-KR 을 기본으로 켜면 전체 화면이 775 ms → **3.1 s** 가 된다. 반대로 켤 수단이 없으면 한국어 사용자에게 Seek 이 **아무것도 못 찾는 기능**이 된다 | ① 항상 ko-KR 우선 — 4배 지연을 전원에게 물린다. ② 아예 노출하지 않기(원본과 동일) — 원본은 영어 단일 앱이지만 이 클론은 아니다 |
| **S-5** | **앱 시작 시 Vision 을 한 번 예열한다** | §2.5 — 콜드 첫 호출이 약 120 ms 비싸다. 그 120 ms 를 **사용자가 처음 Seek 을 여는 순간**에 물릴 이유가 없다 | 예열하지 않기 — 첫 세션만 유독 느리다 |
| **S-6** | ⭐ **F-01 은 검출이 끝나기를 기다리지 말고 세션을 즉시 열어야 한다.** F-02 는 후보를 **비동기·증분**으로 내보내는 API 를 제공한다 | 775 ms 동기 블로킹은 제품이 성립하지 않는다. S-1 과 합치면 주 디스플레이 후보가 **약 335 ms** 에 도착한다 | 검출 완료 후 오버레이 표시 — 캡스락을 누르고 0.8 초 동안 아무 일도 안 일어난다 |

> **S-6 은 F-01(`seek-activation-and-session.md`)·F-03(`seek-overlay-ui.md`) 에
> 대한 요구사항이다.** F-02 의 범위를 넘으므로 여기서는 API 형태만 제공하고
> 구현하지 않는다 — 그 두 위임이 이 문서를 근거로 삼아야 한다.

## 6. ⚠️ 이 스파이크가 **확인하지 못한 것**

정직하게 남긴다.

| # | 확인 못 한 것 | 왜 |
| :--- | :--- | :--- |
| 1 | **Retina(`scale = 2.0`) 실기기 동작** | 이 기기에 붙은 두 디스플레이가 모두 `scale = 1.00` 이고 Retina 패널이 없다. 해상도(시스템 설정)를 바꿔 HiDPI 모드를 만드는 것은 이 작업의 경계 밖이라 하지 않았다. §3.2.3 3단계는 `ultrakey-seek` 의 **단위 테스트로만** 검증됐다 |
| 2 | 명세 §5 #12 의 확인된 OCR 실패 사례(극소 텍스트·저대비 색상·인접 줄) | 임의의 데스크톱 화면 표본에 그런 콘텐츠가 없었다. 전처리 프리셋의 진짜 값어치는 이 사례들에서만 드러난다 |
| 3 | 전체화면(Full Screen) 스페이스·Stage Manager 에서의 캡처 결과 (§5 #5, #15) | 측정 대상이 아니었다 |
| 4 | Screen Recording **권한이 없을 때** 실제로 무엇이 돌아오는가 | 측정 시점에 권한이 이미 부여되어 있었다. 조용한 실패 감지 코드(`screen_recording.rs`)는 `CGPreflightScreenCaptureAccess` 로 **권한 자체**를 보므로 이 미확인에 영향받지 않지만, "배경만 담긴 이미지" 를 직접 눈으로 본 것은 아니다 |
| 5 | 저사양 기기에서의 지연 | M4 Pro 한 대에서만 쟀다. 더 느린 기기에서는 775 ms 가 더 커진다 |
